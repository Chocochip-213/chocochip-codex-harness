# chocochip-codex-harness

Codex CLI로 과제를 풀 때 쓰는 개인 작업 도구 모음입니다.
작업 규칙, 스킬 여덟 개, 데이터·환경 점검 도구를 과제 폴더에 설치합니다.
요구 확인부터 단계별 개발, 결과 검증, 문서 정리까지 매번 정해진 순서로 작업하도록 돕습니다.

데이터 분석과 결과 화면 만들기, 기존 코드 수정에 쓸 수 있습니다.
과제별 판정 코드·화면·결과물은 들어 있지 않고, 작업하면서 만듭니다.

흐름: `$kickoff` → 담당자에게 질문을 보내고 답을 붙여 넣기 → `/new` 뒤 `/plan`으로 계획 → 한 단계씩 개발 → `/new` 뒤 `$verify` → `/new` 뒤 `$wrapup` → `/new` 뒤 `$weakness`

`/new`(새 대화)는 다음 대화에 필요한 것이 모두 파일·커밋에 있는 경계(개발 시작 메모·계획 저장·단계 기록·검증 보고 뒤)에서만 씁니다. Codex의 보고가 그때만 `/new`를 안내하니, 안내가 없는 단계 도중에는 쓰지 않습니다.

개발 중에는 다른 터미널 탭에 읽기 전용 Codex(`codex -s read-only -a never`)를 하나 더 켜고 `$tutor N단계`로 진행 중인 단계를 설명받습니다(아래 '곁에서').

## 설치

### 처음 설치하기

Bash, Git, Python 3, Codex CLI가 있는 환경에서 씁니다.
**과제 작업 폴더 맨 위**로 이동한 뒤, Codex를 켜기 전에 터미널에서 실행합니다.
설치기는 하네스 파일을 바로 커밋하므로 같은 경로의 커밋하지 않은 변경도 함께 들어갈 수 있습니다. 먼저 `git status --short`로 `AGENTS.md`·`.agents/`·`.harness/`·`.codex/`에 그런 변경이 없는지 보고, 있으면 커밋하거나 정리합니다.
홈 폴더가 곧 과제 저장소이면 `.codex/`와 점 파일은 커밋하지 않습니다(Codex 기록·인증·키가 들어 있고, 설치기가 git에서 뺍니다). 이때 금지 규칙 파일은 `~/.codex/rules/`에 들어갑니다.

```bash
git clone --depth 1 https://github.com/Chocochip-213/chocochip-codex-harness /tmp/h && bash /tmp/h/setup.sh
```

설치기는 끝에서 도구 자체 점검(`bash .harness/tools/selftest.sh`)까지 돌립니다.
출력의 `자체 점검` 줄이 `실패 0`으로 끝나면 점검한 도구가 이 환경에서 동작합니다. `ui_check.py`는 도움말만 점검하므로 브라우저가 실제로 뜨는지는 처음 쓸 때 압니다.
실패한 도구는 그 줄 아래에 나오며 쓰지 않습니다.
점검에 실패해도 파일 설치는 끝난 상태입니다. 같은 명령을 직접 실행하면 원인이 보이고, 해결한 뒤 다시 점검합니다. 이 검사는 과제의 결과가 맞는지는 보지 않습니다.

이제 과제 폴더에서 `codex`를 실행합니다.
처음 켤 때 이 폴더를 신뢰한다고 답합니다. 신뢰한 폴더에서만 `.codex/`의 규칙을 읽습니다.
Fast 모드는 치트시트의 시작 명령처럼 실행 인자로 켜고 `/status`에서 실제 값을 확인합니다(하네스는 `.codex/config.toml`을 만들거나 바꾸지 않습니다. 이 실행 인자가 시험 환경에서 되는지는 미확인).
이미 켠 Codex에서 설치했다면 `/new`로 새 대화를 엽니다. 스킬과 금지 규칙은 새 대화부터 적용됩니다(Codex CLI 0.165에서 확인).
`/new` 뒤 어디서 실행할지 묻는 창이 뜨면 1(`Use current Git worktree`)을 고릅니다. 2를 고르면 다른 폴더의 복사본에서 작업하게 됩니다.

Codex에게 설치를 맡길 수도 있습니다.

```text
깃허브 Chocochip-213/chocochip-codex-harness를 /tmp/h에 clone해서 이 폴더에 설치해 줘.
```

이때 네트워크나 `.agents/`·`.codex/`·`.git/` 쓰기에 승인이 필요할 수 있습니다(횟수와 범위는 환경마다 다릅니다).
쓰기가 막히면 사용자가 과제 폴더의 터미널에서 위 설치 명령을 직접 실행합니다(`/tmp/h`가 이미 있으면 `bash /tmp/h/setup.sh`).
설치기가 멈추면 Codex는 과제 파일을 지우거나 옮기지 않고 멈춘 이유를 알립니다.

### 다시 설치할 때

`/tmp/h`에 이 저장소가 이미 있으면 다음 명령만 실행합니다.
설치나 커밋이 중간에 멈췄을 때도 같은 명령으로 다시 시도합니다.

```bash
bash /tmp/h/setup.sh
```

이 명령은 `/tmp/h`의 파일을 다시 설치할 뿐 새 버전을 받지는 않습니다(새 버전은 `git -C /tmp/h pull` 뒤 같은 명령).
작업 폴더를 따로 지정하려면 `bash /tmp/h/setup.sh <작업 폴더>`로 실행합니다.

기존 파일은 이렇게 다룹니다.

- `AGENTS.md`가 있으면 끝에 하네스 규칙을 붙입니다. 다시 설치하면 구분 주석(`<!-- chocochip-codex-harness -->`) 아래만 갱신합니다.
- 하네스가 설치한 스킬과 `.harness/tools/`·`.harness/vendor/`는 새 사본으로 바꿉니다.
- `.codex/`에는 금지 규칙 파일만 넣습니다. 과제나 플랫폼의 `.codex/config.toml`은 읽지도 바꾸지도 않습니다.
- 과제의 `commit-msg` 훅이나 `core.hooksPath` 설정이 있으면 하네스 훅을 넣지 않습니다.
- 같은 폴더 이름의 과제 스킬이 있으면 멈춥니다.
  - 다만 `.harness/`가 비어 있거나, 하네스 표시 파일(`.harness/SOURCE.txt`·`.harness/INSTALLING`)은 있는데 `.harness/INSTALLED_SKILLS` 목록이 없으면 같은 이름의 폴더를 덮어씁니다. 그때는 설치 전에 같은 이름의 과제 스킬이 없는지 직접 봅니다.
  - `.harness/`에 표시 파일은 없고 다른 파일이 있으면 멈춥니다.
- `/`, 하네스 저장소 자체나 그 안에는 설치하지 않습니다.
- 홈 폴더에는 그 자체가 과제 git 저장소의 맨 위일 때만 설치하고, 맨 위의 점 파일·폴더를 `.git/info/exclude`에 넣어 git에서 뺍니다(`.gitignore`·`.gitattributes`·`.github/`·`.streamlit/`은 빼지 않습니다).
- 과제의 다른 스킬 폴더가 `SKILL.md`에서 같은 `name:`을 쓰면 경고만 합니다. 이때는 `.agents/skills/kickoff/SKILL.md를 읽고 그대로 해 줘`처럼 경로로 부릅니다.
- `AGENTS.override.md`가 있으면 Codex가 `AGENTS.md` 대신 그 파일을 읽을 수 있어 설치기가 경고합니다. 그 파일은 고치지 말고 `$kickoff`로 시작합니다(`$kickoff`는 `AGENTS.md`를 직접 읽습니다).
- `AGENTS.md`가 32,000바이트를 넘으면 뒷부분(하네스 규칙)이 잘려 읽힐 수 있다고 경고합니다. 이때는 `$kickoff` 전에 `AGENTS.md에서 <!-- chocochip-codex-harness --> 줄 아래를 직접 읽고 따라 줘`라고 먼저 보냅니다.

### 설치 커밋 확인하기

Git 저장소 맨 위에서 설치하면 `chore(harness): 작업 도구 추가 (...)` 커밋을 만듭니다.
대상은 `AGENTS.md`, 하네스가 설치한 스킬 폴더 여덟 개, `.harness/`, 하네스 규칙 파일(홈 폴더가 과제 저장소이면 뺌)입니다. 과제에 있던 다른 `.agents/` 파일은 넣지 않습니다. 이 경로에 있던 커밋하지 않은 변경은 함께 들어갈 수 있습니다(설치 전 확인은 '처음 설치하기' 참고).
Git 저장소가 아니거나 저장소의 하위 폴더이면 파일만 설치하고 커밋하지 않습니다.

설치 출력의 `git:` 줄에서 커밋 여부를 확인합니다. 이름·이메일이 없으면 안내대로 설정한 뒤 설치기를 다시 실행합니다.
커밋에 실패해도 파일 설치는 끝났을 수 있습니다.

## 작업 흐름

스킬은 Codex에게 맡길 작업 절차입니다. 자동으로 선택되지 않으니(각 `agents/openai.yaml`의 `allow_implicit_invocation: false`) `$kickoff`처럼 이름을 직접 지정해 부릅니다.

### 1. `$kickoff`: 요구와 데이터 읽기

사용자도 과제 README를 직접 읽고, 이해한 목표를 한 줄로 적어 시작합니다.
남은 시간이 정해져 있으면 함께 알려 줍니다.

```text
$kickoff 남은 시간 <남은 시간>. 내가 읽은 목표: <한 줄>
```

Codex는 이 시간에 비율을 두어 계획 문서에 시간 기준점(질문 마감·기본판·중간 검증·기능 동결·제출 시작 시각)을 적습니다.

- 기능 동결 뒤에는 검증·마감·설명 점검과 필수 요구의 결함 수정만 합니다.
- 제출 시작(마감 30분 전) 뒤에는 코드·입력·설정을 고치지 않고 사람 몫 칸·최종 커밋까지 마치고, 남은 시간은 점검 질문 연습에 씁니다.
- 남은 시간을 말하지 않으면 README의 제한 시간으로 짐작하니 다르면 고쳐 줍니다.

환경, README, 데이터와 기존 코드를 살펴봅니다.
기존 코드가 있으면 테스트와 오류 재현도 확인합니다. 구현과 패키지 설치는 하지 않습니다.

계획 문서(기본 `PLAN.md`. 이름 규칙은 '작업 중 생기는 문서')에는 만들 것, 성공 기준, 데이터 사실과 이상한 점을 적습니다.
협업 기록(`COLLAB.md`)에는 요구 확인표를 만들고 상태를 `확정`·`가정`·`질문`·`정의 확인`으로 나눕니다.
제출할 양식 파일은 따로 두고 마감 때 그 양식대로 채웁니다.

대화에서는 과제 요약과 판정 규칙, 애매한 곳을 설명합니다.
담당자에게 보낼 질문은 `COLLAB.md`의 '보낼 질문' 절에 한 줄에 하나씩 씁니다. 한 줄은 담당자가 한 번에 답할 결정이나 사실 하나만 묻고, 실제 데이터 한 건이나 결과를 쓰는 장면을 짚습니다.

**보낼 질문은 사용자가 고르고, 편집기에서 복사해 담당자에게 직접 보냅니다.**
빼거나 바꿀 질문을 말하면 Codex가 그 절을 고쳐 씁니다.
뺀 질문은 처리안이 '가정'으로 남아 범위 합의 때 기본값으로 담당자에게 갑니다.
파일과 다르게 고쳐 보냈으면 답을 붙일 때 그렇다고 알립니다.

### 2. `$relay`: 답을 기록하고 범위 정하기

담당자 답은 담당자와 주고받은 내용을 그대로 긁어 붙여 넣습니다(모양은 상관없습니다).

```text
<담당자 창에서 긁은 질문과 답 그대로>
```

- 앞에 아무것도 붙이지 않아도 Codex가 relay 절차로 처리하고 질문과 답을 짝지으며, 이미 기록한 쌍이 섞여도 다시 적지 않습니다.
- 답을 요약해서 옮겼다면 `담당자 답 요약:`이라고 적습니다.
- 답 끝의 한 줄(남은 질문 수나 바뀐 것)이 안 나오면 같은 내용 앞에 `$relay`를 붙여 다시 보냅니다.
- 개발 중에 새 답이 와도 같습니다. 기록만 하고 코드는 다음 단계를 시킬 때 고치며, 기준이 바뀌면 메모 끝 '합의 뒤 변경'에 남습니다.

협업 기록과 요구 확인표를 고치고, 다음 질문이나 범위 합의 메시지를 '보낼 질문' 절에 씁니다.
답이 온 줄은 담당자 확인 기록으로 옮기고, 사용자가 보냈다고 했거나 붙인 내용에 보낸 질문으로 들어 있는데 답이 없는 줄은 '보냄(답 대기)'로 남깁니다.
답에 붙은 조건은 함께 기록하고, Codex가 보탠 해석은 가정으로 남깁니다.

- 담당자가 일부만 답하면 가장 중요한 질문 하나만 다시 묻고, 그다음부터는 평소대로 묻습니다. 개수를 줄여 달라고 했을 때만 받아 준 개수로 줄입니다.
- 담당자가 모른다고 한 업무 사실은 그 사람에게 다시 묻지 않고, 아는 담당자(적힌 곳이 없으면 아직 묻지 않은 담당자 한 명)에게 한 번 묻습니다. 확인하지 못한 사실 자체는 사용자 선택으로 확정하지 않고 '미확인 한계'로 남습니다.
- 만드는 쪽에 맡긴 주제는 다시 묻지 않습니다.
- 모른다고 했거나 맡긴 주제에서 판정 기준·점수·우선순위는 가정으로 두고 기본판 뒤 `$criteria`에서 고르고, 그 밖에는 결과를 크게 바꾸는 처리 방침만 사용자에게 묻습니다.
- 질문 마감이 지나면 남은 질문은 '가정(기본값)'으로 두고(보낸 줄의 '답 대기' 표시는 남깁니다) 범위 합의로 갑니다.

범위를 합의하기 전에 Codex가 사용자에게 두 가지를 묻습니다. ① 성공 기준과 만들지 않을 것이 이대로 맞는지, ② 조건이 부딪치거나 시간이 모자라면 무엇을 지키고 무엇을 조정할지. 이미 말한 것은 다시 묻지 않습니다.
합의 메시지에는 결과를 바꾸는 가정과 기본값도 넣습니다.
담당자가 동의한 답을 위처럼 붙여 넣으면 계획 문서 맨 위에 **개발 시작 메모**를 쓰고 커밋합니다.
기본값을 "알아서 정하세요"라고 맡긴 답도 동의로 봅니다. 동의는 답한 담당자의 항목에만 반영합니다.
결과를 바꾸는 선택이 아직 남아 있으면 메모를 쓰기 전에 그 부분만 다시 묻습니다('$criteria에서 정함' 가정은 세지 않습니다).
동의 답이 10분 안에 오지 않으면 `동의 대기로 두고 개발 시작 메모 써 줘`라고 보내 계획으로 넘어갑니다.

### 3. `/plan`: 계획을 세우고 한 단계씩 만들기

`/new`로 대화를 새로 엽니다(선택 창이 뜨면 1). 질문으로 길어진 대화는 비우고, 개발 세션은 개발 시작 메모만 읽고 시작합니다.

`/plan`을 입력한 뒤 다음 문장을 붙여 넣습니다.

```text
계획 문서에서는 '개발 시작 메모' 절만 읽고 그대로 계획 세워 줘.
① 메모 항목 번호마다 맡을 단계와 완료 확인을 붙여 줘('못 물음'은 미확인으로 남기고 '없음'만 빼고, 한 단계가 여러 항목을 맡아도 된다).
② 단계마다 만들거나 고칠 것에 근거 항목 번호(메모 번호나 ⑦의 A번호)를 붙여 줘. A번호를 근거로 쓰려면 어느 메모 항목의 구현·검증에 왜 필요한지 적고, 번호를 못 붙이면 그것 없이 어느 항목을 만들거나 검증할 수 없는지 적어 줘. 같은 항목을 채우는 방법이 여럿이면 요구에 없는 기능이 덜 들어가고 고치기·검증하기 쉬운 쪽을 골라 줘(패키지를 쓸지 직접 만들지는 이 기준이 아니라 `.harness/LIBS.md` 원칙대로 정하고, 서버·화면·도표 도구는 그 웹 행대로 후보와 추천을 보여 주면 내가 고른다).
③ 그것도 못 적는 것은 빼서 맨 아래 '넣지 않은 것'에 한 줄로 남겨 줘.
④ 기본판 단계는 맨 앞에 두고 시간 기준점의 기본판 시각을 목표로 하고, 화면이 요구되면 요구된 로그인을 거쳐 실제 입력의 결과를 보는 최소 화면까지 포함해 잡아 줘.
⑤ 판정 기준이 미정이거나 담당자가 만드는 쪽에 맡긴 항목(메모에 '$criteria에서 정함'으로 적힌 것 포함)을 다루는 단계는 이름에 $criteria를 붙이고 기본판 뒤에 두되, 그 단계에는 기준 비교·선택과 고른 기준의 적용만 넣고 그 기준과 무관한 구현은 다른 단계에 둬 줘(그 기준이 결과의 단위나 저장 구조를 바꾸면 그 선택의 추천과 영향을 ⑦ 구조 단락에 적고 계획 승인 때 함께 정해 줘).
⑥ README가 요구한 제출 파일(실행 안내·설정 파일 등)은 그것이 쓰이는 단계에 넣어 동결 전에 준비하고(과제가 준 양식 파일은 제목·질문 줄·순서를 그대로 두고 그 아래만 채우며 새 제목을 만들지 않는다. 최종 검증 결과·사용자 확인을 반영하는 마감 갱신은 wrapup에서. 사용자 자신의 서술을 요구하는 칸은 대신 쓰지 않고 양식대로 두되 사용자가 준 답은 그대로 옮기고, 그 파일을 쓰는 단계 줄에 '사용자 답이 없는 사람 몫 칸은 비워 둔다'를 적어 줘), 중간 검증 $verify도 단계 한 줄로 넣어 줘. 기본판 보고 때 기본판 시각이 지나 있으면 남은 단계와 뺄 단계 후보·영향을 그 보고에 적어 줘(내가 고르기 전에는 빼지 않는다).
⑦ 단계 절 맨 앞(단계 목록 바로 위)에 구조 한 단락을 줄마다 번호(A1…)와 그렇게 둔 이유 한 마디를 붙여 써 줘: 구성 요소와 주고받는 것, 무거운 계산·변환을 언제 해서 어디에 두는지, 데이터 크기와 쓰는 사람 수에 맞춰 결과를 한 번에 내는 양, 다시 켜도 유지돼야 할 상태, 계산부터 그 결과를 쓰기까지 사이에 입력·상태가 바뀌거나 같은 요청이 겹칠 수 있고 결과에 영향을 주면 어느 시점의 입력으로 계산하고 결과에 그 입력 시점을 남기는지(아니면 '없음'), 실패를 어디에 남기는지. 기존 코드가 있으면 그 구조를 적고, 메모에 없는 것은 가정으로, 해당 없는 항목은 '없음'으로 쓴다('없음'을 채우려고 새 부품을 만들지 않는다)(웹이면 `.harness/LIBS.md` 웹 행대로 서버·화면 방식(도표가 있으면 도표 도구도)을 ②대로 정하고 그 행의 함정을 본다).
⑧ 계획이 승인되면 Default 모드로 돌아간 첫 요청에서 구조 단락·단계·'넣지 않은 것'을 계획 문서 '단계' 절에 그대로 옮기되 화면(템플릿·화면 요청 처리·스타일 파일)을 만들거나 고치는 단계는 ⑤처럼 이름 끝에 $screen을 붙이고(기준 비교·검증·마감 단계에는 붙이지 않는다), 계획 중 비교한 안의 핵심 숫자·고르거나 버린 이유와 내가 고른 것·내가 말한 이유('사용자 결정')를 결정 기록에 적어 커밋한 뒤 /new와 첫 단계를 시킬 문장 하나(첫 단계가 화면을 만들거나 고치면 앞에 $screen을 붙여)를 안내해 줘(Plan 모드는 파일을 쓰지 않는다).
```

웹 과제면 기존 코드·README·사용자가 먼저 정한 방식은 따르고, 남은 것만 계획 중에 고릅니다. 원하면 `$kickoff` 때 먼저 골라도 됩니다.

- 서버, 화면을 그리는 방식, 스타일 방식, 도표 도구마다 README 요구의 수준(역할·로그인·화면 수·표·도표 등)에 맞는 후보 둘셋이 쉬운 말로 나옵니다. 스타일만 다른 안도 비교합니다.
- 후보마다 이 과제의 요구에서 좋은 점·나쁜 점, 구조(어디를 고치기 쉬운지), 화면 완성도(채점자가 화면을 스크린샷으로 봅니다), 직접 만들 부품의 양과 깨질 위험, 설치·빌드 절차와 실패 위험, 추천 이유가 붙습니다.
- 모르는 말은 되묻고, 고를 때 한 줄 이유를 붙이면 결정 기록에 사용자 결정으로 남습니다.
- 고른 뒤에는 새 요구나 설치·검증 실패가 없으면 다시 비교하지 않습니다.

1. 계획을 읽고 `Implement this plan?`이 나오면 1(전부 한 번에 만들기)을 누르지 않고 `Esc`로 닫습니다.
2. `Shift+Tab`으로 `Default` 모드로 돌아가, 아래의 `Plan mode` 표시가 사라졌는지 확인합니다.
3. 같은 대화에서 `계획을 계획 문서에 옮기고 커밋해 줘.`라고 보냅니다. Codex가 승인된 계획을 계획 문서의 '단계' 절에, 비교한 안과 사용자의 선택·이유를 결정 기록에 적어 커밋하고 `/new`와 첫 단계를 시킬 문장을 안내합니다(첫 단계는 문맥을 비운 새 대화에서 시작합니다).
4. `/new` 뒤 안내받은 문장(예: `계획의 첫 단계 해 줘.`)을 보냅니다. 번호를 붙이지 않습니다(계획 위쪽이 화면에서 사라져 잘못 볼 수 있습니다). 그 뒤 단계는 계획 문서의 번호로 시킵니다.

코드를 만든 단계의 보고에는 `EXPLAIN.md`에도 남는 쉬운 설명 세 줄이 붙습니다: 이번에 만든 것, 실제 입력 한 건이 거치는 함수와 결과(그 결과를 정한 계획 문서 기준 줄), 약한 곳과 생길 일.
코드를 쓰지 않은 단계는 한 줄이고, 스킬을 부른 턴은 그 스킬의 보고 순서를 따릅니다.
사용자에게 퀴즈를 내지 않으니 정할 것이 없으면 바로 다음 단계를 시킵니다. 설명이 알던 기준과 다르면 그 자리에서 묻습니다.

중간 검증 전인데 그 시각이 지났거나 기능 동결 시각이 지나면 Codex는 단계 도중이라도 멈추고 한 것·남은 것을 적어 커밋합니다.
사용자가 먼저 시간을 봤으면 `Esc`로 끊고 `시간 됐어. 여기서 멈추고 한 것·남은 것을 계획 문서에 적고 커밋해 줘`라고 보냅니다.

화면을 만들거나 고치는 단계는 Codex가 안내하는 문장에 `$screen`이 붙습니다.

- 직접 시킬 때는 `$screen N단계 해 줘`로 하되, 같은 대화에서 이미 불렀으면 다시 붙이지 않습니다(붙일 때마다 스킬 전문이 다시 들어갑니다).
- `screen` 스킬은 역할별 핵심 답·근거·현재 상태·다음 행동이 실제로 여는 폭에서 읽히게 합니다.
- Codex는 첫 주요 화면이 동작한 뒤, 배치·상태를 바꾼 주요 화면 뒤(사용자가 문제를 말한 화면도), 제출 전에 `.harness/tools/ui_check.py`로 실제 브라우저에서 찍어 큰 문제부터 고칩니다. 점검·수정은 다음 시간 기준점까지만 하고 못 고친 것은 '남은 문제'로 적습니다.
- 도구 설치는 3분까지만 시도하고 같은 원인이면 다시 하지 않습니다. 못 쓰면 프로젝트의 브라우저 테스트 이미지로 대신하고, 그것도 없으면 사용자가 IDE 브라우저에서 실제 폭으로 보고 어느 영역이 어느 폭에서 어떻게 보이는지 말해 줍니다.

이름에 `$criteria`가 붙은 단계는 `$criteria N단계 해 줘`로 시킵니다.

- 방법이 미정이면 서로 다른 계열의 후보를, 방법은 정해졌으면 미정인 기준값·가중치만 기준선과 비교합니다. 독립 계산 전 숫자에는 '검증 전'이 붙습니다.
- 사용자가 얻는 것·잃는 것과 추천 이유를 보고 고릅니다.
- 중간 검증 시각이 되면(이미 지났으면 바로) 비교를 끝내고 추천안과 재검토 조건을 보입니다.
- 동결 전에 적용·검증을 끝낼 수 없는 새 계산 방식은 들이지 않습니다.

웹 서버는 Codex가 백그라운드로 띄우고 주소를 알려 줍니다(출력은 `/tmp/server.log`).
서버 코드를 고치면 Codex가 옛 서버를 끄고 다시 띄운 뒤 확인합니다. 사용자는 알려 준 주소를 Browser로 봅니다.

### 4. `$verify`: 결과를 따로 계산해 비교하기

핵심 결과가 갖춰진 중간 점검에서 한 번 부릅니다. 제출 전에는 아직 검증하지 않았거나 마지막 검증 뒤 코드·입력·설정·합의가 바뀌었을 때만 다시 부릅니다.
새 에이전트가 데이터를 처음부터 다시 읽어 토큰이 많이 드니, 부르기 전에 `/status`로 남은 컨텍스트와 사용량을 봅니다.

기본판(입력에서 결과까지 처음 한 번 도는 것)이 나왔을 때는 보통 `$verify`를 부르지 않습니다.
웹이면 사용자가 실제 주소와 창 폭으로 로그인부터 핵심 작업·다시 열기까지 직접 해 보고, 어느 역할로 무엇을 했고 무엇이 보였는지 말합니다.
실제 입력 하나의 처리 순서·결과·그 기준과 아직 확인 못한 점의 확인 방법을 자기 말로 적어, 기록·결과와 다른 곳만 짚어 받습니다.
고칠 것은 그 대화에서 시키지 않고 기본판 보고가 안내한 `/new` 뒤 첫 문장에 붙입니다.
중요한 전제가 의심되면 그때 `$verify`를 불러도 됩니다.

```text
$verify 해 줘
```

숫자를 미리 알 필요는 없습니다. 스킬이 사람이 바로 쓰는 숫자나 결과를 적어도 세 개 고르고, 화면에 요구된 계산값은 실제 입력 한 건의 화면 값도 대조합니다. 숫자가 아닌 결과는 합의한 제약과 정상·빈 결과·실패 때 약속한 모양을 봅니다.
꼭 볼 것이 있으면 아래처럼 덧붙입니다. 결과를 본 뒤에는 확인된 것과 아직 주장하지 않을 것을 자기 말로 한 줄 남깁니다.

```text
$verify 해 줘. 특히 볼 것: <결정에 쓰이는 항목>, 이유: <왜 그것이 걱정되나>, 예상: <짐작되면 값>. 내가 본 장면: <어느 역할로 어느 주소·폭에서 무엇을 끝까지 했나>
```

웹이면 먼저 현재 서버의 응답과 판정 함수를 직접 부른 결과를 비교합니다.
요청은 `verify/curl_check.sh`에 모읍니다.
저장·승인처럼 업무 상태를 바꾸는 요청은 Codex가 따로 띄운 **사본 서버**(이 컴퓨터 안에서만 여는 127.0.0.1 주소)에서만 검사합니다(만들 결과 파일·로그인 세션은 예외).
사본 서버나 분리된 테스트로도 확인하지 못하면 미실행으로 남깁니다.
사람이 실제로 여는 주소·창 폭·역할에서 본 화면 장면만 '확인한 장면'으로 적고, 보지 못한 장면은 '미확인 장면'으로 보고서에 남깁니다.

끝난 단계의 요구마다 정해진 화면·요청·출력에서 실제로 되는지도 봐서 '미구현'·'미실행'·'부분'으로 적습니다.
누가 무엇을 할 수 있는지는 안내문이 아니라 실제 허용·거절 동작으로 보고, 그 조건을 이 서비스가 맡는지 합의되지 않았으면 담당자 질문이 나옵니다.

독립 계산은 지금까지의 대화를 넘기지 않은 새 에이전트(`spawn_agent`, `fork_turns: "none"`)가 합니다.
README, 요구 사본 `verify/spec_N.md`, 원본 데이터만 읽고 구현 코드와 구현 결과는 보지 않습니다. Codex가 그 값과 레코드별 판정을 구현과 비교합니다.
핵심 결과에 영향을 주는 가정은 다른 안으로도 계산합니다.
사용자가 후보를 고를 때 본 숫자와 검증 값이 다르면 보고 첫머리에 전과 후를 보입니다(기록에 숫자가 없으면 '선택 당시 값 미확인').
요구와 확인 항목이 같으면 기존 검증 스크립트를 다시 실행합니다.
새 에이전트를 쓸 수 없으면 구현 코드를 가져다 쓰지 않는 별도 스크립트로 직접 계산합니다.

모두 같으면 '담당자 결과 확인' 한 줄을 '보낼 질문' 절에 씁니다. 대표 사례 한 건의 입력·실제 결과·합의 기준의 구현값·남은 제한을 담당자가 알아보는 말로 보이고, 업무에서 확인할 수 있는 사실 하나만 묻습니다. 받은 답은 그 사례에만 적용합니다.

차이가 나도 자동으로 고치지 않습니다. Codex가 차이와 원인 후보를 설명하고, 사용자가 고치라고 하면 고친 뒤 다시 검증합니다.
"원인을 확인해 말해 줘. 합의한 기준과 어긋난 구현 실수면 고치고, 검증 쪽 실수거나 기준이나 가정을 새로 정해야 하는 차이면 고치지 말고 물어 줘."처럼 한 번에 맡겨도 됩니다.

검증 기록을 커밋하면 보고 끝에 `/new`와 다음에 보낼 문장이 나옵니다.

- 동결 뒤면 `$verify`→`$wrapup`→`$weakness` 중 마지막 변경 뒤 결정 기록에 완료 줄이 없는 첫 스킬 문장(보통 `$wrapup 해 줘`)
- 동결 전이고 남은 개발 단계가 있으면 남은 단계
- 동결 전인데 남은 개발 단계가 없으면 남은 분 안에 끝낼 후보 셋 이내를 보여 고르게 한 뒤 고른 단계나 `$wrapup 해 줘`

차이·미실행·미확인 장면이 남았으면 그 문장에 `verify/report_N.md` 경로와 먼저 처리할 것이 들어 있으니 그대로 보냅니다. 새 대화는 앞 대화를 보지 못합니다.
그 뒤 담당자 답도 '2. `$relay`' 절처럼 그대로 붙여 넣습니다.

### 5. `$wrapup`: 요구와 구현을 맞춰 보고 문서 정리하기

검증 보고의 안내에 따라 마감으로 넘어갈 때 `/new`로 새 대화를 열고 `$wrapup 해 줘`라고 보냅니다. 웹 서버가 꺼져 있거나 옛 코드로 돌면 Codex가 다시 띄웁니다.

요구를 하나씩 대조하고, 보통은 별도 에이전트가 하네스 설치 직전 커밋(`.harness/BASE`) 뒤의 모든 변경과 화면 내용을 검토합니다.
**이 검토자는 구현 코드를 읽습니다.** 요구의 근거는 README와 요구 사본에서 찾습니다.
새 에이전트를 쓸 수 없으면 같은 자료로 직접 검토합니다.
제출 시작까지 20분이 안 남았으면 새 에이전트 없이 빠졌거나 요구와 다른 구현만 직접 보고, 요청 안 한 동작·화면 표시 검토는 '미실행'으로 남깁니다.
화면 모양은 이와 별도로 실제 브라우저로 한 번 봅니다.

제출 문서(기본 `HANDOFF.md`)를 쓰고 계획 문서의 지난 상태 문장을 정리한 뒤 키·개인정보 모양 등을 점검합니다.
커밋된 파일만 받은 새 사본에서 실행 안내의 명령을 적힌 그대로(작업 상태와 분리하고 정해 둔 시간 안에서) 돌려 봅니다. 적힌 그대로 안 되는 곳은 고칠 후보로, 환경 때문에 확인하지 못한 것은 '미실행'으로 나눠 적습니다.

고칠 후보는 마지막에 한 번에 묻고, 사용자가 고르기 전에는 코드를 고치지 않습니다.
번호 질문에 답한 뒤에는 고른 내용과 수정·재검증 상태가 기록·커밋됐다는 안내를 확인하고, 필요하면 `/new` → `$wrapup 해 줘. 수정 계속`으로 이어 갑니다.
받는 역할로 들어갔을 때 고른 결과가 없거나 다른 조건의 결과가 작업 서버에 남아 있으면 앱의 기존 동작으로 반영할지도 이때 따로 묻습니다(업무상 그 역할이 직접 확정한다는 규칙이 있어도 묻습니다).
사람이 직접 하라는 요구가 있거나 직접 하겠다고 하면 Codex가 역할·주소·누를 것을 알려 주고, 아니면 허락했을 때 Codex가 반영합니다.

제출 문서에 사람의 판단·이해·직접 확인을 쓰는 칸(답변, 회고, 협업 기록의 사람 몫 등)은 Codex가 쓰지 않고 비워 둡니다.
마감 작업 뒤 새 대화를 열어 최종 제출 전에(점검 질문 연습보다 먼저) 사용자가 직접 씁니다. Codex와 이야기하며 쓸 사례를 고르고 기록과 다른 곳을 확인할 수 있습니다.
다 쓰면 점검 도구를 다시 돌려 커밋합니다.
사용자가 써 둔 답은 wrapup이 고치지 않습니다. 채워진 칸이 Codex가 쓴 것으로 확인되면 양식대로 되돌리고, 누가 썼는지 모르면 묻습니다.

수정 뒤에는 바뀐 것이 영향을 주는 검증만 다시 하고, 나머지는 이전 결과를 인용합니다. 기준이나 가정이 바뀌면 `/new` → `$verify 해 줘. wrapup 수정 확인`으로 다시 검증합니다.
서버 코드를 고쳤거나 도구로 못 본 화면이 있으면 Codex가 Browser로 확인할 목록(역할·동작·기대 화면)을 주니, 실제 주소와 창 폭으로 따라 해 보고 결과를 말해 줍니다.

### 6. `$weakness`: 직접 설명하고 남은 한계 확인하기

`$wrapup`을 마친 뒤 `/new`로 새 대화를 열고 `$weakness 해 줘`라고 보냅니다(wrapup 대화를 이어 쓰면 커져서 압축될 수 있습니다).

1. 사용자가 자기 말로 정리할 내용을 Codex가 묻고 기다립니다. 부딪친 조건, 틀리는 입력, 맡긴 일과 직접 확인한 일, 실제 입력 하나가 지나가는 길을 적습니다.
2. 답을 받은 뒤 코드·기록과 다른 곳을 짚고, 남은 약점과 설명 노트를 정리합니다.
3. `EXPLAIN.md`에 사용자 문장과 한 화면 요약을 남기고(커밋하지 않습니다), 제출 문서의 빠진 한계는 추가해 커밋합니다.
4. 점검 질문을 받아 풉니다(아래).

시간이 없으면 새 대화를 열지 않고 같은 대화에서 "$weakness 시간이 없어. 점검 질문 줘"로 앞의 정리를 건너뛰고 질문부터 받습니다.

- 점검 질문은 말한 개수(없으면 10개)를 한꺼번에 받고, 몇 개를 풀지는 앞에서부터 사용자가 고릅니다.
- 문항당 5분 안팎으로 AI 없이 쓰고, Codex가 실제 동작과 다른 곳을 짚습니다.
- 모르는 문항은 `N번 모범 답안 보여 줘`라고 청하면 그 문항만 기록에 근거한 답을 보여 줍니다(문장마다 근거 표시). 본 뒤에는 자기 말로 다시 씁니다.
- 실제 제출 전이면 제출 시작 시각이 함께 나옵니다. 그 시각에는 답을 멈추고 비워 둔 사람 몫 칸과 남은 한계 커밋을 확인한 뒤, 남은 문항을 풀고 Codex에 기록과 다른 곳만 짚게 합니다(코드는 고치지 않습니다).
- 모의 연습 뒤에는 "$weakness 연습이야. 점검 질문 6개 줘"로 시험의 후속 질문처럼 써 봅니다. 다 풀면 "연습이야. 6개 더 줘"라고 합니다.

### 곁에서: `$tutor`: 진행 중인 단계를 이해하기

단계 보고를 읽어도 어떻게 만들었는지 감이 안 올 때, 선택지 질문에 답하기 전에, verify·wrapup이 새 에이전트를 기다리는 동안 씁니다. 본 대화는 그대로 두고 다른 터미널 탭에서 같은 작업 폴더에 읽기 전용 Codex를 켭니다.

```bash
codex --no-alt-screen -s read-only -a never
```

```text
$tutor 2단계
$tutor <실제 ID>가 왜 그 결과가 되는지
$tutor 선택
<본 대화가 낸 선택지 질문을 그대로 붙임>
$tutor 전체
```

tutor는 계획 문서(개발 시작 메모·구조 단락·단계·결정 기록), 협업 기록, `EXPLAIN.md`, 지금 코드를 읽고 한 화면으로 답합니다: 하는 일, 쓰는 방법·패턴과 원리, 기록에 있는 이유, 다른 안과 맞바꿈, 실제 한 건이 거치는 길, 깨지는 곳.

- 문장마다 `[계획 파일:줄]`·`[코드 파일:줄]`·`[실행]`·`[셈]`·`[일반]` 꼬리표가 붙습니다.
- 기록에 이유가 없으면 "기록에 이유 없음"이라고 하며 지어내지 않습니다. 그때는 tutor가 준 '주 세션에 보낼 문장'(결정 기록에 이유를 적어 달라는 것)을 본 대화에 보냅니다.
- 선택지 질문을 붙이면 선택지마다 실제 한 건이 어떻게 달라지는지, 기록이 어느 쪽을 뒷받침하는지, 본 대화의 추천과 같은지를 말합니다. 고르는 것은 사용자이고, 고른 것과 이유는 본 대화에 자기 말로 답합니다.
- 사용자가 다른 안이 낫다고 하면 주장을 확인할 수 있는 문장으로 다시 쓰고, 기록·코드·일반 지식에서 뒷받침과 어긋남을 나눠 보이고, 가르는 확인 하나를 듭니다. 새 사실이나 앞 해석의 오류가 있을 때만 결론을 바꿉니다.
- 파일을 쓰거나 커밋하지 않고 구현 코드를 실행하지도 않습니다. 담당자 답은 여기 붙이지 않고 본 대화에 붙입니다. 대화는 아무 때나 `/new`로 비워도 됩니다.

훅과 제외 설정은 Git 폴더(보통 `.git/`) 안에 들어가 커밋되지 않습니다. 이미 추적 중인 파일에는 제외 설정이 적용되지 않습니다.
제외하는 이름은 `.env`, `.env.*`, `.ai_env`, `__pycache__/`, `*.pyc`, `EXPLAIN.md`입니다(`.env.example`은 다시 넣습니다).
설치 중에는 `.harness/INSTALLING` 표시를 두고 파일 설치가 끝나면 지웁니다.

차트 파일은 `.harness/vendor/chart.umd.min.js`입니다. 웹에서 쓸 때는 서비스의 정적 파일 폴더로 복사합니다.

금지 규칙에 적힌 명령 앞부분은 `git push`, `git remote add`, `git remote set-url`, `gh`, `git commit --no-verify`, `git commit -n`입니다.
허용 규칙은 추가하지 않으며, 다른 명령의 승인 여부는 Codex 설정을 따릅니다.
이 파일은 명령 앞부분을 비교하는 규칙이므로 모든 외부 전송을 차단하는 장치는 아닙니다.

작업 규칙의 커밋 형식은 `타입(범위): 한국어 요약`입니다.
훅은 `CODEX_THREAD_ID`나 `CODEX_TOOL_CALL_ID`가 있을 때만 검사합니다.
실제 훅은 범위 생략도 허용하며, 병합·되돌리기·fixup 같은 일부 메시지는 검사에서 뺍니다.

### 작업 중 생기는 문서

계획 문서와 제출 문서 이름은 과제 README에서 정한 것을 우선하고, 없으면 표의 이름을 씁니다. 협업 기록은 늘 `COLLAB.md`에 따로 둡니다.
아래 문서는 설치기가 미리 만들지 않습니다.

| 기본 위치 | 담는 내용 |
|---|---|
| `PLAN.md` | 만들 것, 기준, 개발 시작 메모, 단계, 결정 기록 |
| `COLLAB.md` | 요구 확인표, 보낼 질문, 실제로 보낸 질문과 담당자 답, 합의 |
| `EXPLAIN.md` | 단계별 쉬운 설명 세 줄('3. `/plan`' 절), 내 말로 정리, 한 화면 요약. 커밋 제외 |
| `HANDOFF.md` | 실행 방법, 구조, 판단 근거, 검증 결과, 남은 한계 |
| `verify/spec_N.md` | 개발 시작 메모·합의 뒤 변경·담당자 확인 기록의 사본 |
| `verify/checker_N/check.py` | 원본 데이터를 따로 읽어 계산하는 검증 코드 |
| `verify/report_N.md`, `verify/diff_N.csv` | 구현과 검증의 비교 결과, 다른 레코드 목록 |
| `verify/curl_check.sh` | 웹 화면과 요청을 확인하는 명령 |

`N`은 검증 번호입니다. 지난 검증기를 다시 쓰면 같은 번호를 씁니다. 요구 사본은 처음 만들거나 내용이 바뀔 때 커밋합니다.
`curl_check.sh`, 검증 코드와 보고서, 차이가 있는 비교 파일(다시 검증하며 고쳐 쓴 것 포함)은 커밋합니다.
검증기의 `rows.csv`·`assumption_diff.csv`, 서버 응답, 결과 사본과 로그는 커밋하지 않습니다.
행 대조용 목록은 `/tmp`에 따로 둡니다.

### 점검 도구

설치 뒤 과제 폴더 맨 위에서 `python3 .harness/tools/<도구 이름>`으로 실행합니다.
Python 도구는 표준 라이브러리만 씁니다. `ui_check.py`만 Playwright가 필요하고(프로젝트 가상환경에 설치했으면 그 파이썬으로 실행합니다), 없으면 설치 명령을 안내하고 끝납니다. 셸 도구는 `bash`로 실행합니다.

| 도구 | 확인하는 것 |
|---|---|
| `env_check.py` | Python·pip·PyPI 접속, 설치된 패키지, 포트, Git, 샌드박스 여부 |
| `profile_data.py` | 행 수, 결측, 값 종류, 숫자·날짜의 이상한 값, 표기 차이, 중복 |
| `join_check.py` | 두 표의 키 중복, 짝 없는 키, 빈 키, 합친 뒤 행 수 |
| `reconcile.py` | 입력 행이 쓴 행·뺀 행·따로 둔 행으로 빠짐없이 나뉘었는지 |
| `precheck.py` | 키·개인정보 모양, TODO·FIXME, 다른 글자(가나·한자), 문서의 `/tmp` 인용, 남은 검증 차이, 열지 못한 파일 |
| `ui_check.py` | 실제 브라우저로 화면을 여러 폭에서 찍고(PNG), 가로 넘침·화면 밖 요소·잘린 글자·이름표 없는 입력·콘솔 오류·실패한 요청을 셈(`report.json`) |
| `selftest.sh` | 임시 폴더에서 점검 도구 자체 검사 |

`env_check.py`는 인수 없이 실행합니다. 별도 도움말 처리가 없어 `--help`를 붙여도 환경 점검을 실행합니다.
네트워크와 포트 결과는 실행한 프로세스의 권한에 따라 달라집니다.
나머지 Python 도구는 `--help`로 사용법과 옵션을 봅니다.

도구마다 지원 범위가 다릅니다.

- **`profile_data.py`**: CSV·TSV·JSON·JSONL·NDJSON·SQLite를 읽습니다. 복합 키는 `--key 열1+열2`로 지정합니다. `--all`은 보여 줄 예시 개수의 제한을 풉니다.
  - SQLite 열 점검은 표마다 앞 50만 행까지만 봅니다(전체 행 수는 따로 셉니다). 형식과 상관없이 열별 값 종류가 상한(일반 열 20만 개, 첫 열과 ID처럼 보이는 열 200만 개)을 넘으면 값 목록·표기 차이·중복 점검을 생략합니다. `--all`을 붙여도 이 범위는 늘지 않습니다.
  - JSON에 목록이 여러 개이면 고른 목록과 건너뛴 목록도 확인해야 합니다.
- **`join_check.py`**: CSV·TSV·JSON·JSONL·NDJSON을 읽습니다. `--left 파일:열 --right 파일:열`로 비교합니다. 빈 키끼리는 연결하지 않습니다. 복합 키는 열 하나만 비어도 연결하지 않습니다. `left` 결과 행 수에는 짝 없는 왼쪽 행이 남습니다. `--show 0`으로 예시를 모두 볼 수 있습니다.
- **`reconcile.py`**: CSV·TSV·JSON·JSONL·NDJSON과 ID를 한 줄씩 적은 TXT를 읽습니다. 같은 ID가 여러 번 나오면 횟수까지 대조합니다. JSON 객체 안에 행 목록 후보가 여럿이면 하나를 임의로 고르지 않고 멈춥니다. `--show 0`으로 예시를 모두 볼 수 있습니다.
  - 입력 한 행이 결과 여러 행이 되는 작업은 `reconcile.py --help`의 ID 목록 방식을 따르는데, 결과에 입력 ID가 있는지만 보고 각 결과 행의 판정은 검증하지 않습니다.
- **`precheck.py`**: Git이 추적하는 파일과 무시되지 않은 새 파일을 검사합니다.
  - 입력 자료는 `--exclude`로 뺄 수 있고, `--include-ignored`를 붙이면 Git이 무시한 파일도 봅니다.
  - Git 저장소가 아니거나 무시된 폴더를 훑을 때는 `node_modules`·가상환경·캐시 폴더(홈 폴더가 작업 폴더면 맨 위 점 폴더도)를 건너뜁니다.
  - `.harness/`·`.agents/`·`.git/`과 이진 파일은 검사에서 뺍니다.
  - 찾은 키·개인정보 모양의 값은 가려서 출력합니다. 데이터 파일의 개인정보 모양은 기본으로 파일별 줄 수만 보여 주고, `--show-data`를 붙이면 가린 줄도 봅니다.
- **`ui_check.py`**: Playwright Chromium으로 주소를 엽니다.
  - 설치: `python3 -m pip install playwright && python3 -m playwright install --only-shell chromium`. 설치된 Chrome·Edge가 있으면 `--channel chrome`/`--channel msedge`.
  - 기본 폭은 800과 1280(IDE 미리보기 창 안팎과 넓은 창)이며 `--widths`로 실제 폭을 줍니다.
  - 로그인이 필요한 화면은 앱의 정상 로그인 폼을 `--login-url`과 계정 환경변수 이름으로 거치거나 `--storage-state`로 저장한 상태를 씁니다. 값은 출력하지 않고, 상태 파일과 PNG는 커밋하지 않습니다.
  - 안에서 가로 스크롤하는 표 감싸개 속 요소는 '화면 밖'으로 세지 않습니다.
  - 리눅스에서 브라우저용 시스템 라이브러리가 모자라면 관리자 권한 없이 `~/.cache/ui_check/`에 받아 풀고(못 받으면 동봉 예비 라이브러리), 한글 글꼴이 없으면 동봉 글꼴을 `~/.local/share/fonts/ui_check/`에 둡니다.

종료 코드의 뜻은 도구마다 다릅니다.

| 도구 | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| `env_check.py` | 늘 0 | — | — | — |
| `profile_data.py` | 점검함 | 읽을 파일 없음 | 사용법 오류 | — |
| `join_check.py` | 점검함 | — | 한쪽 행이 0개(빈 목록 포함) | 사용법·파일·실행 오류 |

`profile_data.py`는 파일별 읽기 오류를 출력한 뒤에도 0으로 끝날 수 있습니다.
종료 코드와 함께 출력의 생략·오류 안내를 읽습니다.

## 작업 원칙

- 과제 README와 담당자 답을 우선합니다. 과제에 있던 `AGENTS.md`와 하네스 규칙이 다르면 과제 규칙을 따릅니다.
- 답에 따라 결과의 숫자·ID·순서·권고가 바뀌면 담당자에게 보낼 질문으로 씁니다.
- 판정은 같지만 따로 둔 행을 어디에 어떻게 보여 줄지 같은 선택은, 달라지는 행을 건수·ID로 짚어 사용자에게 묻습니다.
- 계산·데이터 처리 방식·시스템 동작은 결과가 바뀌어도 사용자에게 묻습니다(담당자는 만드는 방법을 정해 주지 않습니다).
- 파일 나누기나 이름 짓기는 Codex가 정하고 보고합니다.
- 계획의 한 단계씩 작업합니다. 끝낼 확인 방법을 먼저 정하고, 끝나면 명령·종료 코드·건수를 보고합니다.
- 결정과 이유는 계획 문서의 결정 기록에 적고 커밋합니다. 약한 곳과 확인한 숫자는 설명 노트에 남깁니다.
- 커밋은 편집과 따로 처음부터 승인을 요청해 실행하니, 승인 창이 뜨면 파일과 명령을 보고 승인합니다.
- 확인 명령은 실행 전에 무엇을 읽고 쓰는지 보고, 입력 원본·업무 상태를 바꾸면 사본에서 합니다(만들 결과 파일·로그인 세션은 예외).
- 판정·계산은 화면과 분리하고 실제 레코드로 테스트합니다. 기대값은 요구·독립 계산·사례에서 정하고 구현을 돌려 얻은 값으로 삼지 않습니다.
- 입력 행을 나눠 결과를 만들면 행 대조도 합니다. 처리하지 못한 행은 사유와 함께 따로 두고, 그 행이 빠진 집계에는 이를 표시합니다.
- 합의한 범위 안에서 만듭니다. 패키지는 `.harness/LIBS.md`대로 고릅니다.
- 웹 서버는 `0.0.0.0`에서 열고 화면의 링크와 요청은 상대 경로를 씁니다. 외부(CDN) 파일을 쓰면 첫 화면에서 미리보기로 읽히는지 확인하고, 막히면 받아서 정적 폴더에 둡니다.
- 키를 커밋하지 않고, 개인정보는 로그에 그대로 내지 않으며 화면에는 요구된 만큼만 보입니다.
- 작업 규칙은 코드·데이터·기록의 외부 전송을 금지합니다. 외부에서 받아오는 설치와 과제 README가 정한 호출은 허용합니다.

## 하네스를 고칠 때

이 저장소에서 다음 명령으로 도구와 설치 동작을 확인합니다.

```bash
bash tools/selftest.sh
bash dev/test_setup.sh
```

둘 다 임시 폴더를 쓰고, 마지막 줄이 `통과 N, 실패 0` 꼴이어야 합니다.
`dev/test_setup.sh`는 이 저장소의 개발용 검사이며 과제 폴더에는 설치하지 않습니다.
이 검사는 `dev/check_plan_block.sh`도 돌려 계획 블록(①~⑧) 세 사본(치트시트·README·relay 스킬)이 같은지 봅니다.

작업 규칙 원본 `AGENTS.md`는 글머리 20개, 4,600자 이내로 유지합니다.
글자 수는 줄바꿈을 포함한 Python `len()` 기준이며 설치 테스트에서 확인합니다.
규칙을 늘릴 때는 겹치는 내용을 합치거나 필요한 스킬·도구 도움말로 옮깁니다.
