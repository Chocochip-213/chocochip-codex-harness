# chocochip-codex-harness

Codex CLI로 과제를 풀 때 쓰는 개인 작업 도구 모음입니다.
작업 규칙, 스킬 다섯 개, 데이터·환경 점검 도구를 과제 폴더에 설치합니다.
요구 확인부터 단계별 개발, 결과 검증, 문서 정리까지 매번 정해진 순서로 작업하도록 돕습니다.

데이터 분석과 결과 화면 만들기, 기존 코드 수정에 쓸 수 있습니다.
과제별 판정 코드·화면·결과물은 들어 있지 않고, 작업하면서 만듭니다.

흐름: `$kickoff` → 담당자 답마다 `$relay` → `/new` 뒤 `/plan`으로 계획 → 한 단계씩 개발 → `/new` 뒤 `$verify` → `/new` 뒤 `$wrapup` → `$weakness`

## 설치

### 처음 설치하기

Bash, Git, Python 3, Codex CLI가 있는 환경에서 씁니다.
**과제 작업 폴더 맨 위**로 이동한 뒤, Codex를 켜기 전에 터미널에서 실행합니다.
설치기는 하네스 파일을 바로 커밋합니다. 먼저 `git status --short`로 `AGENTS.md`·`.agents/`·`.harness/`·`.codex/`에 커밋하지 않은 변경이 없는지 보고, 있으면 먼저 커밋하거나 정리합니다.

```bash
git clone --depth 1 https://github.com/Chocochip-213/chocochip-codex-harness /tmp/h && bash /tmp/h/setup.sh
```

설치기는 끝에서 도구 자체 점검(`bash .harness/tools/selftest.sh`)까지 돌립니다.
출력의 `자체 점검` 줄이 `실패 0`이면 도구가 이 환경에서 제대로 동작한다는 뜻입니다. 실패한 도구는 그 줄 아래에 나오며, 쓰지 않습니다.
점검에 실패하거나 점검을 못 했어도 파일 설치는 끝난 상태입니다. 원인은 `bash .harness/tools/selftest.sh`를 직접 실행하면 보이고, 원인을 해결한 뒤 같은 명령으로 다시 점검합니다.
이 검사는 과제의 결과가 맞는지까지 확인하지는 않습니다.

이제 과제 폴더에서 `codex`를 실행합니다.
처음 켤 때 이 폴더를 신뢰한다고 답합니다. 신뢰한 폴더에서만 `.codex/`의 설정과 규칙을 읽습니다.
이미 켠 Codex에서 설치했다면 `/new`로 새 대화를 엽니다. 스킬과 금지 규칙은 새 대화부터 적용됩니다(Codex CLI 0.165에서 확인).
`/new` 뒤 어디서 실행할지 묻는 창이 뜨면 1(`Use current Git worktree`)을 고릅니다. 2를 고르면 다른 폴더의 복사본에서 작업하게 됩니다.

Codex에게 설치를 맡길 수도 있습니다.

```text
깃허브 Chocochip-213/chocochip-codex-harness를 /tmp/h에 clone해서 이 폴더에 설치해 줘.
```

이때 네트워크나 `.agents/`·`.codex/`·`.git/` 쓰기에 승인이 필요할 수 있습니다.
승인 횟수와 허용 범위는 실행 환경에 따라 다릅니다.
쓰기가 막히면 사용자가 과제 폴더의 터미널에서 위 설치 명령을 직접 실행합니다(`/tmp/h`가 이미 있으면 `bash /tmp/h/setup.sh`).
설치기가 멈추면 Codex는 과제 파일을 지우거나 옮기지 않고, 멈춘 이유를 사용자에게 알립니다.

### 다시 설치할 때

`/tmp/h`에 이 저장소가 이미 있으면 다음 명령만 실행합니다.
설치나 커밋이 중간에 멈췄을 때도 같은 명령으로 다시 시도합니다.

```bash
bash /tmp/h/setup.sh
```

이 명령은 `/tmp/h`에 있는 파일을 다시 설치합니다. 새 버전을 내려받지는 않습니다. 새 버전은 `git -C /tmp/h pull`로 받은 뒤 같은 명령을 실행합니다.
작업 폴더를 따로 지정하려면 `bash /tmp/h/setup.sh <작업 폴더>`로 실행합니다.

기존 파일은 다음과 같이 다룹니다.

- `AGENTS.md`가 있으면 끝에 하네스 규칙을 붙입니다. 다시 설치하면 구분 주석(`<!-- chocochip-codex-harness -->`) 아래만 갱신합니다.
- 하네스가 설치한 스킬과 `.harness/tools/`·`.harness/vendor/`는 새 사본으로 바꿉니다.
- 과제의 `.codex/config.toml`은 보존합니다. 파일이 없으면 새로 넣고, 하네스 주석(`# chocochip-codex-harness`)이 있는 파일만 새 내용으로 바꿉니다.
- 과제의 `commit-msg` 훅이나 `core.hooksPath` 설정이 있으면 하네스 훅을 넣지 않습니다.
- 같은 폴더 이름의 과제 스킬이 있으면 멈춥니다. `.harness/`가 이미 있는데 비어 있지도 않고 하네스가 만든 표시 파일(`.harness/SOURCE.txt`·`.harness/INSTALLING`)도 없으면 멈춥니다. 빈 `.harness/`에는 설치할 수 있습니다.
- 홈 폴더, `/`, 하네스 저장소 자체나 그 안에는 설치하지 않습니다.

과제의 다른 스킬 폴더가 `SKILL.md`에서 같은 `name:`을 쓰면 경고만 합니다.
이때는 `.agents/skills/kickoff/SKILL.md를 읽고 그대로 해 줘`처럼 경로로 부릅니다.
`AGENTS.override.md`가 있으면 Codex가 `AGENTS.md` 대신 그 파일을 읽을 수 있어 설치기가 경고합니다. 그 파일은 고치지 말고 `$kickoff`로 시작합니다(`$kickoff`는 `AGENTS.md`를 직접 읽습니다).

### 설치 커밋 확인하기

Git 저장소 맨 위에서 설치하면 `chore(harness): 작업 도구 추가 (...)` 커밋을 만듭니다.
대상은 `AGENTS.md`, `.agents/`, `.harness/`, 하네스 규칙 파일과 설치기가 넣은 설정 파일입니다.
이 경로에 있던 커밋하지 않은 변경도 함께 들어갈 수 있습니다(설치 전 확인은 '처음 설치하기' 참고).
Git 저장소가 아니거나 저장소의 하위 폴더이면 파일만 설치하고 커밋하지 않습니다.

설치 출력의 `git:` 줄에서 커밋 여부를 확인합니다.
이름·이메일이 없으면 사용자가 본인 이름·이메일을 안내대로 설정한 뒤 설치기를 다시 실행합니다.
커밋에 실패해도 파일 설치는 끝났을 수 있습니다.

## 작업 흐름

스킬은 Codex에게 맡길 작업 절차입니다. 이 저장소의 스킬은 자동으로 선택되지 않습니다.
`$kickoff`처럼 이름을 직접 지정해 부릅니다.
각 `agents/openai.yaml`에 `allow_implicit_invocation: false`로 설정해 두었습니다.

### 1. `$kickoff`: 요구와 데이터 읽기

사용자도 과제 README를 직접 읽고, 이해한 목표를 한 줄로 적어 시작합니다.
남은 시간이 정해져 있으면 함께 알려 줍니다.

```text
$kickoff 내가 읽은 목표: <한 줄>. 남은 시간: <남은 시간>.
```

환경, README, 데이터와 기존 코드를 살펴봅니다.
기존 코드가 있으면 테스트와 오류 재현도 확인합니다. 구현과 패키지 설치는 하지 않습니다.

계획 문서에는 만들 것, 성공 기준, 데이터 사실과 이상한 점을 적습니다.
협업 기록에는 요구 확인표를 만듭니다. 상태는 `확정`·`가정`·`질문`·`정의 확인`으로 나눕니다.
파일 이름은 과제 README를 따르고, 지정이 없으면 `PLAN.md`와 `COLLAB.md`를 씁니다.

대화에서는 과제 요약과 판정 규칙, 애매한 곳을 설명한 뒤 질문 초안을 줍니다.
질문마다 실제 데이터 한 건이나 결과를 쓰는 장면을 짚습니다.
**보낼 질문은 사용자가 고르고 담당자에게 직접 보냅니다.**

### 2. `$relay`: 답을 기록하고 범위 정하기

담당자 답이 올 때마다 붙여 넣습니다. 개발 중에 새 답이 와도 같은 스킬을 씁니다.

```text
$relay 담당자 답: <답 원문>
```

답을 요약해서 옮겼다면 `담당자 답 요약:`이라고 적습니다.
협업 기록과 요구 확인표를 고치고, 다음 질문이나 범위 합의 메시지를 만듭니다.
답에 붙은 조건은 함께 기록하고, Codex가 보탠 해석은 가정으로 남깁니다.
담당자가 일부만 답하면 가장 중요한 질문 하나만 다시 묻고, 그다음부터는 평소대로 묻습니다. 개수를 줄여 달라고 했을 때만 받아 준 개수로 줄입니다.

범위를 합의하기 전에 사용자가 성공 기준과 만들지 않을 것을 확인합니다.
합의 메시지에는 결과를 바꾸는 가정과 기본값도 넣습니다.
담당자가 동의한 답을 `$relay`에 붙여 넣으면 계획 문서 맨 위에 **개발 시작 메모**를 쓰고 커밋합니다.
결과를 바꾸는 선택 가운데 아직 정하지 않은 것이 답에 남아 있으면 메모를 쓰기 전에 그 부분만 다시 묻습니다.

### 3. `/plan`: 계획을 세우고 한 단계씩 만들기

`/new`로 대화를 새로 엽니다(선택 창이 뜨면 1). 개발 세션은 개발 시작 메모를 읽고 시작합니다.
질문과 데이터 점검으로 길어진 대화는 비우고, 합의한 내용은 문서로 이어받습니다.

`/plan`을 입력한 뒤 다음 문장을 붙여 넣습니다.

```text
계획 문서에서는 '개발 시작 메모' 절만 읽고 그대로 계획 세워 줘.
① 메모 항목 번호마다 맡을 단계와 완료 확인을 붙여 줘('못 물음'은 미확인으로 남기고 '없음'만 빼고, 한 단계가 여러 항목을 맡아도 된다).
② 단계마다 만들거나 고칠 것에 근거 항목 번호를 붙여 줘. 번호를 못 붙이면 그것 없이 어느 항목을 만들거나 검증할 수 없는지 적고, 더 작은 방법이 있으면 그것을 골라 줘.
③ 그것도 못 적는 것은 빼서 맨 아래 '넣지 않은 것'에 한 줄로 남겨 줘.
```

1. 계획을 읽고 `Implement this plan?`이 나오면 1을 누르지 않고 `Esc`로 닫습니다. 1을 누르면 전부 한 번에 만들기 시작합니다.
2. `Shift+Tab`으로 `Default` 모드로 돌아가, 아래의 `Plan mode` 표시가 사라졌는지 확인합니다.
3. 계획의 첫 단계 번호로 `N단계 해 줘.`라고 보냅니다. 계획은 앞의 시작 점검·범위 합의를 이어 3단계부터 번호를 붙일 수 있습니다.

코드를 만든 단계가 끝나면 보고의 핵심 함수를 읽고 확인 질문에 답합니다.
질문은 실제 입력 하나가 거치는 처리와 결과를 예측하게 합니다.
모르면 `모름`이라고 답해도 됩니다. 답 없이 다음 지시를 보내면 한 번 되묻습니다.
그다음 지시에도 답이 없으면 `답 없음`으로 적고 진행합니다.

웹 서버는 사용자가 직접 켭니다. 알려 준 명령을 별도 터미널에서 실행합니다.
서버 코드를 고친 뒤에는 다시 켭니다.

### 4. `$verify`: 결과를 따로 계산해 비교하기

핵심 결과가 갖춰진 중간 점검에서 한 번 부릅니다. 그 뒤 코드나 데이터가 바뀌었으면 제출 전에 다시 부릅니다.
기본판(입력에서 결과까지 처음 한 번 도는 것)이 나왔을 때는 보통 사용자가 핵심 함수 하나를 직접 읽는 것으로 충분합니다. 중요한 전제가 의심되면 그때 불러도 됩니다.
새 에이전트가 데이터를 처음부터 다시 읽어 토큰이 많이 드는 단계라, 부르기 전에 사용자가 `/status`로 남은 컨텍스트와 사용량을 봅니다.

```text
$verify 해 줘.
```

숫자를 미리 알 필요는 없습니다. 스킬이 결과에서 사람이 바로 쓰는 숫자를 세 개 이상 고릅니다.
꼭 볼 것이 있으면 값 없이 이름만 덧붙입니다.

```text
$verify 해 줘. 특히 볼 것: <결정에 쓰이는 항목>.
```

웹이면 먼저 현재 서버의 응답과 판정 함수를 직접 부른 결과를 비교합니다.
요청은 `verify/curl_check.sh`에 모읍니다.
저장·승인처럼 상태를 바꾸는 요청은 사용자가 알려 준 **사본 서버**에서만 검사합니다.
사본 주소가 없으면 그 요청은 미실행으로 남깁니다.

독립 계산은 지금까지의 대화를 넘기지 않은 새 에이전트에게 맡깁니다(`spawn_agent`, `fork_turns: "none"`).
이 에이전트는 README, 요구 사본 `verify/spec_N.md`, 원본 데이터만 읽습니다.
새 에이전트는 구현 코드와 구현 결과를 보지 않고 계산합니다. Codex가 그 값과 레코드별 판정을 구현과 비교합니다.
핵심 결과에 영향을 주는 가정은 다른 안으로도 계산합니다.

요구와 확인 항목이 같으면 기존 검증 스크립트를 같은 번호로 다시 실행합니다.
새 에이전트를 쓸 수 없으면 구현 코드를 가져다 쓰지 않는 별도 스크립트로 직접 계산합니다.
모두 같으면 담당자에게 보낼 결과 확인 초안(핵심 숫자·대표 사례·남은 제한)을 줍니다. 받은 답은 `$relay`로 넣습니다.
차이가 나도 자동으로 고치지 않습니다. Codex가 차이와 원인 후보를 설명하고, 사용자가 고치라고 하면 고친 뒤 다시 검증합니다. "원인을 확인해 말해 줘. 합의한 기준과 어긋난 구현 실수면 고치고, 검증 쪽 실수거나 기준이나 가정을 새로 정해야 하는 차이면 고치지 말고 물어 줘."처럼 한 번에 맡겨도 됩니다.
검증이 끝나면 답하지 않은 확인 질문이 있으면 먼저 답하고 `/new`로 대화를 비웁니다. 대화가 길어지면 이후 요청마다 그 대화를 통째로 다시 보내 토큰이 크게 늘기 때문입니다. 새 대화는 앞 대화를 보지 못합니다. 그 뒤 담당자 답은 `$relay <담당자 답>`으로 넣으면 Codex가 확인표의 '질문' 행이나 검증 보고서에서 질문을 찾아 기록하고, 실제로 보낸 질문을 `$relay 보낸 질문: … 답: …`처럼 함께 붙이면 더 정확합니다.

### 5. `$wrapup`: 요구와 구현을 맞춰 보고 문서 정리하기

기능 추가를 마칠 때 답하지 않은 확인 질문이 있으면 답한 뒤 `/new`로 새 대화를 열고 `$wrapup 해 줘`라고 보냅니다.
요구를 하나씩 대조하고, 별도 에이전트가 하네스 설치 직전 커밋(`.harness/BASE`) 뒤의 모든 변경과 화면을 검토합니다.
**이 검토자는 구현 코드를 읽습니다.** 요구의 근거는 README와 요구 사본에서 찾습니다.
새 에이전트를 쓸 수 없으면 같은 자료로 직접 검토합니다.

제출 문서를 쓰고 계획 문서의 지난 상태 문장을 정리한 뒤 키·개인정보 모양 등을 점검합니다.
제출 문서 이름이 정해져 있지 않으면 `HANDOFF.md`를 씁니다.
고칠 후보는 마지막에 한 번에 묻고, 사용자가 고르기 전에는 코드를 고치지 않습니다.
수정 뒤에는 관련 검증과 문서를 갱신합니다. 기준이나 가정이 바뀌면 `$verify`를 다시 부릅니다.

### 6. `$weakness`: 직접 설명하고 남은 한계 확인하기

`$wrapup`을 마친 뒤 `$weakness 해 줘`라고 보내면, 먼저 사용자가 자기 말로 정리할 내용을 묻고 기다립니다.
부딪친 조건, 틀리는 입력, 맡긴 일과 직접 확인한 일, 실제 입력 하나가 지나가는 길을 적습니다.
시간이 없으면 틀리는 입력과 입력의 경로만 적습니다.

답을 받은 뒤 코드·기록과 다른 곳을 짚고, 남은 약점과 설명 노트를 정리합니다.
`EXPLAIN.md`에 사용자 문장과 한 화면 요약을 남깁니다.
제출 문서의 빠진 한계는 추가해 커밋하지만 `EXPLAIN.md`는 커밋하지 않습니다.
시간이 남으면 점검 질문을 하나씩 주고받습니다.

## 구성 파일

### 설치되는 파일

| 저장소 원본 | 과제 폴더의 위치 | 역할 |
|---|---|---|
| `AGENTS.md` | `AGENTS.md` | 작업 중 따를 공통 규칙 |
| `.agents/skills/` | `.agents/skills/` | 스킬 다섯 개의 `SKILL.md`와 `agents/openai.yaml` |
| `tools/` | `.harness/tools/` | Python 점검 도구, 자체 테스트, 예제 데이터 |
| `vendor/` | `.harness/vendor/` | Chart.js 4.5.1과 MIT 라이선스. CDN 없이 차트를 그릴 때 사용 |
| `playbook/LIBS.md` | `.harness/LIBS.md` | 문제 유형별 도구 선택과 주의할 점 |
| `playbook/cheatsheet.md` | `.harness/cheatsheet.md` | 작업 순서와 막힐 때 참고할 명령 |
| `codex/config.toml` | `.codex/config.toml` | 추론 강도: 평소 `medium`, 계획 모드 `high` |
| `codex/rules/chocochip-codex-harness.rules` | `.codex/rules/chocochip-codex-harness.rules` | 명령의 앞부분이 같으면 실행을 막는 규칙 |
| `hooks/commit-msg` | Git의 `hooks/commit-msg` | Codex가 만든 커밋 메시지 검사 |
| 설치기가 만듦 | `.harness/SOURCE.txt` | 가져온 저장소 주소와 커밋 |
| 설치기가 만듦 | `.harness/BASE` | 첫 설치 직전 커밋. Git 저장소 맨 위에서 설치할 때 기록 |
| 설치기가 만듦 | `.harness/INSTALLED_SKILLS` | 설치한 스킬 폴더 이름 |
| 설치기가 덧붙임 | Git의 `info/exclude` | 키 파일, Python 캐시, `EXPLAIN.md`를 Git 추적 대상에서 제외 |

훅과 제외 설정은 Git 폴더(보통 `.git/`) 안에 들어가 커밋되지 않습니다. 이미 추적 중인 파일에는 제외 설정이 적용되지 않습니다.
제외하는 이름은 `.env`, `.env.*`, `.ai_env`, `__pycache__/`, `*.pyc`, `EXPLAIN.md`입니다.
설치 중에는 `.harness/INSTALLING` 표시를 두고 파일 설치가 끝나면 지웁니다.

차트 파일은 `.harness/vendor/chart.umd.min.js`입니다. 웹에서 쓸 때는 서비스의 정적 파일 폴더로 복사합니다.

금지 규칙에 적힌 명령 앞부분은 `git push`, `git remote add`, `git remote set-url`, `gh`, `git commit --no-verify`, `git commit -n`입니다.
허용 규칙은 추가하지 않으며, 다른 명령의 승인 여부는 Codex 설정을 따릅니다.
이 파일은 명령 앞부분을 비교하는 규칙이므로 모든 외부 전송을 차단하는 장치는 아닙니다.

작업 규칙의 커밋 형식은 `타입(범위): 한국어 요약`입니다.
훅은 `CODEX_THREAD_ID`나 `CODEX_TOOL_CALL_ID`가 있을 때만 검사합니다.
실제 훅은 범위 생략도 허용하며, 병합·되돌리기·fixup 같은 일부 메시지는 검사에서 뺍니다.

### 작업 중 생기는 문서

과제 README에서 정한 이름이 있으면 그것을 우선합니다.
아래 문서는 설치기가 미리 만들지 않습니다.

| 기본 위치 | 담는 내용 |
|---|---|
| `PLAN.md` | 만들 것, 기준, 개발 시작 메모, 단계, 결정 기록 |
| `COLLAB.md` | 요구 확인표, 실제로 보낸 질문과 담당자 답, 합의 |
| `EXPLAIN.md` | 단계별 약한 곳·파급·확인한 숫자, 내 말로 정리, 한 화면 요약. 커밋 제외 |
| `HANDOFF.md` | 실행 방법, 구조, 판단 근거, 검증 결과, 남은 한계 |
| `verify/spec_N.md` | 개발 시작 메모·합의 뒤 변경·담당자 확인 기록의 사본 |
| `verify/checker_N/check.py` | 원본 데이터를 따로 읽어 계산하는 검증 코드 |
| `verify/report_N.md`, `verify/diff_N.csv` | 구현과 검증의 비교 결과, 다른 레코드 목록 |
| `verify/curl_check.sh` | 웹 화면과 요청을 확인하는 명령 |

`N`은 검증 번호입니다. 지난 검증기를 다시 쓰면 같은 번호를 씁니다. 요구 사본은 처음 만들거나 내용이 바뀔 때 커밋합니다.
`curl_check.sh`, 검증 코드와 보고서, 차이가 있는 비교 파일(다시 검증하며 고쳐 쓴 것 포함)은 커밋합니다.
검증기의 `rows.csv`, 서버 응답, 결과 사본과 로그는 커밋하지 않습니다.
행 대조용 목록은 `/tmp`에 따로 둡니다.

### 점검 도구

설치 뒤 과제 폴더 맨 위에서 `python3 .harness/tools/<도구 이름>`으로 실행합니다.
Python 도구는 표준 라이브러리만 씁니다. 셸 도구는 `bash`로 실행합니다.

| 도구 | 확인하는 것 |
|---|---|
| `env_check.py` | Python·pip·PyPI 접속, 설치된 패키지, 포트, Git, 샌드박스 여부 |
| `profile_data.py` | 행 수, 결측, 값 종류, 숫자·날짜의 이상한 값, 표기 차이, 중복 |
| `join_check.py` | 두 표의 키 중복, 짝 없는 키, 빈 키, 합친 뒤 행 수 |
| `reconcile.py` | 입력 행이 쓴 행·뺀 행·따로 둔 행으로 빠짐없이 나뉘었는지 |
| `precheck.py` | 키·개인정보 모양, TODO·FIXME, 문서의 `/tmp` 인용, 남은 검증 차이, 열지 못한 파일 |
| `selftest.sh` | 임시 폴더에서 점검 도구 자체 검사 |

`env_check.py`는 인수 없이 실행합니다. 별도 도움말 처리가 없어 `--help`를 붙여도 환경 점검을 실행합니다.
네트워크와 포트 결과는 실행한 프로세스의 권한에 따라 달라집니다.
나머지 Python 도구는 `--help`로 사용법과 옵션을 봅니다.

도구마다 지원 범위가 다릅니다.

- **`profile_data.py`**: CSV·TSV·JSON·JSONL·NDJSON·SQLite를 읽습니다. 복합 키는 `--key 열1+열2`로 지정합니다. `--all`은 보여 줄 예시 개수의 제한을 풉니다.
- **`join_check.py`**: CSV·TSV·JSON·JSONL·NDJSON을 읽습니다. `--left 파일:열 --right 파일:열`로 비교합니다. 빈 키끼리는 연결하지 않습니다. 복합 키는 열 하나만 비어도 연결하지 않습니다. `left` 결과 행 수에는 짝 없는 왼쪽 행이 남습니다.
- **`reconcile.py`**: CSV·TSV·JSON·JSONL·NDJSON과 ID를 한 줄씩 적은 TXT를 읽습니다. 같은 ID가 여러 번 나오면 횟수까지 대조합니다. JSON 객체 안에 행 목록 후보가 여럿이면 하나를 임의로 고르지 않고 멈춥니다.
- **`precheck.py`**: Git이 추적하는 파일과 새 파일을 검사합니다. Git 저장소가 아니면 폴더 전체를 검사합니다. 입력 자료는 `--exclude`로 뺄 수 있습니다. Git에서 제외된 파일도 볼 때는 `--include-ignored`를 씁니다. `.harness/`·`.agents/`와 이진 파일은 검사에서 뺍니다.

`precheck.py`는 찾은 키·개인정보 모양의 값을 가려서 출력합니다.
데이터 파일의 개인정보 모양은 기본으로 파일별 줄 수만 보여 줍니다. `--show-data`를 붙이면 가린 줄도 봅니다.

`profile_data.py`의 SQLite 열 점검은 표마다 앞 50만 행까지만 봅니다. 전체 행 수는 따로 셉니다.
열별 값 종류가 상한을 넘으면 값 목록·표기 차이·중복 점검을 생략합니다.
상한은 일반 열 20만 개, 첫 열과 ID처럼 보이는 이름의 열 200만 개입니다.
`--all`을 붙여도 이 점검 범위는 늘어나지 않습니다.
JSON에 목록이 여러 개이면 고른 목록과 건너뛴 목록도 확인해야 합니다.

`join_check.py`와 `reconcile.py`는 `--show 0`으로 예시를 모두 볼 수 있습니다.
입력 한 행이 결과 여러 행이 되는 작업은 `reconcile.py --help`의 ID 목록 방식을 따릅니다.
그 방식은 결과에 입력 ID가 있는지만 확인하며, 각 결과 행의 판정까지 검증하지는 않습니다.

종료 코드의 뜻은 도구마다 다릅니다.

| 도구 | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| `env_check.py` | 늘 0 | — | — | — |
| `profile_data.py` | 점검함 | 읽을 파일 없음 | 사용법 오류 | — |
| `join_check.py` | 점검함 | — | 한쪽 행이 0개(빈 목록 포함) | 사용법·파일·실행 오류 |
| `reconcile.py` | 일치 | 불일치 | 검사 0건 | 사용법·파일·실행 오류 |
| `precheck.py` | 찾은 것 없음 | 찾은 것 있음 | — | 사용법·실행 오류 |

`env_check.py`는 접속 불가나 없는 패키지를 알려도 0으로 끝납니다.
`profile_data.py`도 파일별 읽기 오류를 출력한 뒤 0으로 끝날 수 있습니다.
종료 코드와 함께 출력의 생략·오류 안내를 읽습니다.

## 작업 원칙

- 과제 README와 담당자 답을 우선합니다. 과제에 있던 `AGENTS.md`와 하네스 규칙이 다르면 과제 규칙을 따릅니다.
- 답에 따라 결과의 숫자·ID·순서·권고가 바뀌면 담당자에게 보낼 질문 초안을 씁니다. 판정은 같지만 빈 값·따로 둔 행을 어디에 어떻게 보여 줄지 같은 선택은, 달라지는 행을 건수·ID로 짚어 사용자에게 묻습니다. 파일 나누기나 이름 짓기는 Codex가 정하고 보고합니다.
- 계획의 한 단계씩 작업합니다. 끝낼 확인 방법을 먼저 정하고, 끝나면 명령·종료 코드·건수를 보고합니다. 결정과 이유는 계획 문서의 결정 기록에 적고 커밋합니다. 약한 곳과 확인한 숫자는 설명 노트에 남깁니다.
- 판정·계산은 화면과 분리하고 실제 레코드로 테스트합니다. 입력 행을 나눠 결과를 만들면 행 대조도 합니다. 처리하지 못한 행은 사유와 함께 따로 두고, 그 행이 빠진 집계에는 이를 표시합니다.
- 합의한 범위 안에서 만듭니다. 새 패키지는 `.harness/LIBS.md`를 보고 묻습니다. 웹 서버는 `0.0.0.0`에서 열고 화면의 링크와 요청은 상대 경로를 씁니다.
- 키를 커밋하거나 개인정보를 화면·로그에 그대로 내지 않습니다. 작업 규칙은 코드·데이터·기록의 외부 전송을 금지합니다. 외부에서 받아오는 설치와 과제 README가 정한 호출은 허용합니다.
