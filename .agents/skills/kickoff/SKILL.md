# kickoff: 과제 시작 점검 (질문 세션)

이 글이 스킬 전문이다. 이 SKILL.md를 다시 열어 읽지 않는다.
구현과 패키지 설치는 하지 않는다. 행 대조와 데이터 사본 파일도 만들지 않는다. AGENTS.md는 Codex가 이미 실어 두었으니 다시 열지 않고 끝까지 따른다(작업 폴더에 AGENTS.override.md가 있을 때만 AGENTS.md를 직접 읽는다).
사용자가 '내가 읽은 목표'를 적었으면 README와 비교해 다른 점을 4번 '과제 한눈에'에서 짚는다.

## 1. 읽기
작업 폴더 맨 위에서 실행한다(`.harness`는 이 스킬 폴더가 아니라 작업 폴더 맨 위에 있다).
- `python3 .harness/tools/env_check.py`
- README(과제 안내)를 끝까지 읽는다.
- 데이터가 있으면 `python3 .harness/tools/profile_data.py <데이터 폴더>`. 여러 열을 합친 키가 보이면 `--key 열1+열2`로 다시 보고, 표를 합쳐야 하면 `python3 .harness/tools/join_check.py --left 파일:열 --right 파일:열`로 합친 뒤 행 수가 어떻게 바뀌는지 본다.
- 도구가 못 읽는 형식은 같은 항목(행 수, 결측, 값 종류, 형식 섞임, 중복)을 직접 센다. 파일 전체를 출력하지 않는다.
- 과제에 기존 코드가 있으면 기존 테스트를 돌리고(돌릴 수 없으면 그렇다고 적는다), 고칠 오류를 재현하고, 바꾸면 안 되는 동작을 확인표에 적는다. 회귀 테스트는 `.harness/LIBS.md`의 '회귀 테스트' 줄을 따른다.

## 2. 계획 문서에 쓰기
아래 6·8번은 협업 기록(README가 정한 파일, 없으면 COLLAB.md)에, 나머지는 계획 문서(README가 정한 이름, 없으면 PLAN.md)에 쓴다. 파일이 없으면 만든다. README가 계획 문서에 넣을 절(문제 정의, 성공 기준 등)을 정했으면 그 절 이름을 제목으로 쓰고 아래 내용을 알맞은 절에 넣는다. 맨 아래 '결정 기록' 절은 제목만 만들어 둔다. '현재 단계', '미실행' 같은 진행 상태는 본문에 쓰지 않는다.
1. **만들 것과 제출물**: README 문장을 그대로 인용한다. 제출 파일 이름은 README에 적힌 그대로 쓴다.
2. **성공 기준**: 확인할 수 있는 숫자나 장면으로 쓴다(예: 누가 언제 무엇을 확인할 수 있다). 담당자 확인이 필요하면 확인표에 '질문'으로 둔다.
3. **환경**: env_check 결과 중 구현 선택을 바꾸는 것(파이썬 버전, pip, 이미 있는 패키지, 쓸 수 있는 포트).
4. **데이터 사실**: 파일별 행 수, 기간, 키.
5. **데이터에서 이상한 점**: 찾은 것 전부, 결과를 바꿀 수 있는 것부터. 항목마다 실제 예시 한 건(파일, 행 번호 또는 ID, 값)을 붙인다. 서로 맞아야 하는 열끼리 어긋난 행도 넣는다.
6. **요구 확인표**: 한 행에 한 가지. 무엇을 만드나, 누가 언제 쓰나, 대상, 기간, 기간·집계의 경계(끝 날짜를 넣는지, 날짜만 보는지 시각까지 보는지, 어느 팀·사람에 속하는지의 기준), 단위(결과 한 행이 무엇인가), 포함·제외 기준, 판정 기준(등급·단계로 나누면 단계를 가르는 기준), 결과 모양, 5번에서 처리 방침이 필요한 것. 그리고 데이터만 봐서는 알 수 없는 것: 데이터가 어떻게 기록되는지와 그 기간에 바뀐 것·알려진 오류(장비·시스템·측정 방식·담당 변경 등), 결과를 받는 사람이 여는 양식과 밖에 내면 안 되는 값, 결과로 조치를 정하는 과제면 그 조치의 비용·제약과 조치 전에 이미 지나갔거나 진행 중인 대상(지난 처리분·진행 중인 물량 등)을 어떻게 다루는지, 다음에 기간·대상을 바꿔 다시 쓰는지.
   | 항목 | 지금 아는 것 | 상태 | 이 답이 바꾸는 것 |
   - 상태는 넷 중 하나: 확정(README 문장 인용) / 가정(내 제안과 이유) / 질문 / 정의 확인(같은 말이 두 뜻일 수 있음)
   - README나 데이터로 알 수 있는 것은 질문으로 만들지 않는다. 데이터만 봐서는 알 수 없는 항목은 README에 없으면 '질문'으로 둔다.
   - 없는 지표를 다른 지표로 몰래 바꾸지 않는다. 바꿔야 하면 후보를 적고 '질문'으로 둔다.
7. **시간 기준점**: 사용자가 남은 시간을 말했으면 기본판·기능 동결·제출 시작 시각을 적는다. 기본판(입력에서 결과 파일·화면까지 한 번 도는 것)은 범위 합의 뒤 30분 안으로 잡고, 못 지키면 화면·보조 출력을 뒤로 미룬다. 기능 동결은 남은 시간의 4분의 1 전, 제출 시작은 마감 10분 전.
8. **담당자 확인 기록**: 협업 기록에 이 절의 제목만 만들어 둔다.

## 3. 담당자에게 보낼 첫 메시지 초안
- 확인표의 '질문'·'정의 확인' 가운데 답에 따라 결과의 숫자·ID나 권고가 바뀌는 것부터 고른다. 첫 메시지는 세 개 안팎으로, 데이터 질문에 장면 질문 하나를 더한다. 사용자가 담당자는 한 번에 하나만 답한다고 하면 하나만 고른다(어느 것인지는 사용자가 고른다). 넣지 못한 것은 확인표에 '다음에 물을 것'으로 표시한다.
- 데이터 질문: 질문 하나에 결정 하나만 묻는다. 실제 데이터 한 건을 짚고 내 처리안과 다른 선택지 하나를 붙여, 담당자가 "네"나 "두 번째요"만 해도 정해지게 쓴다.
  - 모양: "<언제> <대상>(ID)은 <무엇이 어떻게> 되어 있습니다. 이런 건이 n건입니다. <처리안>으로 하려고 합니다. 아니면 <다른 선택지>로 할까요?" 건수는 이 한 번뿐이고, 비교·비율 같은 분석 숫자는 담당자 메시지에 넣지 않는다(사용자용 후보 목록에만).
  - 데이터는 담당자가 알아보는 말(대상 이름, 시각 등)로 짚고 ID는 괄호에 넣는다.
  - 예로 든 건이 그 상황에 실제로 해당하는지(다른 기준에 걸려 빠지지 않는지) 확인한 것만 쓴다.
- 장면 질문: README의 사용 장면을 인용해(없으면 결과를 쓸 사람과 때를 묻는다) 묻는다. 처리안은 붙이지 않고, 묻는 것은 셋까지다.
  - 결과로 조치나 결정을 고르는 과제면 모양: "<README 장면 인용>에서 이 결과를 보고 무엇을 정하시나요? 고를 수 있는 선택지(이미 지나갔거나 진행 중인 대상을 어떻게 할지도)와 각각 드는 비용·시간, 지금 짐작하고 계신 것이 있으면 함께 알려 주세요."
  - 그렇지 않으면 모양: "<README 장면 인용>에서 이 결과를 보고 나서 누가 무엇을 하나요? 그때 지켜야 할 것(단위·양식·내면 안 되는 값)이 있으면 알려 주세요."
- 업무 말로 쓴다. README·담당자 답에 없는 해법 단어(API, DB, 대시보드 등)와 "할 일을 알려 주세요", "요구사항을 전부 정리해 주세요", "이 설계 괜찮을까요?"는 쓰지 않는다.
- 복사하기 쉽게 코드 블록 하나로 준다.
- 무엇을 물을지는 사용자가 고른다. 초안 아래에 넣지 않은 질문 후보를 번호와 영향 건수로 보이고, 빼거나 바꾸거나 더할 질문을 고르게 한다. 사용자가 고르면 초안을 고쳐 다시 준다. 사용자가 뺀 질문은 지우지 않고 '가정'(내 처리안)으로 바꿔 두고, 범위 합의 메시지의 기본값 목록으로 담당자에게 간다고 알린다. 장면 질문은 빼도 가정으로 바꾸지 않고 '다음에 물을 것'으로 둔다.

## 4. 사용자에게 보일 것 (대화에만, 메시지 초안 위에)
사용자는 과제를 처음 읽어 아직 감이 없다. 3분 안에 이해하고 담당자 앞에서 설명할 수 있게, 아래를 짧게 먼저 보인다.
- **과제 한눈에**: 무엇을 만드나, 누가 언제 무엇을 결정하는 데 쓰나, 입력 파일, 결과 화면 한 줄 모양. 다섯 줄 이내.
- **판정 규칙 요약**: README 기준을 번호 목록으로 줄여 쓴다. 규칙마다 조건에 필요한 열·대상·기간이 데이터에 있는지를 붙이고, 건수는 데이터 점검으로 셀 수 있는 것만 붙인다.
- **애매한 곳**: 결과를 크게 바꾸는 순서로 세 개 안팎. 각각 "어느 쪽으로 정하느냐에 따라 무엇이 몇 건 바뀌나"를 한 줄로.
- **질문마다 왜 묻는지**: 메시지 초안의 질문 번호마다 한 줄. 담당자가 되물으면 사용자가 이 줄로 답한다.
