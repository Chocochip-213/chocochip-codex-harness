# kickoff: 과제 시작 점검 (질문 세션)

구현과 패키지 설치는 하지 않는다. 행 대조와 데이터 사본 파일도 만들지 않는다. 작업 폴더 맨 위의 AGENTS.md를 이 세션에서 아직 읽지 않았다면 먼저 읽고 끝까지 따른다.
사용자가 '내가 읽은 목표'를 적었으면 README와 비교해 다른 점을 4번 '과제 한눈에'에서 짚는다.

## 1. 읽기
작업 폴더 맨 위에서 실행한다(`.harness`는 이 스킬 폴더가 아니라 작업 폴더 맨 위에 있다).
- `python3 .harness/tools/env_check.py`
- README(과제 안내)를 끝까지 읽는다.
- 데이터가 있으면 `python3 .harness/tools/profile_data.py <데이터 폴더>`. 여러 열을 합친 키가 보이면 `--key 열1+열2`로 다시 보고, 표를 합쳐야 하면 `python3 .harness/tools/join_check.py --left 파일:열 --right 파일:열`로 합친 뒤 행 수가 어떻게 바뀌는지 본다.
- 도구가 못 읽는 형식은 같은 항목(행 수, 결측, 값 종류, 형식 섞임, 중복)을 직접 센다. 파일 전체를 출력하지 않는다.

## 2. 계획 문서에 쓰기
계획 문서(README가 정한 이름, 없으면 PLAN.md)를 만들거나 열어 아래 내용을 쓴다. README가 계획 문서에 넣을 절(문제 정의, 성공 기준 등)을 정했으면 그 절 이름을 제목으로 쓰고 아래 내용을 알맞은 절에 넣는다. 맨 아래 '결정 기록' 절은 제목만 만들어 둔다. '현재 단계', '미실행' 같은 진행 상태는 본문에 쓰지 않는다.
1. **만들 것과 제출물**: README 문장을 그대로 인용한다. 제출 파일 이름은 README에 적힌 그대로 쓴다.
2. **성공 기준**: 확인할 수 있는 숫자나 장면으로 쓴다(예: 누가 언제 무엇을 확인할 수 있다). 담당자 확인이 필요하면 확인표에 '질문'으로 둔다.
3. **환경**: env_check 결과 중 구현 선택을 바꾸는 것(파이썬 버전, pip, 이미 있는 패키지, 쓸 수 있는 포트).
4. **데이터 사실**: 파일별 행 수, 기간, 키.
5. **데이터에서 이상한 점**: 찾은 것 전부, 결과를 바꿀 수 있는 것부터. 항목마다 실제 예시 한 건(파일, 행 번호 또는 ID, 값)을 붙인다. 서로 맞아야 하는 열끼리 어긋난 행도 넣는다.
6. **요구 확인표**: 한 행에 한 가지. 무엇을 만드나, 누가 언제 쓰나, 대상, 기간, 단위(결과 한 행이 무엇인가), 포함·제외 기준, 판정 기준, 결과 모양, 5번에서 처리 방침이 필요한 것.
   | 항목 | 지금 아는 것 | 상태 | 이 답이 바꾸는 것 |
   - 상태는 넷 중 하나: 확정(README 문장 인용) / 가정(내 제안과 이유) / 질문 / 정의 확인(같은 말이 두 뜻일 수 있음)
   - README나 데이터로 알 수 있는 것은 질문으로 만들지 않는다.
   - 없는 지표를 다른 지표로 몰래 바꾸지 않는다. 바꿔야 하면 후보를 적고 '질문'으로 둔다.
7. **시간 기준점**: 사용자가 남은 시간을 말했으면 기본판·기능 동결·제출 시작 시각을 적는다.
8. **담당자 확인 기록**: README가 다른 파일을 정했으면 그 파일을, 아니면 이 절의 제목만 만들어 둔다.

## 3. 담당자에게 보낼 첫 메시지 초안
- 확인표의 '질문'·'정의 확인' 가운데 결과를 크게 바꾸는 것부터 세 개 안팎을 고른다. 사용자가 담당자는 한 번에 하나만 답한다고 하면 하나만 고른다. 크기는 답에 따라 바뀌는 건수나 핵심 결과로 잰다. 넣지 못한 것은 확인표에 '다음에 물을 것'으로 표시한다.
- 질문 하나에 결정 하나만 묻는다. 질문마다 실제 장면이나 데이터 한 건을 짚고, 내 처리안과 다른 선택지 하나를 붙인다. 담당자가 "네"나 "두 번째요"만 해도 정해지게 쓴다.
  - 모양: "<언제> <대상>(ID)은 <무엇이 어떻게> 되어 있습니다. 이런 건이 n건입니다. <처리안>으로 하려고 합니다. 아니면 <다른 선택지>로 할까요?"
  - 데이터는 담당자가 알아보는 말(대상 이름, 시각 등)로 짚고 ID는 괄호에 넣는다.
  - 예로 든 건이 그 상황에 실제로 해당하는지(다른 기준에 걸려 빠지지 않는지) 확인한 것만 쓴다.
- README에 결과를 쓰는 장면이나 그때 지킬 조건이 없으면 그것을 묻는 질문을 하나 넣는다.
- 업무 말로 쓴다. API, DB, 대시보드 같은 해법 단어와 "할 일을 알려 주세요", "요구사항을 전부 정리해 주세요", "이 설계 괜찮을까요?"는 쓰지 않는다.
- 복사하기 쉽게 코드 블록 하나로 준다.
- 무엇을 물을지는 사용자가 고른다. 초안 아래에 넣지 않은 질문 후보를 번호와 영향 건수로 보이고, 빼거나 바꾸거나 더할 질문을 고르게 한다. 사용자가 고르면 초안을 고쳐 다시 준다.

## 4. 사용자에게 보일 것 (대화에만, 메시지 초안 위에)
사용자는 과제를 처음 읽어 아직 감이 없다. 3분 안에 이해하고 담당자 앞에서 설명할 수 있게, 아래를 짧게 먼저 보인다.
- **과제 한눈에**: 무엇을 만드나, 누가 언제 무엇을 결정하는 데 쓰나, 입력 파일, 결과 화면 한 줄 모양. 다섯 줄 이내.
- **판정 규칙 요약**: README 기준을 번호 목록으로 줄여 쓴다. 규칙마다 데이터에서 해당하는 건수를 붙인다.
- **애매한 곳**: 결과를 크게 바꾸는 순서로 세 개 안팎. 각각 "어느 쪽으로 정하느냐에 따라 무엇이 몇 건 바뀌나"를 한 줄로.
- **질문마다 왜 묻는지**: 메시지 초안의 질문 번호마다 한 줄. 담당자가 되물으면 사용자가 이 줄로 답한다.

같은 내용을 `EXPLAIN.md`(사용자용 설명 노트, 커밋하지 않음) 맨 위 '과제 한눈에' 절로도 쓴다. 나중에 결정을 설명할 때 다시 본다.
