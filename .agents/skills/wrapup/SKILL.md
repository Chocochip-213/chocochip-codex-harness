# wrapup: 마감

이 글이 스킬 전문이다. 전문이 현재 문맥에 있으면 이 SKILL.md를 다시 열지 않고, 없거나 불확실하면(자동 압축 뒤 등) 다시 읽는다.
지금부터 기능을 더하지 않는다. 사용자가 6번에서 고르기 전에는 코드를 고치지 않는다. 1~5번은 묻지 않고 이어서 하고, 고칠 후보는 6번에서 세 묶음 이내로 묶어 한 번에 묻는다. 점검 출력은 대화에만 보이고 파일로 남기지 않는다. 앞선 wrapup 뒤에 다시 부르면 1번 표는 다시 만들고, 그 뒤 바뀐 것이 영향을 주지 않는 확인은 제출 문서의 검증 결과와 verify/report_N.md에 남은 것(명령·시각)만 인용한다.

## 1. 요건 대조
| 요건(README 문장·담당자 답 인용) | 충족/부분/미충족 | 근거(파일·함수, 실행한 명령과 결과 또는 verify/report_N.md) |
- 요건은 빠짐없이 한 줄씩 뽑는다: README의 과제·화면·제출물·꼭 지킬 것 문장, 협업 기록에서 담당자가 확정한 답, 개발 시작 메모의 성공 기준과 만들지 않을 것(만들지 않았는지 확인). README가 정한 제출 파일과 실행·빌드에 필요한 프로젝트 파일(의존성·설정·정적 파일 등)마다 `git ls-files --error-unmatch <파일>`로 추적되는지 보고, 추적되지 않으면 `git check-ignore -v <파일>`로 무시 규칙에 걸렸는지 보아, 걸렸으면 `git add -f`, 아니면 `git add`를 6번 고칠 후보에 넣는다(키·비밀값이 든 파일은 넣지 않고 5번에 적는다). 표 위에 '요건 n개: 충족 a, 부분 b, 미충족 c'를 적는다.
- '충족'은 실행해 확인한 것만 쓴다: 이 턴에 실행한 curl_check·테스트 출력, 그리고 가장 최근 확인(verify 보고·단계 확인) 뒤 그 요건에 걸린 코드·입력·설정·합의·실행 상태가 그대로면(`git diff --stat <그 확인의 커밋>`에 해당 파일이 없고 '합의 뒤 변경'이 늘지 않았을 때) 그 결과를 '이전 확인 재사용(명령·시각)'으로 근거에 쓴다(요건마다 명령을 따로 만들지 않는다). 테스트 통과가 아니라 요건 문장과 실제 동작을 맞춰 본다. 요건이 정한 대상·환경·사용 경로(예: 화면에서 적용)와 근거가 실제로 같은 범위만 충족이다(다른 경로로 확인한 것은 부분. 상태를 바꾸는 확인을 사본에서 했으면 코드·설정·사용 경로가 같을 때만 충족). 필수 요건의 부분·미충족·미확인은 남은 한계에 적더라도 6번 고칠 후보에서 빼지 않는다.
- 단위 테스트 전체는 이 턴에 한 번 돌려(지원하면 `-q`) 명령·종료 코드·건수를 표 위에 적는다(단계마다는 바뀐 곳만 돌렸으므로 여기서 한 번 모아 확인한다).

## 2. 새 에이전트의 검토
- 기준 커밋: `.harness/BASE`에 적힌 해시(하네스 설치 직전 커밋). 파일이 없거나 비어 있으면(둘 다 없으면 첫 커밋) 가장 오래된 하네스 커밋 `git log --format=%h --grep='chore(harness): 작업 도구 추가' | tail -n 1`.
- 사용자에게 보이는 화면: 웹이면 먼저 서버가 지금 코드로 도는지 보고(꺼져 있거나 옛 코드면 AGENTS.md대로 다시 띄운다) 마지막 `bash verify/curl_check.sh`가 실패·미실행 없이 끝났고 그 뒤 관련 코드·입력·설정·저장 상태가 같음을 확인할 수 있으면(`git diff --stat <그 커밋>`과 Git 밖 설정·저장 상태의 읽기 확인. 사용자가 화면에서 바꾼 것 포함) 그 결과를 '이전 확인 재사용(명령·시각)'으로 쓰고, 아니면 다시 실행해 화면 파일을 새로 받는다. 작업 서버 첫 화면의 저장 결과가 채택한 기준과 다른 조건으로 만든 것이면, 업무 적용 없이 결과만 다시 만드는 기존 동작이 있을 때 사용자가 Browser에서 채택한 조건으로 다시 만들고 본 결과를 알려 줄 일을 6번 목록에 넣는다(Codex는 작업 서버 상태를 바꾸지 않는다). 사용자가 해 보기 전까지 제출 문서에는 지금 저장 결과의 조건과 채택한 기준의 차이를 적는다. 화면 모양은 screen 스킬 4절의 제출 전 점검(다른 역할의 첫 화면·바뀐 화면을 실제 폭으로 `ui_check.py`)을 이 턴에 한 번 하고 그 결과(본 장면·남은 문제)를 ③과 함께 쓴다. 결정 기록 '화면 점검' 줄에 적힌 원인이 그대로이거나 screen 4절의 방법으로 보지 못한 화면은 사용자가 볼 목록을 6번에 주고 모양은 '미확인'으로 둔다.
- 요구 사본: 가장 최근 verify/spec_N.md를 쓴다. 그 뒤 '합의 뒤 변경'이 생겼거나 사본이 없으면 개발 시작 메모와 담당자 확인 기록을 verify/spec_N.md(새 번호)로 옮긴다. 결정 기록은 옮기지 않는다.
- 시간 기준점의 제출 시작까지 30분이 안 남았으면 새 에이전트를 띄우지 않고 같은 자료로 ②만 직접 보고 ①·③은 '미실행'으로 적고, 아래 두 줄(새 에이전트 띄우기·기다리기)은 건너뛴다.
- `spawn_agent`로 새 에이전트를 띄운다. `task_name`은 `reviewer_N`, `fork_turns`는 `"none"`. 메시지:
  "너는 요건 검토를 맡은 하위 에이전트다. AGENTS.md의 결정 기록·커밋·행 대조 규칙은 이 일에 적용하지 않는다: 파일을 만들거나 고치지 말고 커밋하지 마라. 요구는 README와 <요구 사본 경로>에서만 읽는다(계획 문서의 결정 기록은 요구의 근거로 쓰지 않는다). 구현은 기준 커밋 <해시> 뒤의 모든 변경으로 본다: 먼저 `git diff --stat <해시> -- . ':!.harness' ':!.agents' ':!.codex' ':!AGENTS.md' ':!*.min.js'`로 바뀐 파일을 보고(커밋 안 한 변경 포함), 코드와 문서는 `git diff <해시> -- <그 파일들>` 한 번으로 읽는다. 생성 결과·데이터 파일(json, csv 등)은 크기와 앞부분만 본다. 새 파일은 `git status --short -uall`의 ?? 줄이다. 요건을 이해하는 데 필요하면 바뀌지 않은 과제 파일도 연다. 사용자에게 보이는 화면은 /tmp/screen_last/의 파일로 읽는다(HTML은 태그를 무시하고 글자만, JSON은 앞부분). 화면을 자바스크립트로 그리면 그 화면 코드도 함께 읽는다. 돌려줄 것 세 표: ① 요청 안 한 동작·화면·설정 | 위치 | 이유(계획 문서의 단계와 '넣지 않은 것'은 변경 대조용으로만 읽고, 요구 근거는 README와 요구 사본에서만 찾아라. 그 근거가 없고 해당 요구의 구현·검증에도 필요하지 않은 추가 동작·라우트·응답 헤더·화면 기능·설정·결과 파일의 항목을 적어라. 계획에 적혔다는 이유만으로 빼지 마라. 승인된 정보의 요약·이름표·배치 조정과, 그 사용 장면에 필요해 화면이 받은 데이터 안에서 하는 정렬·필터·쪽 이동·검색(새 지표가 아닌 것)은 화면 작업이므로 적지 않는다(서버 동작이 더해졌으면 다른 추가 동작처럼 근거를 대조한다). 남길지는 사용자가 정한다. 기준 커밋 전부터 있던 동작과, 새 동작 없이 구조만 나눈 것(계층·공통 함수·설정 모듈. 구조 검토는 ②)은 이 표에 넣지 않는다. 어디서도 쓰지 않는 부품·설정은 적는다) ② 빠졌거나 요건과 다르게 보이는 구현 | 위치 | 어느 문장과 다른가(결론·등급이 입력과 상관없이 글자로 고정된 곳, 기간·ID·기준값이 여러 곳에 흩어져 박힌 곳, 판정·계산·표시의 구조 때문에 고치거나 검증할 범위가 쓸데없이 넓어진 곳, 맞음을 보이려는 기대값을 구현 함수를 돌려 얻은 값으로 고정한 테스트도 적어라(바꾸면 안 되는 기존 동작을 지금 출력으로 고정한 회귀 테스트는 빼고)) ③ 이 화면을 쓰는 사람(README의 사용 장면) 입장에서 읽기 어렵거나 이상하거나 오해할 만한 표시 | 화면에 실제로 보이는 글자 | 왜 문제인가. 중간 보고나 질문은 보내지 말고 끝났을 때 결과만 돌려줘."
- 띄운 뒤 결과를 기다리는 동안 결과에 기대지 않는 3·4번(제출 문서·계획 문서 정리)을 먼저 한다. 최종 결과를 이미 받았으면(알림·메시지 포함) 기다리지 않고 쓴다. 3·4번을 마쳤는데 아직이면 `wait_agent`를 넉넉한 대기 시간(예: timeout_ms 600000)으로 한 번 부른다(짧게 되풀이하지 않는다). 새 에이전트를 쓸 수 없으면 같은 자료만 보고 직접 한다.
- 1번 표와 어긋나는 곳(1번은 충족인데 ②에 나온 것)은 둘 다 보이고, 받은 결과로 바뀌는 제출 문서 문장(검증 결과·남은 한계)은 고친다.

## 3. 제출 문서
- 파일 이름은 README가 정한 것을 쓴다. 정하지 않았으면 HANDOFF.md 하나에 쓴다.
- README가 제출하라고 한 문서·양식 파일은 각각 README가 정한 절·양식대로 채운다. 담당자와의 질문·답·합의를 담는 파일은 COLLAB.md의 확인표·담당자 확인 기록에서 옮겨 쓴다(원문은 바꾸지 않는다).
- 제출 문서에 사람의 판단·이해·직접 확인을 서술하는 칸(답변·회고·협업 기록의 사람 몫 등)이 있으면, 그 문장은 사용자 발언과 결정 기록·협업 기록·검증 보고에 남은 실행 기록에 근거해서만 쓴다. 사용자 문장을 아직 받지 못했으면 그 칸만 미루고 나머지(3번의 다른 문서와 4~5번)를 계속한다. 입력부터 결과까지의 흐름·고른 안과 이유·남은 한계 하나를 세 줄로 써 달라는 요청은 6번 질문과 함께 한다. 받은 뒤 그 문장과 기록으로 확인되는 사용자 판단만으로 1인칭 초안을 쓴다(AI가 한 일은 AI가 했다고 쓰고, 기록에 없는 것은 비워 두거나 '미확인'으로 남긴다). 이미 답이 있으면 사용자 판단만 보강한다.
- README가 분량·절을 정하면 그것을 따른다. 없으면 아래 '담을 것'을 다 담고 같은 숫자를 여러 절에서 되풀이하지 않는다. 결과 전체 표는 넣지 않고 결과 파일 경로를 적는다.
- 하네스 용어(kickoff, relay, verify, wrapup, weakness, 쓴/뺀/따로)는 풀어 쓴다: 담당자 확인, 독립 재계산, 마감 점검, 사용/제외/보류 등.
- 담을 것:
  - 목표(담당자 표현으로)
  - 실행 방법(명령, 포트, 주소)
  - 데이터 흐름: 입력 파일마다 읽는 함수 → 판정·계산 함수 → 저장·화면, 파일 사이를 잇는 키(한 줄씩), 대표 입력 하나가 입력부터 최종 출력까지 거치는 길 한 줄(EXPLAIN.md 단계별 설명과 맞춰 빠진 연결을 채운다)
  - 구조: 구성 요소마다 맡은 일·주고받는 것과 그렇게 나눈 이유 한 줄(계획 문서 구조 단락의 A번호. 함께 본 다른 나눔이 있으면 그것도)
  - 판단 기준과 출처(담당자 답·데이터·가정 구분)
  - 검증 결과(실행한 명령과 숫자. 1번에서 근거로 쓴 verify 보고 포함. 확인한 사용 장면과 미확인 장면)
  - 이번에 만들지 않은 것과 이유
  - 비교한 안과 버린 방법: 실제로 비교한 안마다 무엇을 바꿨나·핵심 숫자·고르거나 버린 이유 한 줄(재지 않은 것은 '미측정')
  - 남은 한계(항목마다 '지점(구성 요소·함수) → 발생 조건과 파급 → 다음에 검증·개선할 것' 한 줄)
  - 이어받을 사람이 할 다음 한 단계
  - Codex에 맡긴 것과 사람이 직접 정하거나 다시 확인한 것(결정 기록의 '사용자 결정'과 검증 결과에서)
  - 사용한 공개 자료(작업 폴더 맨 위 `.harness/SOURCE.txt`의 저장소 주소, 작업 규칙·스킬·점검 도구이며 판정 로직과 화면은 이 작업에서 썼다는 한 줄)
- 실행하지 않은 검증이나 없는 기능은 쓰지 않는다. 검증 근거로 적는 스크립트는 커밋된 파일이어야 한다(새로 만든 것은 verify/, 기존 tests/는 그대로. /tmp에만 있는 스크립트는 근거로 들지 않는다. 행 목록 같은 자료 사본은 /tmp에 둬도 된다).

## 4. 계획 문서 정리
- 계획 문서 본문에서 지금의 요구·기준·가정과 모순되는 문장과 지난 진행 상태 문장('미실행'·'현재 단계', 폐기한 시간표)만 고친다. 실제로 하지 않은 검증과 미확인 사항은 남긴다. 협업 기록의 원문과 결정 기록은 그대로 둔다.
- 3·4번에서 지금 쓸 수 있는 문서를 마치면 커밋한다(사용자 문장을 기다리는 칸은 미완료로 둔다).

## 5. 점검
- 작업 폴더 맨 위에서 `python3 .harness/tools/precheck.py --exclude <입력 데이터 폴더>`를 실행한다(키 모양, TODO·FIXME, 이메일·전화번호·등록번호 모양, 제출 문서의 /tmp 인용, 남은 검증 차이, 열지 못한 파일. 값은 가려서 나온다). 종료 코드 0은 찾은 것 없음, 1은 있음, 3은 실행 오류다.
- 맨 앞 줄의 건수를 옮기고, 찾은 것마다 지울지 남길지(과제가 준 파일은 남김)와 이유를 적는다.
- 과제가 준 파일(키 파일 포함)은 지우자고 하지 않는다. 키 파일은 커밋에 들어가지 않는지(.gitignore·.git/info/exclude)만 확인하고 그 결과를 적는다.
- '검사하지 않은 것(.gitignore에 걸림)'이 나왔는데 제출이 폴더 통째인지 모르면 `--include-ignored`를 붙여 한 번 더 돌린다.

## 6. 끝에 한 번에 알려 줄 것
- 3번에서 미룬 사용자 문장이 있으면 고칠 후보와 함께 요청한다. 받기 전에는 그 칸을 작성 완료로 적지 않는다. 받은 뒤에는 3번 원칙대로 쓰고, 그 문서가 제출 파일이면 5번 점검을 다시 돌려 커밋한다. 고칠 후보의 수정도 있으면 아래 수정 후 절차와 합쳐 한 번만 점검·커밋한다.
- 고칠 후보: 미충족, 요청 안 한 동작, 요건과 다르게 보이는 구현, 화면 검토(③과 화면 점검)에서 나온 것, 5번에서 남길지 정하지 못한 것. 항목마다 내 제안(고침/남김과 이유)을 붙여 번호로 묻는다. 요청 안 한 동작은 기본 제안을 '뺌'으로 하고, 남기자고 할 때는 그 동작이 필요한 요구 문장이나 실행·검증상 이유를 한 줄로 댄다. 제출 결과의 결론·등급·권고가 달라지는 후보는 현행이 합의한 기준에 맞는다고 이번 검증으로 확인됐으면 기본 제안을 '현행 유지 + 제출 문서에 한 줄 보충'으로 한다. 바꾸자고 할 때는 바꾼 뒤 다시 확인하는 데 드는 시간을 적고, 계획 문서 시간 기준점의 제출 시작 시각 안에 끝낼 수 있을 때만 권한다(기준점이 없으면 시간만 적는다).
- 사용자가 고른 것을 고친 뒤에는: 바뀐 것이 무엇에 닿는지로 다시 할 확인을 고른다. 판정·계산·입력·설정에 닿으면(서버 응답이 필요하면 서버를 다시 띄운 뒤) 가장 최근 verify/checker_N/check.py를 다시 실행하고 구현 결과를 새로 만들어 같은 방법으로 다시 비교해 report_N.md와 diff_N.csv를 지금 값으로 갱신한다(끝에 '수정 후 재실행: 명령·종료 코드·비교 건수·불일치 건수'). 기준·가정이 바뀐 수정이면 다시 비교하지 않고 `/new` → `$verify 해 줘. wrapup 수정 확인`을 안내한다. 문서나 화면 표시만 바뀌었으면 비교는 다시 하지 않고 이전 결과를 인용하며, 화면이 바뀌었으면 그 화면만 screen 스킬대로 다시 본다. 제출 파일이 바뀌었으면 precheck를 다시 돌린다. 제출 문서의 검증 결과·남은 한계를 맞게 고치고 커밋한다. 서버 코드가 바뀌었으면(아직 다시 띄우지 않았으면 다시 띄우고) 사용자가 브라우저로 확인할 것을 목록으로 준다: 1번 표의 화면 요건마다 한 줄(어느 역할로 무엇을 누르거나 고르면 무엇이 보여야 하는지, 실제로 여는 주소와 창 폭으로).
- 서버 주소와 다시 띄우는 명령 한 줄(사용자가 Browser로 확인한다).
- 사용자가 고른 수정과 다시 할 확인·커밋까지 끝났으면 마지막 줄에 `/new` → `$weakness 해 줘`를 안내한다(남은 한계가 제출 문서에 커밋돼 있어야 다음 대화가 읽는다).
- 담당자에게 물을 것이 생기면 협업 기록 '보낼 질문' 절에 한 줄에 결정 하나로 쓰고(협업 기록에 '한 번에 n개'가 있으면 n개까지), 나머지는 확인표 '질문' 행으로 남긴다. 이미 받은 답으로 정해지는 것은 다시 묻지 않는다.
