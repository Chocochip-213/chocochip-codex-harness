# wrapup: 마감

이 글이 스킬 전문이다. 이 SKILL.md를 다시 열어 읽지 않는다.
지금부터 기능을 더하지 않는다. 사용자가 6번에서 고르기 전에는 코드를 고치지 않는다. 1~5번은 묻지 않고 이어서 하고, 고칠 후보는 6번에서 세 묶음 이내로 묶어 한 번에 묻는다. 점검 출력은 대화에만 보이고 파일로 남기지 않는다.

## 1. 요건 대조
| 요건(README 문장·담당자 답 인용) | 충족/부분/미충족 | 근거(파일·함수, 이번에 실행한 명령과 결과) |
- 요건은 빠짐없이 한 줄씩 뽑는다: README의 과제·화면·제출물·꼭 지킬 것 문장, 협업 기록에서 담당자가 확정한 답, 개발 시작 메모의 성공 기준과 만들지 않을 것(만들지 않았는지 확인). 표 위에 '요건 n개: 충족 a, 부분 b, 미충족 c'를 적는다.
- '충족'은 이번에 실행해 확인한 것만 쓴다. 테스트 통과가 아니라 요건 문장과 실제 동작을 맞춰 본다.

## 2. 새 에이전트의 검토
- 기준 커밋: `.harness/BASE`에 적힌 해시(하네스 설치 직전 커밋). 파일이 없거나 비어 있으면(둘 다 없으면 첫 커밋) 가장 오래된 하네스 커밋 `git log --format=%h --grep='chore(harness): 작업 도구 추가' | tail -n 1`.
- 사용자에게 보이는 화면: 웹이면 `bash verify/curl_check.sh`를 다시 실행해(서버가 지금 코드로 도는지도 본다) /tmp/screen_last/의 화면 파일을 새로 받는다. 서버가 꺼져 있으면 켜는 명령을 6번에 적고, 화면 검토는 '미실행'으로 둔다.
- 요구 사본: 가장 최근 verify/spec_N.md를 쓴다. 그 뒤 '합의 뒤 변경'이 생겼거나 사본이 없으면 개발 시작 메모와 담당자 확인 기록을 verify/spec_N.md(새 번호)로 옮긴다. 결정 기록은 옮기지 않는다.
- `spawn_agent`로 새 에이전트를 띄운다. `task_name`은 `reviewer_N`, `fork_turns`는 `"none"`. 메시지:
  "너는 요건 검토를 맡은 하위 에이전트다. AGENTS.md의 결정 기록·커밋·행 대조 규칙은 이 일에 적용하지 않는다: 파일을 만들거나 고치지 말고 커밋하지 마라. 요구는 README와 <요구 사본 경로>에서만 읽는다(계획 문서의 결정 기록은 요구의 근거로 쓰지 않는다). 구현은 기준 커밋 <해시> 뒤의 모든 변경으로 본다: 먼저 `git diff --stat <해시> -- . ':!.harness' ':!.agents' ':!.codex' ':!AGENTS.md' ':!*.min.js'`로 바뀐 파일을 보고(커밋 안 한 변경 포함), 코드와 문서는 `git diff <해시> -- <그 파일들>` 한 번으로 읽는다. 생성 결과·데이터 파일(json, csv 등)은 크기와 앞부분만 본다. 새 파일은 `git status --short -uall`의 ?? 줄이다. 요건을 이해하는 데 필요하면 바뀌지 않은 과제 파일도 연다. 사용자에게 보이는 화면은 /tmp/screen_last/의 파일로 읽는다(HTML은 태그를 무시하고 글자만, JSON은 앞부분). 화면을 자바스크립트로 그리면 그 화면 코드도 함께 읽는다. 돌려줄 것 세 표: ① 요청 안 한 동작·화면·설정·추상화 | 위치 | 이유(계획 문서의 단계와 '넣지 않은 것'은 변경 대조용으로만 읽고, 요구 근거는 README와 요구 사본에서만 찾아라. 그 근거가 없고 해당 요구의 구현·검증에도 필요하지 않은 추가 동작·라우트·응답 헤더·화면 요소·설정·결과 파일의 항목을 적어라. 계획에 적혔다는 이유만으로 빼지 마라. 남길지는 사용자가 정한다. 기준 커밋 전부터 있던 동작은 이 표에 넣지 않는다) ② 빠졌거나 요건과 다르게 보이는 구현 | 위치 | 어느 문장과 다른가(결론·등급이 입력과 상관없이 글자로 고정된 곳, 기간·ID·기준값이 여러 곳에 흩어져 박힌 곳, 바뀐 핵심 함수에서 따로 검증할 판정이나 계산과 표시가 섞여 고칠 범위를 넓히는 곳도 적어라) ③ 이 화면을 쓰는 사람(README의 사용 장면) 입장에서 읽기 어렵거나 이상하거나 오해할 만한 표시 | 화면에 실제로 보이는 글자 | 왜 문제인가. 중간 보고나 질문은 보내지 말고 끝났을 때 결과만 돌려줘."
- 최종 결과를 이미 받았으면(알림·메시지 포함) 기다리지 않고 쓴다. 아직이면 `wait_agent`를 넉넉한 대기 시간(예: timeout_ms 600000)으로 한 번 부른다(짧게 되풀이하지 않는다). 새 에이전트를 쓸 수 없으면 같은 자료만 보고 직접 한다.
- 1번 표와 어긋나는 곳(1번은 충족인데 ②에 나온 것)은 둘 다 보인다.

## 3. 제출 문서
- 파일 이름은 README가 정한 것을 쓴다. 정하지 않았으면 HANDOFF.md 하나에 쓴다.
- 처음 보는 사람이 10분 안에 읽을 분량으로 쓴다. 같은 숫자를 여러 절에서 되풀이하지 않는다. 결과 전체 표는 넣지 않고 결과 파일 경로를 적는다.
- 하네스 용어(kickoff, relay, verify, wrapup, weakness, stale, 쓴/뺀/따로)는 풀어 쓴다: 담당자 확인, 독립 재계산, 마감 점검, 사용/제외/보류 등.
- 담을 것:
  - 목표(담당자 표현으로)
  - 실행 방법(명령, 포트, 주소)
  - 구조(입력 → 판정 → 화면, 파일·함수)
  - 판단 기준과 출처(담당자 답·데이터·가정 구분)
  - 검증 결과(이번에 실행한 명령과 숫자)
  - 이번에 만들지 않은 것과 이유
  - 시도했다가 버린 방법과 이유
  - 남은 한계
  - 이어받을 사람이 할 다음 한 단계
  - Codex에 맡긴 것과 사람이 직접 정하거나 다시 확인한 것(결정 기록의 '사용자 결정'과 검증 결과에서)
  - 사용한 공개 자료(작업 폴더 맨 위 `.harness/SOURCE.txt`의 저장소 주소, 작업 규칙·스킬·점검 도구이며 판정 로직과 화면은 이 작업에서 썼다는 한 줄)
- 실행하지 않은 검증이나 없는 기능은 쓰지 않는다. 검증 근거로 적는 스크립트는 커밋된 파일이어야 한다(새로 만든 것은 verify/, 기존 tests/는 그대로. /tmp에만 있는 스크립트는 근거로 들지 않는다. 행 목록 같은 자료 사본은 /tmp에 둬도 된다).

## 4. 계획 문서 정리
- 계획 문서 본문에서 지금의 요구·기준·가정과 모순되는 문장과 지난 진행 상태 문장('미실행'·'현재 단계', 폐기한 시간표)만 고친다. 실제로 하지 않은 검증과 미확인 사항은 남긴다. 협업 기록의 원문과 결정 기록은 그대로 둔다.
- 3·4번을 마치면 커밋한다.

## 5. 점검
- 작업 폴더 맨 위에서 `python3 .harness/tools/precheck.py --exclude <입력 데이터 폴더>`를 실행한다(키 모양, TODO·FIXME, 이메일·전화번호·등록번호 모양, 제출 문서의 /tmp 인용, 남은 검증 차이, 열지 못한 파일. 값은 가려서 나온다). 종료 코드 0은 찾은 것 없음, 1은 있음, 3은 실행 오류다.
- 맨 앞 줄의 건수를 옮기고, 찾은 것마다 지울지 남길지(과제가 준 파일은 남김)와 이유를 적는다.
- 과제가 준 파일(키 파일 포함)은 지우자고 하지 않는다. 키 파일은 커밋에 들어가지 않는지(.gitignore·.git/info/exclude)만 확인하고 그 결과를 적는다.
- '검사하지 않은 것(.gitignore에 걸림)'이 나왔는데 제출이 폴더 통째인지 모르면 `--include-ignored`를 붙여 한 번 더 돌린다.

## 6. 끝에 한 번에 알려 줄 것
- 고칠 후보: 미충족, 요청 안 한 동작, 요건과 다르게 보이는 구현, 화면 검토(③)에서 나온 것, 5번에서 남길지 정하지 못한 것. 항목마다 내 제안(고침/남김과 이유)을 붙여 번호로 묻는다. 요청 안 한 동작은 기본 제안을 '뺌'으로 하고, 남기자고 할 때는 그 동작이 필요한 요구 문장이나 실행·검증상 이유를 한 줄로 댄다. 제출 결과의 결론·등급·권고가 달라지는 후보는 현행이 합의한 기준에 맞는다고 이번 검증으로 확인됐으면 기본 제안을 '현행 유지 + 제출 문서에 한 줄 보충'으로 한다. 바꾸자고 할 때는 바꾼 뒤 다시 검증하고 결과(화면·파일)를 확인하는 데 드는 시간을 적고, 계획 문서 시간 기준점의 제출 시작 시각 안에 끝낼 수 있을 때만 권한다(기준점이 없으면 시간만 적는다).
- 사용자가 고른 것을 고친 뒤에는: 서버 코드가 바뀌었고 다시 비교에 서버 응답이 필요하면 먼저 다시 켜 달라고 하고 이 턴을 끝낸다(다시 켠 뒤 이어서 한다). 제출 문서의 검증 결과·남은 한계를 맞게 고치고, precheck를 다시 돌리고, 가장 최근 verify/checker_N/check.py를 다시 실행하고 구현 결과를 새로 만들어 같은 방법으로 다시 비교해 report_N.md와 diff_N.csv를 지금 값으로 갱신하고(끝에 '수정 후 재실행: 명령·종료 코드·비교 건수·불일치 건수'), 커밋한다. 기준·가정이 바뀐 수정이면 다시 비교하지 않고 `$verify`를 다시 하라고 알린다. 서버 코드가 바뀌었으면 다시 켜 달라고 말하고, 브라우저로 확인할 것을 목록으로 준다: 1번 표의 화면 요건마다 한 줄(무엇을 누르거나 고르면 무엇이 보여야 하는지).
- 서버를 다시 켜는 명령 한 줄(사용자가 직접 켜서 Browser로 확인한다).
