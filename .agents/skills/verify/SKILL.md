# verify: 다른 눈으로 다시 확인

이 글이 스킬 전문이다. 전문이 현재 문맥에 있으면 이 SKILL.md를 다시 열지 않고, 없거나 불확실하면(자동 압축 뒤 등) 다시 읽는다.
먼저 README, 계획 문서(README가 정한 이름, 없으면 PLAN.md)의 개발 시작 메모·합의 뒤 변경·단계와 결정 기록의 '화면 점검'·'사용자 확인' 줄(본 역할·주소·폭·상태), 협업 기록(COLLAB.md)의 담당자 답·'보낼 질문' 절(답 대기)을 읽고 입력·구현·결과 파일을 찾는다. 0~6번을 이어서 한다. 결과는 모두 이번에 실행한 명령과 출력(종료 코드·건수)으로 보인다. 이번에 돌리지 않은 것은 '미실행'이라고 쓴다. 사용자가 "고쳐 줘"라고 하기 전에는 고치지 않는다. N은 이번 검증 번호다(verify/checker_* 번호 중 가장 큰 것 + 1). 2번에서 지난 검증기를 다시 쓰면 그 검증기의 번호를 N으로 쓰고 report_N.md·diff_N.csv를 새 결과로 고쳐 쓴다(차이가 없어졌으면 diff_N.csv는 머리 줄만 남긴다).
확인 명령마다 실행 전에 무엇을 읽고 쓰는지(저장 파일·DB·세션·외부 호출) 본다. 입력 원본·저장된 업무 상태를 바꿀 수 있는 것은 사본에서만 하고(로그인 세션과 이 스킬이 만드는 verify/ 파일은 예외), 분리를 확인하지 못하면 '미실행'으로 둔다. 이 규칙은 요청뿐 아니라 스크립트와 직접 함수 호출에도 적용한다.

## 0. 웹 서비스면 서버부터 (새 에이전트를 띄우기 전에)
- 서버는 AGENTS.md대로 내가 띄운다(명령·주소는 실행 안내 문서, 없으면 계획 문서 구조 단락의 서버 줄). 꺼져 있거나 옛 코드로 돌면 다시 띄운 뒤 확인한다.
- 확인할 요청을 verify/curl_check.sh 한 파일에 모은다.
  - 맨 앞은 이렇게 쓴다:
    ```bash
    #!/usr/bin/env bash
    B="${1:-<실행 안내 문서의 서버 주소>}"
    if ! curl -sS --noproxy '*' --connect-timeout 5 -m <대기 초> -o /dev/null "$B/"; then
      echo
      if [ -n "${CODEX_SANDBOX_NETWORK_DISABLED:-}" ]; then echo "응답 없음: 샌드박스가 네트워크를 막았을 수 있음(승인받아 다시 실행)"; exit 2; fi
      echo "서버 응답 없음"; exit 3
    fi
    ```
  - 이어서 요구에 나온 화면마다 본문과 그 화면이 받는 결과 JSON을 /tmp/screen_last/ 폴더에 파일로 저장한다.
  - 그다음 코드에서 뽑은 라우트마다(직접 만든 것과 화면이 쓰는 것. 고른 도구가 기본으로 붙인 라우트는 과제가 쓰거나 고친 것만) 정상 요청을 한 번 보내 한 줄에 `상태코드 메서드 경로`를 출력한다(`curl -sS --noproxy '*' -m <대기 초> -o /dev/null -w "%{http_code}"`. 대기 초는 개발 시작 메모의 허용 대기 시간, 없으면 10). 입력을 받는 라우트에는 경계 입력과 잘못된 입력을 한 번씩 더 보낸다. 거절·실패 응답에는 요구·합의상 공개 가능한 범위에서 원인과 해당 항목이 남는지 본다. 필요한 설명이 일반 문구로만 나오면 4번 표에 넣는다. 숫자를 돌려주는 라우트는 본문을 /tmp/screen_last/에 저장하고 핵심 숫자 줄만 출력한다.
  - 라우트마다 무엇을 읽고 쓰는지 코드에서 확인해 나눈다. 작업 데이터·상태를 바꿀 수 있는 요청(저장·승인·적용 등)은 작업 폴더의 서버에는 보내지 않는다. 사본 서버(저장 파일·DB까지 사본을 쓰는 서버. 검사할 때마다 지금 코드·설정과 작업 폴더의 저장 상태를 새로 복사하고 저장 경로도 사본을 가리키게 해 다른 포트(개발 시작 메모·계획 문서 '환경'의 허용 범위 안)로 띄우되 주소는 127.0.0.1에만 묶는다(사본은 이 컴퓨터 안의 확인에만 쓴다. AGENTS.md의 0.0.0.0은 작업 서버만). 시작·끄기는 AGENTS.md 방식대로 하되 로그·PID는 /tmp/server_copy.log·/tmp/server_copy.pid. 이 준비와 끄기(검사가 오류로 끝나도)는 curl_check.sh 안에 둔다)에만 보내고, 요구된 상태 변화(저장 뒤 조회 등)가 맞는지와 그 뒤 주요 화면·요청을 계속 쓸 수 있는지 본다. 그 요청 전후로 사본에서 보존할 대상(입력 원본·설정·제출 산출물)의 경로 목록과 내용 지문(예: `sha256sum`)을 견줘 생성·삭제·내용 변경을 본다(요구·합의가 바꿔도 된다고 한 파일과 실행에 필요한 일시 파일만 빼고, 같은 폴더 안의 보존 대상은 빼지 않는다). 설명되지 않는 변경은 경로·종류와 함께 4번 표에 넣고, 비교하지 못한 범위는 '미확인'으로 둔다(테스트 클라이언트로 대신할 때도 같다). 사본 서버를 띄우지 못했으면 프레임워크 테스트 클라이언트와 임시 저장소처럼 작업 폴더 상태와 분리된 방법으로 같은 요청을 curl_check.sh 안에서 확인해 그 줄 끝에 '(테스트 클라이언트)'를 붙이고, 그것도 못 하면 그 라우트는 "미실행: 상태 변경(사본 서버 없음)"으로 출력한다. 읽기만 하는 요청과 로그인·로그아웃(세션을 만들고 지우는 것까지)은 작업 폴더 서버에 보낸다(로그인 값은 실행 안내의 환경 파일에서 읽고 출력하지 않는다. 로그인이 세션 밖의 업무 데이터(접속 기록·시도 횟수 등)를 저장하면 사본 서버). 외부 서비스(AI 등)를 부르는 라우트는 비용·부작용을 보고 필요한 최소 횟수만 보낸다.
  - 계획 문서 구조 단락에 입력·상태가 바뀌거나 같은 요청이 겹칠 때의 처리가 적혀 있으면('없음'이 아니면) 그 조건을 이 사본 확인에 넣는다: 그 조건을 재현하는 데 필요한 최소 입력만 사본에 만들어(요구·합의 밖의 입력 유형은 더하지 않는다) 계산과 그 결과를 쓰는 요청 사이에 입력·상태를 바꾸거나 같은 요청을 겹쳐 보내고, 기대 동작은 요구·합의에서 정한다(근거가 없으면 '미확인').
  - 입력 데이터를 바꿔 적용·재계산하는 웹 서비스면, README·메모가 지원하라고 한 변경 중 ① 결과의 유무·포함 대상이 달라지는 제약 경계 ② 후속 선택·표시가 따라야 할 입력 범위(기간·대상 등)의 변경을 각각 한 사례씩, 해당하는 것만 총 두 사례 이내로 사본에서 확인한다. 상태가 입력의 버전·내용과 묶여 있으면, 위 사례 중 해당하는 하나의 변경 뒤 원래 내용을 다시 적용하고 상태·안내를 요구·합의의 기대값과 대조한다. 복원해야 하는지 새 버전으로 보아야 하는지 근거가 없으면 '미확인'으로 둔다. 준비된 정상 변경 묶음만으로 대신하지 않고, 입력의 허용 범위 안에서 각 조건을 만드는 최소 변경을 쓴다(이상 입력은 요구·합의된 입력 범위나 제공 데이터에 실제로 있는 오류만). 적용 직후 재계산에 쓰는 선택 범위·기본값과 재계산 뒤 주요 화면·응답·출력을 확인한다(화면이 없으면 응답·출력만). 기대 동작은 요구·합의에서 정하고 근거가 없으면 '미확인'으로 두며, 처리되지 않은 실패나 새 입력을 따라야 할 값이 이전 입력에 머무는 차이는 4번 표에 넣는다. 사례마다 시작 전에 시간 기준점의 제출 시작까지 끝낼 수 있을지 보고, 끝내지 못할 사례는 이유와 함께 '미실행'으로 남긴다. 입력 변경 기능이나 해당 조건이 없으면 사례를 억지로 만들지 않고 '해당 없음'으로 적는다.
- `bash verify/curl_check.sh`는 지금 권한에서 네트워크가 막혀 있으면(샌드박스면 대개 막힌다) 처음부터 승인을 받아(샌드박스 밖에서) 실행한다. 뒤에 리다이렉트나 파이프를 붙이지 않는다(사용자가 승인 창에서 '다시 묻지 않기'를 고르면 다음부터 그대로 통과한다). 로그인 값이 필요하면 실행 안내의 환경 파일을 스크립트 안에서 읽어 쓴다(값은 출력하지 않는다). 승인이나 로그인 값을 얻을 수 없으면 사용자에게 shell 탭에서 칠 명령 한 줄을 주고, 이 확인은 미실행으로 두고 그 출력에 기대지 않는 1~3번은 계속한다(직접 함수를 부른 값을 실제 요청 통과로 적지 않는다. 사용자가 출력을 붙여 넣으면 그 출력으로 이 확인을 마친다).
  - 승인 없이 돌려 종료 코드 2가 나오면: 승인을 받아 한 번 더 실행한다.
  - 승인받아 실행했는데도 종료 코드 2나 3(응답 없음)이면: 서버를 다시 띄우고 한 번 더 실행한다. 그래도 응답이 없으면 /tmp/server.log 끝 줄로 원인을 알리고, 이 확인은 미실행으로 둔 채 그 출력에 기대지 않는 1~3번은 계속한다.
  - 서버가 지금 코드로 도는지: 서버 응답의 핵심 숫자(건수 등)를 판정 함수를 직접 불러 얻은 값과 비교한다. 다르면 AGENTS.md대로 서버를 다시 띄워 curl_check와 이 비교를 다시 하고, 남은 차이는 4번 표에 넣는다.
- 상태 코드는 그 요청의 기대 동작과 견준다(예: 2xx 정상, 400 입력 거절, 404 없는 대상이나 라우트, 500 버그, 000 응답 없음). 200이어도 본문이 틀릴 수 있으니 숫자 본문은 4번에서 검증 값과 비교한다.
- 실제 사용 장면: 사람이 실제로 여는 주소(미리보기 경로 포함)·창 폭·역할·시작 상태에서 끝까지 본 장면만 '확인한 장면'이다. 근거는 screen 스킬의 화면 점검 기록(어느 역할·폭·상태를 봤는지)이나 사용자가 말한 것이고, curl 본문은 그 근거가 아니다. 화면 점검 기록은 그 화면이 그렇게 보였다는 근거일 뿐이고, 누르기·저장·다시 열기 같은 흐름을 끝까지 했다는 근거는 그 흐름을 실행한 기록이나 사용자가 말한 것이다. 요구된 장면 중 근거가 없는 것은 report_N.md에 '미확인 장면'으로 적는다.

## 1. 확인할 것 고르기
- 사용자가 꼭 볼 항목이나 예상값을 말했으면 그것부터 넣고, 예상값과 다르면 표에 함께 보인다. 결과(서버 응답 본문, 출력 파일, 판정 함수를 직접 부른 결과)에서 사람이 바로 쓰는 숫자·결과를 모두 합쳐 적어도 세 개 고른다(예: 핵심 결과, 전체 건수나 합계, 특정 입력 하나의 처리 결과). 담당자 결정에 쓰이는 숫자가 더 있으면 그것도 넣는다. README·메모가 화면에 요구한 계산 표시(입력에서 계산해 화면에 보이는 값)가 있으면 그 표시마다(같은 계산의 반복은 한 번) 실제 입력 한 건의 화면 값을 항목에 넣는다(아래 '할 수 있는지' 점검과 별개로 값을 대조한다). 고르지 못한 숫자는 '확인 못 한 숫자'로 적는다.
- 결과가 숫자가 아니면 결과 모양에 맞춰 고른다: ① 요구·합의 문장에 있는 제약마다 위반 건수(0건이어야 할 것) ② 합의한 경우(정상·결과 없음·일부만·실패 등)마다 실제 입력 하나의 최종 결과가 합의한 모양인지(내부 집계 일치만으로 충족이라 하지 않는다) ③ 바꾸면 안 되는 동작의 전후 값과 고친 오류의 재현 입력 결과 ④ 레코드마다 결과가 있으면 rows.csv로 대조하고, 맞는 답이 여럿일 수 있으면 ID 일치 대신 ①과 고른 기준의 숫자(누락·중복·고정 규칙은 그대로 대조) ⑤ 결과가 원문·근거와 맞는지를 판정하면 글자 포함만 보지 말고, 값·단위·대상과 부정·조건·시점이 같은 뜻인지 본다. 결과가 '모름·판단 불가'일 수 있으면 거짓과 모름을 따로 센다(모름을 거짓으로 내보낸 건은 차이).
- 외부 서비스를 부르면 결과 형식과 관계없이 다음을 내가 직접 확인해 표에 넣는다: 한 번 실행의 호출 횟수, 키가 없거나 호출이 실패할 때 요구·합의한 동작, 호출 제한·실패 뒤 재시도 횟수와 멈추는 조건이 요구·합의대로인지, 보낸 본문에 개인정보가 없는지, 요구·합의에 입력 길이·크기 한도가 있으면 실제 입력 가운데 그 한도에 가장 가까운 한 건을 실제 경로로 보낸 결과가 잘림·실패 없이 요구대로인지, 마지막 verify 뒤 응답을 받아들이는 검사(수용·거절 조건)를 바꿨으면 직전에 실제 경로로 성공한 입력 한 건(사용자가 보고한 것 포함)을 다시 보낸 결과가 그대로인지(이 둘의 실제 호출은 각각 한 번). 만든 글이 사실을 전해야 하면 결과 한 건을 원문과 대조해 없는 숫자·약속이 없는지도 확인한다.
- 항목마다 정의를 한 줄로 쓴다(대상, 기간, 포함·제외, 단위). 정의는 README, 담당자 답, 개발 시작 메모의 말로 쓰고 구현 코드나 결정 기록에서 옮기지 않는다.
- 개발 시작 메모의 가정(사용자 결정·기본값) 중 핵심 결과를 바꿀 수 있는 것을 하나 고르고(시간 기준점의 제출 시작까지 60분 넘게 남았거나 기준점이 없으면 세 개 이내로. 그런 가정이 없으면 '없음'이라 쓴다), 가정마다 다른 안을 한 줄로 쓴다. 다른 안은 그 가정을 정할 때 함께 본 선택지나 요구·실제 데이터로 성립하는 다른 해석 가운데 핵심 결과를 가장 크게 바꿀 것으로 한다(예: 값이 모자라 건을 보류·제외한 가정이면 확인된 값만으로 결과가 정해지는 건은 판정하는 안).
- 계획 문서 단계 표에서 지금까지 끝난 단계가 맡은 개발 시작 메모 항목마다, 쓰는 사람이 요구된 곳(화면·요청·출력)에서 그것을 실제로 할 수 있는지 한 줄(어디서·무엇으로)로 본다. 기능 동결 뒤이거나 남은 개발 단계가 없으면, 메모 항목 대신 README의 과제·화면·제출물·꼭 지킬 것 문장과 담당자 확정 답을 요구 한 줄씩으로 삼아 같은 방법으로 본다(wrapup 1번 표와 같은 단위). 메모에만 있는 요구도 더한다. 사람 몫 제출 칸은 대신 채우지 않고 작성 여부만 기록한다.
  - 항목 단위: README·메모가 열거한 요구와 한 항목에 묶인 여러 동작·조건은 각각 나눈다. 동결 전 중간 검증에서만 아직 남은 개발 단계가 맡은 부분을 뺀다. 같은 실행으로 확인되는 요구는 근거를 함께 쓴다.
  - 줄마다 적을 것: 요구가 구별하는 역할·입력 조건·경로·동작의 확인 범위와 실행 환경·모의한 부분(해당 없는 축은 뺀다). 요구 밖 조건·모든 조합은 추가하지 않는다.
  - 판정: 누가 언제 무엇을 보거나 할 수 있는지를 정하는 담당자·README 조건은 안내문·기록이 아니라 실제 동작(허용·거절)으로 본다. 실행 근거가 없는 요구 범위는 '부분: <항목>(안 본 조건과 이유)'으로 남기고, 실제 연동·사용 경로가 필요한 부분과 모의로 확인할 별도 요건을 구별한다. 없거나 일부만 되면 '미구현: <항목>(빠진 것)', 입력·권한·환경 때문에 못 봤으면 '미실행: <항목>(이유)'.
  - '미구현'·'미실행'·'부분' 줄은 4번 표 맨 위에 적는다(사유가 겹치면 한 줄에서 구별한다). 고칠지·더 볼지는 사용자가 정한다. 그 줄이 README 필수 문장·담당자 확정 답에 닿으면 두었을 때 쓰는 사람에게 생기는 일을 한 줄 붙여 보이고, 사용자가 두기로 하면 그 결정을 적는 자리에 항목과 영향을 함께 적는다. 그 조건을 새 서비스가 맡는지 합의되지 않았으면 미구현 대신 4번의 담당자 질문으로 한 줄 쓴다.
- 구현 값은 파일에 쓰지 않고 대화에 둔다. 새 에이전트의 결과를 받기 전에는 파일로 쓰지 않는다(새 에이전트가 볼 수 있어서).

## 2. 새 에이전트에게 따로 계산시키기
- 다시 부를 때 계획 문서의 개발 시작 메모와 '합의 뒤 변경'이 지난 verify/spec_N.md와 같고, 지난 검산이 근거로 삼은 README 요구 문장이 그대로이며, 1번에서 고른 항목과 그 정의·적용 범위·가정이 지난 check.py와 같으면 새 에이전트를 띄우지 않는다. 지난 `verify/checker_N/check.py`만 다시 실행해(남겨 둔 빠진 조건·구별 사례도 함께 나온다) 3번으로 간다(같은 계산을 되풀이하지 않는다).
- 계획 문서의 '개발 시작 메모' 절(뒤에 붙은 '합의 뒤 변경' 포함)과 담당자 확인 기록을 그대로 verify/spec_N.md에 옮긴다. 결정 기록과 구현 값은 옮기지 않는다.
- `spawn_agent`로 새 에이전트를 띄운다. `task_name`은 `checker_N`, `fork_turns`는 `"none"`(지금까지의 대화를 넘기지 않는다). 메시지는 아래 틀을 채워 보낸다.
  "너는 검증을 맡은 하위 에이전트다. AGENTS.md의 결정 기록·커밋·행 대조 규칙은 이 일에 적용하지 않는다. 읽을 것은 README, verify/spec_N.md, 데이터 <경로>뿐이다. 계획 문서, 구현 코드(<구현 폴더·파일>), 출력 파일, tests/, git 기록, verify/의 다른 파일은 열지 않는다. 파일은 verify/checker_N/ 아래에만 만든다. 본문·표본·오류를 화면에 출력할 때는 전화번호·이메일 모양을 가린다(원본과 계산용 값은 바꾸지 않는다). 다시 계산할 것: <항목마다 정의 한 줄>. 항목마다 내가 준 정의를 README·spec의 해당 원문과 견줘, 원문에는 있는데 정의에 없는 조건만 원문 위치·적용 범위와 함께 '정의에 빠진 조건'으로 돌려주고(위치를 못 대는 조건은 쓰지 말고 목적·예시·가정을 조건으로 바꾸지 마라), 계산할 수 있으면 그 조건을 넣은 값을 따로 계산하되 내가 준 정의의 값은 그대로 두어라. 가정을 바꿔 한 번 더 계산할 것: <가정 | 다른 안>(가정마다 핵심 결과에서 들어가고 빠지는 건수와 ID 세 개, 바뀌는 값·판정을 적고, 바뀐 ID 전체는 verify/checker_N/assumption_diff.csv에 저장하라). 구현 코드를 불러오지 않고 원본을 직접 읽어 계산하는 스크립트를 verify/checker_N/check.py로 저장해 실행하고, 검사마다 '구현이 어떻게 틀리면 이 검사가 잡나'를 주석 한 줄로 적고, 그 틀림을 드러낼 입력이나 입력 묶음이 제공 자료에 있으면 위치(ID가 있으면 ID)·기대 결과·어느 검사인지를 '구별 사례'로 돌려줘라(같은 사례는 여러 검사에 함께 쓰고, 없으면 '구별 사례 없음'. 새 입력을 만들거나 외부 호출을 더하지 마라). 빠진 조건의 계산과 사례를 고르는 방법은 check.py에 넣어, 재실행 때 지금 제공 자료에서 사례를 다시 고르고 기대 결과를 다시 계산하게 하라(없으면 '없음'). 레코드마다 판정이 있으면 ID와 판정을 verify/checker_N/rows.csv로 저장하라(csv.writer에 lineterminator='\n'). check.py는 실행할 때 항목 값(가정별 값 포함)과 읽은 행 수, 결과가 갈래로 나뉘면 갈래별 건수(0건 포함), 정의에 빠진 조건과 구별 사례(없으면 '없음')만 출력하고 행별 결과는 rows.csv·assumption_diff.csv에만 써라. 그 밖의 파일은 만들지 마라. 정의가 두 가지로 읽히면 네가 고른 해석과 다른 해석을 표 아래에 적어라. 결과가 갈래(범주·구간·등급 등)로 나뉘면 갈래마다 건수를 세고, 0건인 갈래는 지금 해당이 없는 것인지 이번 입력으로는 평가할 수 없는 조건(필요한 대상·열·기간이 데이터에 없음)인지 적어라. 기준은 고치지 마라. 오류가 나면 그 항목에 오류를 적고 나머지를 계속하되, 오류·미실행 항목이 있으면 check.py는 0이 아닌 코드로 끝내라. 중간 보고나 질문은 보내지 말고 끝났을 때 결과만 돌려줘. 돌려줄 것: 항목 | 값 | 계산 방법 한 줄 | 실행한 명령 | 읽은 행 수(0건이면 '검사 0건'), 그리고 가정 | 다른 안 | 바뀐 건수·ID 세 개·값·판정, 갈래가 있으면 갈래 | 건수 | 0건이면 이유, 정의에 빠진 조건 | 원문 위치·적용 범위 | 조건 넣은 값(못 계산하면 이유), 구별 사례 위치 | 기대 결과 | 어느 검사."
- 최종 결과를 이미 받았으면(알림·메시지 포함) 기다리지 않고 쓴다. 아직이면 `wait_agent`를 넉넉한 대기 시간(예: timeout_ms 600000)으로 한 번 부른다(짧게 되풀이하지 않는다). 받은 뒤 `python3 verify/checker_N/check.py`를 이번에 직접 한 번 더 실행해 같은 값이 나오는지 본다.
- 새 에이전트를 쓸 수 없으면 직접 한다. 이때도 구현 코드를 import하지 않고, 원본을 따로 읽는 스크립트를 verify/checker_N/에 만든다.

## 3. 행 대조
- 입력 행이 결과 쪽(쓴 것, 뺀 것, 따로 둔 것)으로 나뉘면 작업 폴더 맨 위에서 `python3 .harness/tools/reconcile.py`를 실행한다(사용법 `--help`). 종료 코드 0은 일치, 1은 불일치, 2는 검사 0건, 3은 실행 오류다. 차이는 메우지 않고 원인 미상 건수로 둔다.
- 결과가 화면에만 있으면, 2번이 끝난 뒤 판정 함수를 직접 불러 결과를 /tmp/result_N.json으로 만들어 `--group /tmp/result_N.json:<ID 열>:<판정 열>`로 대조한다. 결과 사본은 작업 폴더에 두지 않는다.

## 4. 보여 줄 것
| 항목 | 구현 값 | 검증 값 | 같음/다름 | 실행한 명령 |
- 이 표를 verify/report_N.md에 저장한다. 보고의 건수·통과 문구는 이번 실행 결과에서 만든다. 0번의 curl_check 실행 결과(명령·시각·종료 코드, '미실행' 줄)와 '미확인 장면'도 이 파일에 적는다.
- 레코드마다 판정이 있으면 verify/checker_N/rows.csv와 구현의 레코드별 결과를 ID로 맞춰, 다른 ID 전체를 verify/diff_N.csv(ID, 구현, 검증)로 저장한다.
- 다르면 차이 나는 건수 전체와, 원인을 먼저 볼 ID 세 개와 원인 후보를 적는다(셋은 먼저 볼 순서일 뿐이고 전체는 diff 파일에 있다). 새 에이전트가 적은 다른 해석도 함께 보인다. 정의가 달라서 생긴 차이면 담당자에게 물을 질문 한 줄을 붙인다.
- '정의에 빠진 조건'이 있으면 표 맨 위에 조건·원문 위치·두 값(정의대로/조건 넣음)을 보인다. 그 조건이 확정 원문(README·담당자 답)에 있으면 구현 결과를 그 조건으로 직접 대조해 다를 때만 구현 차이로, 같으면 정의(메모) 누락으로 적고 다시 묻지 않는다. 해석이 갈리거나 출처가 충돌하면 담당자 질문 한 줄을 쓴다. 구별 사례는 그 입력(묶음)의 구현 결과를 직접 확인해 표에 넣는다(상태 변경·외부 호출 제한은 그대로).
- 가정을 달리했을 때 핵심 값·대상·순서·판정·문장이 바뀌면 같음이어도 표 맨 위에 '가정 | 다른 안 | 바뀐 것과 건수'를 보인다. 그 가정이 협업 기록의 담당자 원문에서 그 대상·조건까지 확정됐는지 확인한다. 내 해석이면 지금 보낼 질문 한 줄을 쓰고 '미확인'으로 남긴다. 같은 대상·조건에 이미 답했거나 '기준 없음'으로 맡긴 것은 다시 묻지 않는다. 이번 입력으로는 평가할 수 없는 결론·갈래(조건에 필요한 대상·열·기간이 데이터에 없는 등)가 있으면 같은 자리에 그것과 이유를 보이고, 담당자가 이미 알고 답한 것이 아니면 물을 질문 한 줄을 쓴다. 단지 해당 사례가 없는 0건은 문제로 보지 않는다. 바뀐 것이 없으면 그렇다고 한 줄로 쓴다.
- 모두 같으면 '담당자 결과 확인' 한 줄을 협업 기록 '보낼 질문' 절에 쓴다(이미 보냈고 결과가 그대로면 다시 쓰지 않는다): 대표 사례 한 건을 담당자가 알아보는 말로(ID는 괄호) 그 입력·실제 결과·합의 기준의 구현값·남은 제한을 보이고(비율은 모수와 함께, 결정과 무관한 내부 수치는 제외), 담당자가 업무에서 확인할 수 있는 사실 하나만 묻는다(예: 이 건의 결과가 업무에서 맞는 값인지. 전체 결과나 구현의 승인은 묻지 않는다). 받은 답은 그 사례에만 적용하고 다른 결과·구현의 확인으로 넓히지 않는다. 이 절에서 생긴 담당자 질문도 같은 절에 한 줄에 결정 하나씩 쓴다(협업 기록에 '한 번에 n개'가 있으면 n개까지, 나머지는 확인표 '질문' 행으로). report_N.md 맨 위에는 '담당자에게 보낼 질문'으로 그 줄들의 요지를 적는다(없으면 '없음'. 사용자가 보냈다고 한 줄만 '답 대기'). 받은 답은 주고받은 내용을 그대로 붙여 넣게 안내한다.

## 5. 커밋
- 결과가 같든 다르든 verify/curl_check.sh(만들었으면), verify/checker_N/check.py, verify/report_N.md를 커밋한다(verify/spec_N.md는 처음 한 번, 그 뒤로는 내용이 바뀐 때만). 차이가 있거나 지난 verify/diff_N.csv를 고쳐 썼으면 그 파일도, '보낼 질문' 절을 고쳤으면 COLLAB.md도 같은 커밋에 넣는다(계획 문서의 완료 줄은 6번에서 따로 커밋한다). checker의 rows.csv·assumption_diff.csv, 서버 응답·결과 사본·로그는 넣지 않는다. 메시지 예: "test(verify): 핵심 결과 3개 독립 계산 일치" 또는 "test(verify): 2개 불일치 기록, 고치지 않음"

## 6. 끝에
- 미실행·차이·미확인 장면과, 사용자가 고를 때 본 숫자(결정 기록의 그 선택 줄)가 이번 검증 값과 다르면 바뀐 값(전→후. 그 줄에 숫자가 없으면 '선택 당시 값 미확인')을 먼저 알리고, '보낼 질문' 절에 새 줄이 있으면 복사해 보내라고 알린다. 끝나면 결정 기록에 'verify 완료: <기준 커밋>' 한 줄을 적어 커밋한다. 그다음 안내는 아래 세 갈래 중 하나다(모두 5번 커밋 뒤에. 요청에 'wrapup 수정 확인'이 있으면 갈래와 상관없이 `/new` → `$wrapup 해 줘`. wrapup은 바뀐 항목만 다시 한다. 차이·미실행·미확인 장면이 남았으면 안내 문장에 report_N.md 경로와 먼저 처리할 것을 넣는다. 새 대화는 이 보고를 따로 읽지 않는다).
  - 시간 기준점의 기능 동결 뒤면: `/new`와 AGENTS.md 순서로 완료 줄이 없는 다음 스킬 문장.
  - 동결 전이고 계획에 남은 개발 단계가 있으면: `/new`와 남은 단계를 이어 갈 문장 하나(화면을 만들거나 고치는 단계면 `$screen `을 앞에 붙여).
  - 동결 전인데 남은 개발 단계가 없으면(최종 verify·마감·제출 단계만 남은 것도 같다): 동결까지 남은 분(`date`)과 그 안에 고르기·답·수정·재검증·기록까지 끝낼 수 있는 후보를 셋 이내로 보이고 같은 대화에서 사용자가 고르게 한다.
    - 후보 출처: 이 보고의 미구현·차이·부분·미실행·미확인 항목(남은 조건을 확인하거나 빠진 구현을 고칠 일. 권한·환경이 그대로라 할 수 없는 것은 권하지 않고 필요한 조건만 적는다), 개발 시작 메모 항목에 닿는데 계획에서 뺀 것(담당자와 빼기로 합의한 것은 담당자 답 없이 다시 넣지 않는다), 결과를 바꾸는 '답 대기'·'가정'(담당자 질문으로), 결정 기록에 남은 앞선 후보 중 아직 안 한 것(버리기로 정한 것은 빼고), `EXPLAIN.md` 단계별 '약한 곳과 생길 일' 중 요구·합의 범위 안에서 고칠 수 있는 것(새 기능은 아니다). README 필수 문장·담당자 확정 답에 닿는 것을 먼저 두되 결과 영향과 끝낼 수 있는지로 고른다. 출처마다 해당이 없으면 '없음'이라 적고, 셋에 못 넣은 후보는 이름만 한 줄로 적는다.
    - 후보마다 닿는 메모 항목과 예상 분(비슷한 지난 단계가 실제 걸린 분과 이번 verify 분)을 붙이고, 필수 문장·확정 답에 닿는 후보에는 두었을 때 쓰는 사람에게 생기는 일을 한 줄 붙인다.
    - 고르면 `date`로 다시 재어 동결 전에 끝낼 수 있을 때만 그 단계를 계획 문서에 적고(화면을 만들거나 고치면 단계 이름 끝에 `$screen`), 이유와 고르지 않은 후보 이름(필수 요구면 그 상태와 영향도)을 결정 기록에 '사용자 결정'으로 적어 커밋한 뒤 `/new`와 그 단계 문장(이름에 `$screen`이 있으면 앞에 `$screen `을)을 안내한다. 수정은 그 새 대화의 단계에서 한다.
    - 후보가 없거나 사용자가 마감을 고르거나 시간이 모자라면 `/new` → `$wrapup 해 줘`를 안내한다.
