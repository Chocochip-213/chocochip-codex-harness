# verify: 다른 눈으로 다시 확인

0~5번을 이어서 한다(0번에서 이 턴을 끝내라고 한 경우만 빼고). 결과는 모두 이번에 실행한 명령과 출력(종료 코드·건수)으로 보인다. 이번에 돌리지 않은 것은 '미실행'이라고 쓴다. 사용자가 "고쳐 줘"라고 하기 전에는 고치지 않는다. N은 이번 검증 번호다(verify/checker_*가 몇 개 있는지 + 1).

## 0. 웹 서비스면 서버부터 (새 에이전트를 띄우기 전에)
- 서버는 사용자가 켠다. 이 스킬은 서버를 켜거나 끄지 않는다.
- 확인할 요청을 verify/curl_check.sh 한 파일에 모은다. 샌드박스에서는 요청마다 승인이 필요할 수 있어 한 번에 돌리려는 것이다.
  - 맨 앞은 이렇게 쓴다:
    ```bash
    #!/usr/bin/env bash
    B="${1:-<사용자가 알려 준 서버 주소>}"
    if ! curl -sS --noproxy '*' -m 5 -o /dev/null "$B/"; then
      echo
      if [ -n "${CODEX_SANDBOX_NETWORK_DISABLED:-}" ]; then echo "응답 없음: 샌드박스가 네트워크를 막았을 수 있음(승인받아 다시 실행)"; exit 2; fi
      echo "서버 응답 없음"; exit 3
    fi
    ```
  - 이어서 요구에 나온 화면마다 본문과 그 화면이 받는 결과 JSON을 /tmp/screen_last/ 폴더에 파일로 저장한다(마감 검토가 사용자에게 보이는 화면을 읽을 때 쓴다).
  - 그다음 코드에서 뽑은 라우트마다 정상 요청을 한 번 보내 한 줄에 `상태코드 메서드 경로`를 출력한다(`curl -sS --noproxy '*' -m 10 -o /dev/null -w "%{http_code}"`). 입력을 받는 라우트만 경계 입력과 잘못된 입력을 한 번씩 더 보낸다. 숫자를 돌려주는 라우트는 본문도 출력한다.
  - 상태를 바꾸는 요청(저장·승인 등)이 있으면: 보내기 전에 상태 파일이 든 폴더째(DB면 -wal·-shm·journal 포함) verify/state_backup/에 복사하고, 같은 요청을 두 번 보내 두 결과를 출력하고, 폴더째 되돌린 뒤 "상태를 바꾸는 요청을 보냈으니 서버를 다시 켜야 함"을 출력한다. 상태가 작업 폴더 밖(외부 DB 등)에 있거나 어디인지 모르면 그 라우트는 보내지 않고 "미실행: <사유>"를 출력한다.
- `bash verify/curl_check.sh`는 처음부터 승인을 받아(샌드박스 밖에서) 실행한다. 뒤에 리다이렉트나 파이프를 붙이지 않는다(사용자가 승인 창에서 '다시 묻지 않기'를 고르면 다음부터 그대로 통과한다). 승인을 받을 수 없으면 사용자에게 shell 탭에서 칠 명령 한 줄을 주고 이 턴을 끝낸다(사용자가 출력을 붙여 넣으면 그 출력으로 이어서 한다).
  - 승인 없이 돌려 종료 코드 2가 나오면: 승인을 받아 한 번 더 실행한다.
  - 승인받아 실행했는데도 종료 코드 2나 3(응답 없음)이면: 서버를 켜는 명령 한 줄을 알려 주고 이 턴을 끝낸다.
  - 서버가 지금 코드로 도는지: 서버 응답의 핵심 숫자(건수 등)를 판정 함수를 직접 불러 얻은 값과 비교한다. 다르면 옛 코드가 돌 수 있으니 다시 켜 달라고 하고 이 턴을 끝낸다. 다시 켠 뒤에도 다르면 옛 코드 문제가 아니니 그 차이를 4번 표에 넣는다.
- 상태 코드: 200 정상, 400 입력 거절, 404 라우트 없음, 500 버그, 000 응답 없음. 200이어도 본문이 틀릴 수 있으니 숫자 본문은 4번에서 검증 값과 비교한다.

## 1. 확인할 숫자 고르기
- 사용자가 꼭 맞아야 할 숫자나 예상값을 말했으면 그것부터 넣고, 예상값과 다르면 표에 함께 보인다. 결과(서버 응답 본문, 출력 파일, 판정 함수를 직접 부른 결과)에서 사람이 바로 쓰는 숫자·결과를 모두 합쳐 적어도 세 개 고른다(예: 핵심 결과, 전체 건수나 합계, 특정 입력 하나의 처리 결과). 담당자 결정에 쓰이는 숫자가 더 있으면 그것도 넣는다. 고르지 못한 숫자는 '확인 못 한 숫자'로 적는다.
- 숫자마다 정의를 한 줄로 쓴다(대상, 기간, 포함·제외, 단위). 정의는 README, 담당자 답, 개발 시작 메모의 말로 쓰고 구현 코드나 결정 기록에서 옮기지 않는다.
- 개발 시작 메모의 가정(사용자 결정·기본값) 중 핵심 결과를 바꿀 수 있는 것을 세 개 이내로 고르고, 가정마다 다른 안을 한 줄로 쓴다. 다른 안은 그 가정을 정할 때 함께 본 다른 선택지로 하고, 빈 값이 있는 건을 보류·제외한 가정이면 확인된 값만으로 결과가 정해지는 건을 판정하는 안으로 한다.
- 구현 값은 대화에만 적는다. 새 에이전트의 결과를 받기 전에는 파일로 쓰지 않는다(새 에이전트가 볼 수 있어서).

## 2. 새 에이전트에게 따로 계산시키기
- 다시 부를 때 계획 문서의 개발 시작 메모와 '합의 뒤 변경'이 지난 verify/spec_N.md와 같고 1번에서 고른 숫자와 가정이 지난 check.py에 다 있으면 새 에이전트를 띄우지 않는다. 지난 `verify/checker_N/check.py`만 다시 실행해 3번으로 간다(같은 계산을 되풀이하지 않는다).
- 계획 문서의 '개발 시작 메모' 절(뒤에 붙은 '합의 뒤 변경' 포함)과 담당자 확인 기록을 그대로 verify/spec_N.md에 옮긴다. 결정 기록과 구현 값은 옮기지 않는다.
- `spawn_agent`로 새 에이전트를 띄운다. `task_name`은 `checker_N`, `fork_turns`는 `"none"`(지금까지의 대화를 넘기지 않는다). 메시지는 아래 틀을 채워 보낸다.
  "너는 검증을 맡은 하위 에이전트다. AGENTS.md의 결정 기록·커밋·행 대조 규칙은 이 일에 적용하지 않는다. 읽을 것은 README, verify/spec_N.md, 데이터 <경로>뿐이다. 계획 문서, 구현 코드(<구현 폴더·파일>), 출력 파일, tests/, git 기록, verify/의 다른 파일은 열지 않는다. 파일은 verify/checker_N/ 아래에만 만든다. 다시 계산할 것: <숫자마다 정의 한 줄>. 가정을 바꿔 한 번 더 계산할 것: <가정 | 다른 안>(가정마다 핵심 결과에서 들어가고 빠지는 ID를 적어라). 원본을 csv·json·sqlite3 같은 표준 라이브러리로 직접 읽어 계산하는 스크립트를 verify/checker_N/check.py로 저장해 실행하고, 검사마다 '구현이 어떻게 틀리면 이 검사가 잡나'를 주석 한 줄로 적어라. 레코드마다 판정이 있으면 ID와 판정을 verify/checker_N/rows.csv로 저장하라(csv.writer에 lineterminator='\n'). 그 밖의 파일은 만들지 마라. 정의가 두 가지로 읽히면 네가 고른 해석과 다른 해석을 표 아래에 적어라. 오류가 나면 그 항목에 오류를 적고 나머지를 계속하라. 돌려줄 것: 항목 | 값 | 계산 방법 한 줄 | 실행한 명령 | 읽은 행 수(0건이면 '검사 0건'), 그리고 가정 | 다른 안 | 바뀐 ID."
- 결과는 `wait_agent`로 기다린다. 받은 뒤 `python3 verify/checker_N/check.py`를 이번에 직접 한 번 더 실행해 같은 값이 나오는지 본다.
- 새 에이전트를 쓸 수 없으면 직접 한다. 이때도 구현 코드를 import하지 않고, 원본을 따로 읽는 스크립트를 verify/checker_N/에 만든다.

## 3. 행 대조
- 입력 행이 결과 쪽(쓴 것, 뺀 것, 따로 둔 것)으로 나뉘면 작업 폴더 맨 위에서 `python3 .harness/tools/reconcile.py`를 실행한다(사용법 `--help`). 종료 코드 0은 일치, 1은 불일치, 2는 검사 0건, 3은 실행 오류다. 차이는 메우지 않고 원인 미상 건수로 둔다.
- 결과가 화면에만 있으면, 2번이 끝난 뒤 판정 함수를 직접 불러 결과를 /tmp/result_N.json으로 만들어 `--group /tmp/result_N.json:<ID 열>:<판정 열>`로 대조한다. 결과 사본은 작업 폴더에 두지 않는다.

## 4. 보여 줄 것
| 항목 | 구현 값 | 검증 값 | 같음/다름 | 실행한 명령 |
- 이 표를 verify/report_N.md에 저장한다.
- 레코드마다 판정이 있으면 verify/checker_N/rows.csv와 구현의 레코드별 결과를 ID로 맞춰, 다른 ID 전체를 verify/diff_N.csv(ID, 구현, 검증)로 저장한다.
- 다르면 차이 나는 건수 전체와, 원인을 먼저 볼 ID 세 개와 원인 후보를 적는다(셋은 먼저 볼 순서일 뿐이고 전체는 diff 파일에 있다). 새 에이전트가 적은 다른 해석도 함께 보인다. 정의가 달라서 생긴 차이면 담당자에게 물을 질문 한 줄을 붙인다.
- 가정을 바꾼 계산에서 핵심 결과의 ID가 바뀌었으면 같음이어도 표 아래에 '가정 | 다른 안 | 바뀐 ID와 건수'를 보이고, 담당자에게 확인할 질문 한 줄을 붙인다. 바뀐 것이 없으면 그렇다고 한 줄로 쓴다.

## 5. 커밋
- 결과가 같든 다르든 verify/spec_N.md, verify/curl_check.sh, verify/checker_N/check.py, verify/report_N.md만 커밋하고, 차이가 있으면 verify/diff_N.csv도 넣는다(checker의 rows.csv, 서버 응답·결과 사본·로그는 넣지 않는다). 메시지 예: "test(verify): 핵심 결과 3개 독립 계산 일치" 또는 "test(verify): 2개 불일치 기록, 고치지 않음"
