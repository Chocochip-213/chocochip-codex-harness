# screen: 읽히는 업무 화면

이 글이 스킬 전문이다. 전문이 현재 문맥에 있으면 이 SKILL.md를 다시 열지 않고, 없거나 불확실하면(자동 압축 뒤 등) 다시 읽는다. 화면 구현 지침이며 단계 보고·기록은 AGENTS.md를 따른다.

## 0. 범위
- 과제에 기존 화면·부품·스타일이 있으면 먼저 따르고 필요한 부분만 고친다. 화면 방식과 도표 도구는 계획 때 `.harness/LIBS.md` 웹 행·'표·차트' 행에서 고른 것을 쓴다.
- 목표는 운영에서 매일 쓰는 사람이 쓰기 좋은 화면이다(채점자도 실제 화면을 열어 본다). 화면을 다듬는 일로 업무 규칙·계산 결과·권한·저장/적용 동작을 바꾸지 않는다(그것을 만들거나 고치는 일은 계획 단계대로 한다). 새 업무 기능·화면 기능은 AGENTS.md대로 묻고, 패키지는 `.harness/LIBS.md`대로 고른다. 스타일·배치·가독성을 다듬는 것은 새 기능이 아니다.
- 승인된 정보의 요약·이름표·묶음·배치 조정과, 쓰는 사람이 그 정보를 찾고 견주는 데 필요한 정렬·필터·쪽 이동·검색은 화면 작업에 든다(승인된 데이터·권한 안에서 하는 것. 데이터가 커서 서버가 나눠 보내야 하면 서버에서 한다. '화면 기능'은 새 데이터·권한·저장/적용 동작이다). 새 판정 기준이나 지표는 만들지 않는다.
- 값을 숨기거나 바꿔 달라는 요청(사용자 요청 포함)은, 그 값이 README·메모가 그 화면에 요구한 표시면 지우지 않고 읽기 쉬운 꼴로 바꾼다.
- 화면을 처음 만들 때 역할마다 '찾을 답 / 읽을 근거 / 현재 상태 / 다음 행동'을 한 줄씩 정해 스타일 파일 맨 위 주석에 둔다(별도 승인·비교 단계는 만들지 않는다).
- 실제 데이터의 짧은 값·긴 값·빈 결과를 보고 배치한다. 임시 문구만으로 설계하지 않는다.

## 1. 읽는 순서
- 결과가 있으면 역할의 핵심 답과 현재 상태를 먼저 보인다. 없으면 필요한 선행 행동을 먼저 보인다.
- 조작·근거·보조 정보는 업무 흐름 순서로 뒤에 둔다. HTML 순서가 좁은 화면의 읽는 순서다.
- 요약은 승인된 데이터와 범위에서만 만들고, 전체·필터 결과·현재 쪽의 건수를 구분해 표시한다.
- 이름·상태·시각·숫자는 쓰는 사람이 판단할 말과 단위로 쓰고, 원래 값과 표시 문자열을 분리한다. 업무에서 쓰는 식별번호와 핵심 근거는 화면에 남기고(줄바꿈은 되지만 hover·title에만 숨기지 않는다), 추적용 해시·내부 버전·정밀 시각은 보조 위치에 둔다.
- 지금 보는 결과와 실제 반영된 상태가 다르면 결과 가까이에 구별해 쓴다. 조건·기준 시점도 함께 읽히게 한다.

## 2. 폭과 배치
- 사람이 실제로 여는 폭에 맞춘다(README·담당자 답·사용자가 말한 미리보기 폭. 모르면 `ui_check.py`의 기본 폭 둘). 모바일 폭은 README·담당자·사용자가 말했을 때 넣는다.
- 좁은 폭은 한 열이 기본이다. 넓은 폭에서는 읽을 공간이 있는 묶음(조건과 결과, 요약과 표 등)을 나란히 두고, 좁아지면 한 열로 접는다.
- 페이지를 밀어내는 고정 최소폭을 피한다. 줄어들어야 하는 grid·flex 자식은 `min-width:0`, 가변 열은 `minmax(0,1fr)`, 조작 묶음은 줄바꿈한다.
- 표가 주 작업이면 넓은 영역을 준다. 가로 스크롤은 표·도표 안에만 두고 제목·필터·쪽 이동은 밖에 둔다.
- 페이지 `overflow:hidden`이나 글자 축소로 잘림을 감추지 않는다. 긴 기술 문자열만 `overflow-wrap:anywhere`로 꺾고 일반 문장은 그대로 둔다.

## 3. 표현
- 고른 방식의 체계(프레임워크면 그 부품·변수, 직접 쓰는 CSS면 `:root`의 색·글자·간격 토큰 한 곳)로 쓰고, 과제의 업무와 쓰는 사람에 맞는 색·글꼴·밀도를 정해 모든 화면에 같게 둔다. 업무 구조를 스타일 체계에 맞추지 않는다.
- 외부(CDN) 파일을 쓰면 첫 화면 점검 때 실제 미리보기에서 읽히는지 보고, 막히면 받아서 정적 폴더에 둔다.
- 본문은 16px 안팎에서 시작하고 글자와 바탕 대비는 4.5:1 이상. 크기·굵기·간격으로 순서를 드러내고 주 동작 하나만 강조한다. 상태는 말과 색을 함께 쓴다.
- 표는 업무상 중요한 열(대상·판정·근거)부터 두고, 숫자는 오른쪽 정렬·`tabular-nums`, 단위와 날짜 형식은 한 가지로. 큰 목록은 계획에 있는 필터·쪽 나누기로 서버에서 나눠 보낸다.
- 입력에는 label, 오류에는 원인과 고치는 법(위치 정보가 있으면 함께). 버튼 글자는 동작 이름. 버튼·표는 `<button>`·`<table>` 같은 시맨틱 요소로 만들고(모양은 고른 화면 방식대로 꾸민다) `:focus-visible`을 지우지 않는다.
- 데이터를 보이는 곳마다 비어 있음·처리 중·오류·완료와 행동 뒤 결과를 구별한다. 지난 결과에는 언제·어느 입력의 결과인지 붙인다.
- 도표는 판단에 필요한 것부터 강조하고, 중요한 값·근거는 글이나 표로도 읽히게 한다. 계산으로 정해지는 표시는 계산 함수가 낸 값만 그린다(도구는 `.harness/LIBS.md` '표·차트' 행).

## 4. 확인과 종료
- curl로 응답·권한·데이터를 확인한다. 이것으로 배치가 확인됐다고 하지 않는다.
- 화면을 실제로 눌러 보는 확인(브라우저 스크립트 포함)에도 AGENTS.md의 사본 규칙을 적용한다: 저장·적용처럼 업무 상태를 바꾸는 흐름은 사본 서버(verify 스킬 0절의 정의대로 저장 파일·DB까지 복사해 다른 포트에, 로그·PID는 /tmp/server_copy.*)에서 확인한다.
- 실제 모양은 두 때에 본다: ① 첫 주요 화면이 실제 데이터로 동작했을 때(주 역할, 실제 폭과 넓은 폭. 서버를 (다시) 띄운 뒤 같은 턴에서 본다) ② 제출 전(wrapup)에 다른 역할의 첫 화면과 바뀐 화면, 빈 결과·오류는 대표 사례 하나. 그 밖에는 새로 만들거나 배치·상태를 바꾼 주요 화면(그 단계에서 서버를 다시 띄운 뒤), 사용자가 고쳐 달라고 한 화면, '남은 문제'가 적힌 화면.
- 명령: `<파이썬> .harness/tools/ui_check.py <주소> --out /tmp/ui_check/<화면 이름>` (`<파이썬>`은 Playwright가 설치된 파이썬: 프로젝트 가상환경이 있으면 그것(예: `.venv/bin/python`), 없으면 `python3`. 설치와 복구도 같은 파이썬으로 한다(도구 안내의 `python3`도 이것으로 바꿔 쓴다). `--widths`에 실제 폭, 목표 화면에 비밀번호 칸이 있으면 `--ready`에 그 화면에만 있는 요소, 로그인은 앱의 정상 로그인 폼을 `--login-url`과 환경변수 이름으로(값은 실행 안내의 환경 파일에서 읽어 넘기고 명령줄에 쓰지 않는다), 사용법 `--help`. 설치와 실행은 지금 권한에서 네트워크가 막혀 있으면(샌드박스면 대개 막힌다) 승인을 받아 샌드박스 밖에서). PNG는 이미지 보기 도구로 열어 보고 report.json의 넘침·잘림·이름표 수와 예시 요소를 함께 읽는다. 찍었다고 본 것이 아니다.
- 회차마다 아래 넷에 답을 적는다(도구의 '배치 문제 0건'은 배치만의 결과이고 글자 내용은 재지 않는다): 이 역할이 찾는 답이 보이나 / 근거를 읽을 수 있나 / 현재 상태와 다음 행동을 혼동하지 않나 / 판단할 말 대신 내부 코드·영문 식별자(상태 코드·열거값·해시·열 이름)·정밀 시각·단위나 자릿수 구분이 없는 수가 그대로 보이는 곳이 있나(1절·3절의 표시 규칙대로. PNG와 그 화면의 curl 본문 글자를 실제로 읽고 '없음' 또는 '있음(무엇이 어디에)'으로 적는다) / 이를 막는 문제(큰 것부터). 지금 작업이 코드 수정을 허용하면 다음 시간 기준점(기본판·중간 검증·동결·제출 시작 시각 중 다음 것) 전에 끝나게 큰 것부터 관련 HTML·CSS로 고치고 같은 역할·상태·폭에서 다시 본다(수정 선택을 기다리는 작업이면 고칠 후보로만 낸다). 답·근거·상태·다음 행동이 읽히면 끝이고, 못 고친 것은 '남은 문제'로 적어 다음 화면 작업 때 먼저 본다. 확인된 기능은 다시 쓰지 않는다.
- 시간: 도구 설치 시도는 3분까지(안 되면 같은 원인이 그대로인 동안은 다시 시도하지 않고 아래 대신하는 방법으로). 점검·수정은 다음 시간 기준점까지 남은 시간 안에서 하고, 모자라면 큰 문제만 고치고 나머지는 '남은 문제'로 적는다.
- 도구가 안 되면: 프로젝트에 이미 있는 브라우저 테스트로 같은 역할·주소·상태·폭을 찍을 수 있으면 그 이미지를 열어 위 확인을 대신한다. 그것으로도 보지 못하면 그 원인을 결정 기록 '화면 점검' 줄에 적고(원인이 그대로면 뒤 대화도 다시 시도하지 않는다), 사용자에게 실제 주소·폭·역할로 열어 어느 영역이 어떤 폭에서 어떻게 보이는지 말해 달라고 하고, 그동안 코드에서 구조·줄바꿈·고정 최소폭과, 판단할 말 대신 원래 값(상태 코드·해시·영문 열거값·정밀 시각)이 본문에 그대로 나오는 곳을 점검한다. 배치는 '미확인'이다.
- 본 역할·주소·상태·폭, 본문 글자에서 본 내부 값(없음/있음과 무엇), 남은 문제를 단계 보고와 결정 기록에 '화면 점검' 한 줄로 남긴다. ①을 마친 단계 보고의 `/new` 안내 앞에는 사용자에게 실제 주소·폭·역할로 실제 한 건을 처음부터 끝까지 따라가 보고 읽기 어렵거나 이상한 곳을 `/new` 뒤 첫 문장에 다음 단계 요청과 함께 말해 달라고 한 줄로 청한다(안 보겠다고 하면 그대로 진행한다). 사용자가 Browser에서 본 것을 말하면 '사용자 확인'으로 같은 자리에 적고 고칠 후보로 삼는다. 보지 못한 화면은 확인했다고 쓰지 않는다. 로그인 상태 파일과 PNG는 커밋하지 않는다.
