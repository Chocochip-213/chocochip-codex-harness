# weakness: 남은 한계와 한 화면 요약

코드는 고치지 않는다. 실제 코드와 데이터에 근거한 것만 쓰고, 모르면 "확인 못 함"이라고 쓴다. 사용자가 이 작업을 남에게 설명할 때 코드와 다른 말을 하지 않게 하는 것이 목표다.

## 1. 남은 약점 (파급이 큰 순서로, 열 개 이내, 대화에만)
| 위치(파일·함수) | 어떤 입력·상황에서 | 생기면 무슨 일이 나나 | 다음에 확인하거나 고칠 것 |
- 이미 고친 것은 넣지 않는다. 고치지 못한 이유(범위 밖, 시간, 담당자 확인 못 함)를 '어떤 입력·상황에서' 칸에 함께 적는다.
- 제출 문서의 '남은 한계' 절에 없는 항목만 그 절에 한 줄씩 추가하고 커밋한다.

## 2. 설명 노트를 지금 코드에 맞추기
- `EXPLAIN.md`의 줄마다 지금 코드와 맞는지 본다. 나중 단계에서 바뀐 함수 이름·기준·숫자는 그 줄을 고치고 끝에 '(나중에 바뀜: 무엇이 언제)'를 붙인다. 코드에 없는 기능을 말하는 줄은 지운다.
- 고친 줄 수를 한 줄로 알린다. EXPLAIN.md는 커밋하지 않는다.

## 3. 한 화면 요약 (`EXPLAIN.md` 맨 아래 '한 화면 요약' 절에 쓰고 대화에도 보인다)
- 구조: 입력 → 주요 함수 → 출력. 함수마다 파일 이름과 판정 규칙의 출처(담당자 답, README, 가정).
- 핵심 숫자: 이 과제의 결과를 설명할 때 쓰이는 것만 서너 개(과제에 있는 것만. 예: 전체 건수, 빠진 건수와 사유, 핵심 결과, 기준값, 다시 계산해 일치했는지). 숫자마다 나오는 곳(파일·함수 또는 명령).
- 약점 두 개: 1번 표의 위 두 줄을 '지점 → 왜 위험한지 → 다음에 확인할 것' 한 줄로.
- 버린 대안 하나와 이유, 일부러 만들지 않은 것 하나와 근거(담당자 합의, 요구 문장).
- 실제 입력 하나가 처음부터 결과까지 지나가는 길(ID나 값, 거치는 함수, 나오는 결과).
- 끝에 묻는다: 구조의 함수 중 설명하기 어려운 것이 있으면 고르게 하고, 고른 함수마다 하는 일·이렇게 만든 이유·틀리는 경우를 세 줄로 설명한다.

## 4. 사용자가 자기 말로 정리할 것 세 가지
- 사용자에게 아래 셋을 자기 문장으로 쓰게 한다. 내가 대신 쓰지 않는다.
  1. 부딪친 조건 하나와, 무엇을 반드시 지키고 무엇을 조정했는지
  2. 틀린 답을 내는 입력 하나와 그 이유, 고치지 못한 이유
  3. Codex에 맡긴 것과 사람이 직접 다시 확인한 것, 확인한 방법
- 사용자가 쓰면 실제 코드·기록과 다른 문장만 짚고, 고친 문장을 `EXPLAIN.md`의 '내 말로 정리' 절에 사용자 문장 그대로 둔다.

## 5. 점검 질문 (사용자가 시간이 있다고 할 때)
- 제출 문서, 결정 기록, 커밋 기록, `EXPLAIN.md`, 실제 코드를 보고 이 작업을 처음 보는 사람이 물을 만한 질문을 대여섯 개 만든다. 유형을 섞는다: 설계 이유, 동작 추적(실제 레코드 하나), 장애·예외(호출 실패, 빈 데이터, 이상한 값), 변경 영향(기준이 바뀌거나 데이터가 커지면), 약점·한계, 검증 근거, Codex에 맡긴 것과 사람이 바꾼 것, 범위(만들지 않은 것). 그중 하나는 전제가 실제 구현과 다른 질문으로 낸다.
- 한 번에 하나만 낸다. 사용자가 자기 말로 답하면 세 가지만 짚는다: 실제 코드와 다른 문장(실제로는 어느 파일·함수가 무엇을 하는지), 위치를 짚었는지, 위치·숫자 없는 일반론 문장. 답을 대신 써 주지 않는다.
- 다름이 나온 질문은 결정 기록에 한 줄 남긴다.

## 끝에 알려 줄 것
- 제출 문서의 '남은 한계' 절은 사용자가 직접 읽을 곳이라는 것. 고칠 말을 알려 주면 그대로 반영한다.
- 설명하는 순서: 결론(파일·함수) → 이유(담당자 말·데이터) → 약점과 파급 → 확인한 것과 다음 검증.
