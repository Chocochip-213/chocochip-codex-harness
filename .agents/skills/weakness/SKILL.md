# weakness: 남은 한계와 한 화면 요약

이 글이 스킬 전문이다. 전문이 현재 문맥에 있으면 이 SKILL.md를 다시 열지 않고, 없거나 불확실하면(자동 압축 뒤 등) 다시 읽는다.
코드는 고치지 않는다. 실제 코드와 데이터에 근거한 것만 쓰고, 모르면 "확인 못 함"이라고 쓴다. 사용자가 이 작업을 남에게 설명할 때 코드와 다른 말을 하지 않게 하는 것이 목표다.

사용자가 점검 질문만 요청하거나(예: "점검 질문 6개 줘") 시간이 없다고 하면 0~3번과 끝 안내를 건너뛰고 4번만 하되, 끝 안내의 '마지막 verify 뒤 바뀐 것' 한 줄과 비워 둔 사람 몫 칸 한 줄은 질문 앞에 대화로 적는다(파일은 고치지 않는다).

## 0. 사용자가 먼저 쓸 것 (아래 1~3번을 보이기 전에 받는다)
- 사용자에게 아래 넷을 자기 문장으로 먼저 쓰게 한다. 내가 대신 쓰거나 예시 답을 보이지 않는다. 이 턴은 요청만 하고 끝낸다.
  1. 부딪친 조건 하나와, 무엇을 반드시 지키고 무엇을 조정했는지
  2. 틀린 답을 내는 입력 하나와 그 이유, 고치지 못한 이유(모르면 '확인 못 함')
  3. Codex에 맡긴 것과 사람이 직접 다시 확인한 것, 확인한 방법
  4. 실제 입력(ID) 하나가 어떤 순서로 무엇을 거쳐 어떤 결과가 될지(내 예측. 함수 이름은 몰라도 된다), 그리고 설명하기 어려운 부분이 있으면 무엇인지와 내가 아는 만큼 한 줄
- 아무것도 못 쓰겠다고 하면 '사용자 문장 없음'이라고 적고 1번으로 간다.
- 받은 뒤 1~3번을 하며 사용자 문장과 코드·기록이 다른 곳만 쉬운 말로 짚는다(근거 파일:줄은 괄호로 붙이고, 사용자에게 코드를 열어 보라고 하지 않는다). '직접 했다·확인했다'는 문장은 결정 기록·검증 보고에 누가 실행한 것으로 남았는지와 맞춰 본다. 3번의 실제 입력 하나는 사용자가 고른 ID로 쓴다. 사용자 문장은 고친 것까지 `EXPLAIN.md`의 '내 말로 정리' 절에 그대로 둔다.

## 1. 남은 약점 (파급이 큰 순서로, 열 개 이내, 대화에만)
| 위치(파일·함수) | 어떤 입력·상황에서 | 생기면 무슨 일이 나나 | 다음에 확인하거나 고칠 것 |
- 찾는 법: 요구와 실제 입력 → 처리 → 결과를 대조해 결과가 틀리거나 요구를 못 지키는 지점을 찾는다. 가정으로 정한 판정 기준·데이터 처리(개발 시작 메모·결정 기록의 '가정'), 상태를 바꾸는 동작, 무거운 처리, 밖에서 들어오는 입력, 저장과 다시 켜기, 권한·공개 경계는 찾을 단서이고 그 밖의 약점도 본다. 찾은 지점이 서로 겹치거나(처리 도중 변경, 같은 요청 동시) 실패하거나 데이터가 커질 때 결과가 어떻게 되는지 본다. 이 산출물에 없는 종류는 채우지 않는다.
- 이미 고친 것은 넣지 않는다. 고치지 못한 이유(범위 밖, 시간, 담당자 확인 못 함)를 '어떤 입력·상황에서' 칸에 함께 적는다.
- 제출 문서의 '남은 한계' 절에 없는 항목만 그 절에 '지점(구성 요소·함수 이름) → 발생 조건과 파급 → 다음에 검증·개선할 것' 한 줄씩으로 추가하고, 결정 기록에 'weakness 완료: <기준 커밋>' 한 줄과 함께 커밋한다. 그 절이 사용자 자신의 서술을 요구하는 사람 몫 칸이면 거기에 쓰지 않고 대화로만 알린다(끝 안내의 '남은 한계' 한 줄도 같다).

## 2. 설명 노트를 지금 코드에 맞추기
- `EXPLAIN.md`에서 이후 변경과 관련된 줄만 지금 코드와 대조해, 숫자·함수 이름뿐 아니라 처리 규칙·결과·약점이 달라진 문장을 고치고(꼬리표는 붙이지 않는다) 없는 기능 설명은 지운다.
- 고친 줄 수를 한 줄로 알린다. EXPLAIN.md는 커밋하지 않는다.

## 3. 한 화면 요약 (`EXPLAIN.md` 맨 아래 '한 화면 요약' 절에 쓰고 대화에도 보인다)
- 전체 구조: 구성 요소(화면·서버·계산·저장 등)마다 맡은 일과 서로 주고받는 것을 한 줄씩, 그렇게 나눈 이유 한 줄.
- 흐름: 입력 → 처리 단계 → 출력. 단계마다 쉬운 말 한 줄과 판정 규칙의 출처(담당자 답, README, 가정)를 쓰고, 함수·파일 이름은 괄호로 붙인다.
- 핵심 숫자: 이 과제의 결과를 설명할 때 쓰이는 것만 서너 개(과제에 있는 것만. 예: 전체 건수, 빠진 건수와 사유, 핵심 결과, 기준값, 다시 계산해 일치했는지). 숫자마다 나오는 곳(파일·함수 또는 명령).
- 약점: 1번 표에서 파급이 큰 순서로 세 개까지(없으면 '확인된 약점 없음')를 '지점(구성 요소·함수 이름) → 발생 조건과 파급 → 다음에 검증·개선할 것' 한 줄씩으로. 후속 질문에 답할 때 이 이름과 모양을 그대로 쓴다.
- 핵심 처리(판정·계산 등)가 결과를 만드는 순서: 쉬운 말 3~5단계로, 실제 입력 하나(ID나 값)가 단계마다 무엇이 되어 어떤 결과가 나오는지(함수 이름은 괄호로). 이름 있는 방법(알고리즘·통계 기법 등)을 썼으면 그 이름, 일반 원리 두세 줄, 이 과제에 고른 이유, 대신 쓸 수 있던 방법 하나와 안 쓴 이유(재 보지 않았으면 그렇다고 쓰고, 실제로 비교한 안은 아래 '비교한 안'에만 쓴다), 잘 안 맞는 경우를 함께 쓴다.
- 비교한 안: 안마다 무엇을 바꿨나·핵심 숫자(재지 않았으면 '미측정')·고르거나 버린 이유 한 줄(결정 기록·제출 문서에서. 비교하지 않았으면 '없음'), 그리고 일부러 만들지 않은 것 하나와 근거(담당자 합의, 요구 문장).
- 0절에서 사용자가 어렵다고 한 부분은 사용자의 한 줄에서 틀린 곳만 짚는다. 못 쓰겠다고 한 부분만 하는 일·이렇게 만든 이유·틀리는 경우를 쉬운 말 세 줄로 설명한다.

## 4. 점검 질문 (AI 없이 답하는 후속 질문 연습)
- 제출 문서, 결정 기록, 커밋 기록, `EXPLAIN.md`, 실제 코드를 보고 이 작업을 처음 보는 리뷰어가 코드 리뷰하듯 실제 처리 지점을 짚어 물을 만한 질문을 만든다. 질문마다 위 자료에서 실제로 찾은 지점(약점·선택·숫자·구조 줄) 하나를 바탕으로 만들고, 그런 지점이 없는 종류는 내지 않는다. 일반적인 질문 목록으로 채우지 않는다. 개수: 사용자가 말한 수, 없으면 10개를 실전 후속 질문에 나올 만한 것부터 중요한 순서로 한 번에 낸다(남은 시간이 짧아도 줄이지 않는다. 몇 개를 풀지는 사용자가 앞에서부터 고른다). 질문을 내기 전에 커밋되지 않은 제출 변경이 있으면 제출 전에 할 일로 함께 알린다(질문은 그대로 낸다). 실제 제출을 앞두고 시간 기준점이 있으면 질문과 함께 제출 시작 시각을 알리고 그때는 답을 멈추고 제출로 넘어가게 한다(사용자가 연습이라고 했으면 이 시각 규칙은 쓰지 않는다). 같은 대화에서 이미 낸 질문은 다시 내지 않고, 아직 다루지 않은 종류부터 낸다. 종류는 이번 작업에 해당하는 것에서 섞는다: 핵심 동작과 그것을 확인한 방법, Codex 제안을 직접 확인하거나 고친 것과 이유, 비교한 안과 고른 이유, 데이터가 이어져 결과가 되는 흐름, 핵심 처리(판정·계산 등)가 결과를 만드는 순서, 장애·예외(호출 실패, 빈 데이터, 이상한 값)나 변경 영향, 전체 구조와 그렇게 나눈 이유, 쓴 방법(알고리즘 등)의 원리와 고른 이유, 운영에 쓸 수 있게 확인한 것(장애·데이터가 바뀔 때·다시 켤 때), 남은 한계, 지금 못 했지만 보완할 것과 그 순서, 범위(만들지 않은 것), 코드에 쓴 구현 방식·패턴 하나를 왜 그렇게 짰는지, 요구보다 무겁게 만든 부분이 있으면 왜 필요했는지. 함수 이름·파일 위치는 묻지 않는다. 전제를 일부러 틀리게 낸 질문은 만들지 않는다.
- 질문을 한꺼번에 내고 그 위에 답의 틀을 한 번 적는다: 결론(무엇이 언제 어떻게 되나) → 이유(담당자 말·데이터·숫자) → 확인(실제 실행 주체·방법·대상 환경을 기록대로 적고, 안 했으면 '미실행') → 약점은 '지점 → 발생 조건과 파급 → 다음에 검증·개선할 것'(약점·장애·한계·보완을 묻는 문항은 이 세 단계만). 문항마다 5분 안에 AI 없이 자기 말로 쓰게 한다. 답을 받기 전에는 답을 대신 써 주지 않는다. 답을 받으면 문항마다 짚는다: 실제 동작과 다른 문장(실제로는 무엇이 어떻게 되는지 쉬운 말로, 근거 파일:줄은 괄호로), 사례·숫자 없이 일반론으로 쓴 문장, 빠진 핵심(그 질문에 꼭 들어갈 이유나 숫자), 위 틀에서 빠진 단계, 그리고 '확인'이 결정 기록·검증 보고에 남은 실행 주체와 다른 문장. 지점은 한 화면 요약(없으면 제출 문서의 데이터 흐름·남은 한계)에 나온 구성 요소·함수 이름으로 말하면 된다(코드를 열 필요는 없다).
- 다름이 나온 질문은 결정 기록에 한 줄 남긴다.

## 끝에 알려 줄 것
- 다음에 보낼 말: `date`로 다시 잰다. 제출 시작 전이고 4번을 아직 안 했으면 점검 질문(사용자가 말한 수, 없으면 10개)을 권한다. 제출 시작까지 15분이 안 남았으면 `/new`나 다른 스킬은 권하지 않고, 제출 시작이 됐으면 같은 대화에서 '비워 둔 사람 몫 칸 확인 → 남은 한계 커밋 확인 → 제출'로 한다. 15분 넘게 남았으면 남은 분과 할 일 순서를 한 줄로 알린다: 결과를 바꾸는 미확인 기준(담당자 질문) → 제출 문서의 미실행 중 지금 할 수 있는 실제 사용 확인 → 비워 둔 사람 몫 칸·점검 질문. 기능은 더하지 않는다. 필수 결함 수정은 관련 검증·문서·커밋까지 제출 시작 전에 끝날 때만 하고, 답이나 수정으로 코드·입력·설정·합의가 바뀌면 `$verify` 뒤 wrapup의 바뀐 항목만 다시 하며 설명도 지금 결과와 맞춘다. 마지막 verify 뒤 바뀐 것(코드·입력·설정)은 기억이 아니라 git으로 본다: 마지막 `$verify`가 verify/report_N.md를 넣은 커밋(wrapup이 고쳐 쓴 커밋은 아님) 뒤를 `git log --stat <그 해시>..HEAD`로, 커밋하지 않은 변경은 `git status --short`로 보고, 코드·입력·설정이 바뀌었으면 그 해시(또는 파일)와 그 뒤 다시 돌린 확인(wrapup의 재실행 등. 없으면 '재검증 없음')을, 둘 다 없으면 '없음'을 남은 한계에 한 줄로 남긴다.
- 제출 문서에 비워 둔 사람 몫 칸(답변·회고 등)이 남아 있으면 파일과 질문 제목(사용자가 직접 쓴다. 위 첫 줄에서 새 대화를 권하지 않는 때면 이 대화에서).
- 제출 문서의 '남은 한계' 절은 사용자가 직접 읽을 곳이라는 것. 고칠 말을 알려 주면 그대로 반영한다.
- 설명하는 순서: 결론(무엇이 언제 어떻게 되나) → 이유(담당자 말·데이터·숫자) → 확인(실제 실행 주체·방법·대상 환경을 기록대로 적고, 안 했으면 '미실행') → 약점은 '지점 → 발생 조건과 파급 → 다음에 검증·개선할 것'. 약점·장애·한계·보완을 묻는 문항은 뒤의 세 단계만으로 된다.
