# relay: 담당자 답 정리 (질문 세션, 개발 중에도 씀)

코드는 고치지 않고 행 대조도 하지 않는다.

## 1. 기록
- 협업 기록에 한 줄씩 추가한다: 시각 / 보낸 질문(원문 그대로. 사용자가 고쳐 보냈다고 하지 않았으면 직전 초안) / 담당자 답(그대로. 사용자가 요약해 붙였으면 '요약'이라고 적는다) / 바뀐 확인표 항목 이름(없으면 '없음'). 파일은 README가 정한 협업 기록, 없으면 COLLAB.md. 질문 초안과 사용자에게 보인 선택표는 파일에 쓰지 않는다.
- 요구 확인표의 상태를 고친다. README 문장과 담당자가 말한 것만 '확정'이다. 담당자가 답하지 않은 처리안은 '가정'으로 둔다. 내가 답을 해석해 채운 부분은 '가정'으로 적는다.
- 결정 기록은 여기서 쓰지 않는다(개발 세션이 그 변경을 적용하는 단계에서 쓴다). 개발 시작 메모가 이미 있으면 바뀐 것을 메모 끝에 '합의 뒤 변경'으로 덧붙인다.

## 2. 짚을 것
- README와 다른 답: "README에는 A, 담당자는 B"로 적고, 어느 쪽인지 묻는 질문을 만든다. 다른 답이 없으면 아무것도 적지 않는다.
- "구체적으로 물어봐 달라"는 답: 앞 질문을 실제 데이터 한 건이나 사용 장면의 한 순간을 짚는 질문으로 바꾼다.
- "알아서 하세요": 결과(건수나 핵심 결과)를 크게 바꾸는 것만 세 개 이내로 골라 처리안 두셋과 영향 건수, 추천을 사용자에게 보이고, 사용자가 고른 것을 '가정(사용자 결정)'으로 적는다. 나머지는 추천안을 '가정(기본값)'으로 적고 한 줄 목록으로 보인다(사용자가 바꾸라고 하면 바꾼다). 한 번만 묻는다. 다음 메시지에 "이렇게 정했습니다" 한 줄로 알린다. 범위 합의로 보지 않는다.
- 답에 데이터에 없는 새 이름이나 사실(바뀐 것, 새로 들어온 것, 알려진 문제, 규칙, 누군가의 짐작)이 나오면: 확인표에 새 행으로 넣는다. 그 답에 따라 결과의 숫자·ID나 권고가 바뀔 수 있으면 다음 메시지의 세 개 안에 그것에 대한 질문 하나를 먼저 넣는다: 언제부터 어디에 해당하는지(처음과 그 뒤), 기록에 적힌 것 말고 같이 바뀐 것, 짐작이면 그 근거. 이미 '확인 필요'로 따로 두기로 한 건의 사정이나 처리 방침의 이유로 덧붙인 짐작('~일 수 있어서')은 묻지 않고 '가정'으로 둔다.
- 앞선 답과 모순되면 바로 짚는다.
- 담당자가 되묻거나 질문을 이해하지 못했으면: 같은 질문을 실제 데이터 한 건과 쉬운 말로 다시 쓴 답장을 만든다.
- 일부만 답했거나 "너무 많다·길다"고 하면: 답 안 된 질문 중 결과를 가장 크게 바꾸는 것 하나만 두세 줄로 다시 묻는다. 그 뒤로는 담당자가 받아 준 개수만큼만 한 메시지에 넣고, 답 안 된 나머지는 '다음에 물을 것'으로 남긴다. 협업 기록에 '한 번에 n개'를 적어 다음 초안도 따른다.

## 3. 다음 메시지 초안 (둘 중 하나, 코드 블록 하나로)
- '질문'이 남았으면: 답에 따라 결과의 숫자·ID나 권고가 바뀌는 것부터 세 개 안팎을 넣는다. 확정된 항목은 다시 묻지 않는다. 데이터 질문은 "① [실제 데이터 한 건] → [처리안], 아니면 [다른 선택지]" 모양으로 쓰고, 장면 질문(결과를 보고 누가 무엇을 정하거나 하는지, 선택지와 비용·시간 또는 지킬 것, 짐작하는 것)을 아직 하지 않았으면 하나를 넣는다. 건수는 질문마다 하나까지, 비교·비율은 넣지 않는다. 넣지 못한 것은 '다음에 물을 것'으로 남긴다.
- 결과를 바꾸는 항목이 모두 확정·가정이면(데이터만 봐서는 알 수 없는 항목은 답이 없어도 합의를 막지 않고, 합의 메시지 끝 질문에 묶는다): 범위 합의 메시지. 만들 것 한 줄, 핵심 기준 한 줄, 이번에 만들지 않을 것과 이유 한 줄, 성공 기준 한 줄, 그리고 '정해 둔 기본값' 목록: 확인표의 '가정' 가운데 업무 기준(답이 바뀌면 결과가 바뀌는 것), 그리고 계획 문서 '데이터에서 이상한 점'의 항목 중 담당자가 답하지 않은 처리 방침은 하나도 빼지 않고 번호를 붙여 한 줄씩 쓴다("<항목>: <기본값>. 다르면 <무엇이 바뀌나>"). 구현 선택의 가정은 넣지 않는다. 끝에 "이대로 진행해도 될까요? 기본값 중 다른 것은 번호로 말씀해 주세요. 이 일에 쓰는 정해진 양식이나 따로 받은 공지·문서가 있으면 그대로 받아 볼 수 있을까요?". 이 턴에서는 개발 시작 메모를 쓰지 않는다.
  - 초안 위에 사용자에게 먼저 묻는다: 성공 기준과 '만들지 않을 것'이 이대로 맞는지, 두 조건이 부딪치면 무엇을 지키고 무엇을 조정할지. 사용자가 고치면 초안을 고쳐 다시 준다.
- 업무 말로 쓴다.

## 4. 합의가 끝나면: 개발 시작 메모
담당자가 범위 합의 메시지에 동의한 답을 붙여 넣었을 때만 쓴다. 답에 결과를 바꾸는 새 사실이나 바꿀 기본값이 섞여 있으면 쓰지 않고 1번부터 다시 한다. 계획 문서 맨 위에 '개발 시작 메모' 절을 쓰고 커밋한다. 개발은 새 세션이 이 메모만 보고 시작하므로, 대화에만 있는 내용이 없게 쓰되 한 화면 안팎으로 줄인다.
- 만들 것과 제출물
- 성공 기준(확인할 수 있는 숫자나 장면)
- 결과를 받는 장면: 누가 언제 무엇으로 보나, 양식·단위, 결과를 보고 고르는 선택지와 비용(담당자 말 그대로. 묻지 못했으면 '못 물음', 그런 장면이 없으면 '없음')
- 판정 기준과 출처: 기준마다 한 줄, 그 줄만 읽어도 뜻이 통하게 쓴다(확정·가정 구분과 확인표 항목 이름을 붙인다). 답 원문과 회차는 다시 쓰지 않는다
- 이번에 만들지 않을 것과 이유
- 데이터 처리 방침(이상한 점마다 어떻게 처리하는지)
- 환경(파이썬, pip, 포트)
- 시간 기준점(기본판 시각과, 못 지킬 때 뺄 것)
- 남은 가정과 '다음에 물을 것'

쓴 뒤 사용자에게 다음 두 가지를 알려 준다: `/new`로 새 세션을 연다 → `/plan`에서 "AGENTS.md와 계획 문서의 개발 시작 메모를 읽고 그대로 계획 세워 줘. 제출물·성공 기준·받는 장면의 항목마다 어느 단계가 만드는지 번호를 붙여 줘('못 물음'·'없음'은 빼고, 한 단계가 여러 항목을 맡아도 된다)".

## 5. 끝에
- `EXPLAIN.md`의 '담당자와 정한 것' 절에 한두 줄을 덧붙인다: 무엇을 왜 물었고, 답으로 무엇이 바뀌었나.
- 사용자에게 한 줄: 합의 전이면 남은 질문 수와 가정, 합의 뒤면 이번 답이 바꾼 것.
