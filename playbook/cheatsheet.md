## 당일 카드 — 지금 시점의 줄만 본다(아래 절의 문장을 모은 것이고 새 규칙은 없다)
- 시작·질문: README를 읽고 실제 남은 시간으로 kickoff. 실제 한 건의 이름·ID를 대조하고 결정 하나·담당자 한 명. 답은 원문으로 붙이고 결과를 바꾸는 미답·모순·새 사실만 이어 묻는다. 모른다·맡긴다는 주제는 새 사실 없이 다시 묻지 않는다. → '질문 세션'
- 합의·계획: 성공 기준·만들지 않을 것·부딪치면 지킬 것을 내 말로 답한다. 기본판·미룰 것을 고르고 모르는 방법·도구는 그 자리에서 묻는다. 새 기준은 담당자 우선순위·같은 대상·기준선·실제 한 건을 보고 이유를 말한다. → '계획 세우기'·'정해지지 않은 기준'
- 기본판: Browser로 한 건을 끝까지 해 보고 입력→처리→결과와 계산·반영 시점을 5분 동안 내 말로 쓴다. 어느 역할로 무엇을 눌렀나를 말하고 AI 검사와 내 실행을 구별한다. → '단계마다'
- 검증: 전에는 특히 볼 것·이유, 뒤에는 확인된 것·주장하지 않을 것과 연습 한 문항. 담당자에게는 '보낼 질문' 줄을 그대로 보내고 답은 그 건에만. → '시간표' 중간 검증
- 동결·마감: 남기는 필수 결함과 쓰는 사람에게 미치는 영향을 이유에 적고 고친 범위만 재검증한다. 고칠 것이 둘 이상이면 기록·커밋만 시키고 /new. wrapup 뒤 weakness·사람 몫 칸을 쓰고 점검 질문 10개를 받아 둔다. → '시간표' 기능 동결·사람 몫·연습 준비
- 제출 시작(0:30): 코드를 더 고치지 않는다. 사람 몫 칸 → 최종 커밋 → 제출. 남은 시간은 받아 둔 점검 질문을 AI 없이 내 말로 쓰고 Codex에 교정만 받는다. → '시간표' 제출 시작

## 개발 세션 (2:15~)

### 계획 세우기
- /new → /plan → 아래 블록을 그대로 붙여 넣는다
```text
계획 문서에서는 '개발 시작 메모' 절만 읽고 그대로 계획 세워 줘.
① 메모 항목 번호마다 맡을 단계와 완료 확인을 붙여 줘('못 물음'은 미확인으로 남기고 '없음'만 빼고, 한 단계가 여러 항목을 맡아도 된다).
② 단계마다 만들거나 고칠 것에 근거 항목 번호(메모 번호나 ⑦의 A번호)를 붙여 줘. A번호를 근거로 쓰려면 어느 메모 항목의 구현·검증에 왜 필요한지 적고, 번호를 못 붙이면 그것 없이 어느 항목을 만들거나 검증할 수 없는지 적어 줘. 같은 항목을 채우는 방법이 여럿이면 요구에 없는 기능이 덜 들어가고 고치기·검증하기 쉬운 쪽을 골라 줘(패키지를 쓸지 직접 만들지는 이 기준이 아니라 `.harness/LIBS.md` 원칙대로 정하고, 서버·화면·도표 도구는 그 웹 행대로 후보와 추천을 보여 주면 내가 고른다).
③ 그것도 못 적는 것은 빼서 맨 아래 '넣지 않은 것'에 한 줄로 남겨 줘.
④ 기본판 단계는 맨 앞에 두고 시간 기준점의 기본판 시각을 목표로 하고, 화면이 요구되면 요구된 로그인을 거쳐 실제 입력의 결과를 보는 최소 화면까지 포함해 잡아 줘.
⑤ 판정 기준이 미정이거나 담당자가 만드는 쪽에 맡긴 항목(메모에 '$criteria에서 정함'으로 적힌 것 포함)을 다루는 단계는 이름에 $criteria를 붙이고 기본판 뒤에 두되, 그 단계에는 기준 비교·선택과 고른 기준의 적용만 넣고 그 기준과 무관한 구현은 다른 단계에 둬 줘(그 기준이 결과의 단위나 저장 구조를 바꾸면 그 선택의 추천과 영향을 ⑦ 구조 단락에 적고 계획 승인 때 함께 정해 줘).
⑥ README가 요구한 제출 파일(실행 안내·설정 파일 등)은 그것이 쓰이는 단계에 넣어 동결 전에 준비하고(과제가 준 양식 파일은 제목·질문 줄·순서를 그대로 두고 그 아래만 채우며 새 제목을 만들지 않는다. 최종 검증 결과·사용자 확인을 반영하는 마감 갱신은 wrapup에서. 사용자 자신의 서술을 요구하는 칸은 대신 쓰지 않고 양식대로 두되 사용자가 준 답은 그대로 옮기고, 그 파일을 쓰는 단계 줄에 '사용자 답이 없는 사람 몫 칸은 비워 둔다'를 적어 줘), 중간 검증 $verify도 단계 한 줄로 넣어 줘. 기본판 보고 때 기본판 시각이 지나 있으면 남은 단계와 뺄 단계 후보·영향을 그 보고에 적어 줘(내가 고르기 전에는 빼지 않는다).
⑦ 단계 절 맨 앞(단계 목록 바로 위)에 구조 한 단락을 줄마다 번호(A1…)와 그렇게 둔 이유 한 마디를 붙여 써 줘: 구성 요소와 주고받는 것, 무거운 계산·변환을 언제 해서 어디에 두는지, 데이터 크기와 쓰는 사람 수에 맞춰 결과를 한 번에 내는 양, 다시 켜도 유지돼야 할 상태, 계산부터 그 결과를 쓰기까지 사이에 입력·상태가 바뀌거나 같은 요청이 겹칠 수 있고 결과에 영향을 주면 어느 시점의 입력으로 계산하고 결과에 그 입력 시점을 남기는지(아니면 '없음'), 실패를 어디에 남기는지. 기존 코드가 있으면 그 구조를 적고, 메모에 없는 것은 가정으로, 해당 없는 항목은 '없음'으로 쓴다('없음'을 채우려고 새 부품을 만들지 않는다)(웹이면 `.harness/LIBS.md` 웹 행대로 서버·화면 방식(도표가 있으면 도표 도구도)을 ②대로 정하고 그 행의 함정을 본다).
⑧ 계획이 승인되면 Default 모드로 돌아간 첫 요청에서 구조 단락·단계·'넣지 않은 것'을 계획 문서 '단계' 절에 그대로 옮기되 화면(템플릿·화면 요청 처리·스타일 파일)을 만들거나 고치는 단계는 ⑤처럼 이름 끝에 $screen을 붙이고(기준 비교·검증·마감 단계에는 붙이지 않는다), 계획 중 비교한 안의 핵심 숫자·고르거나 버린 이유와 내가 고른 것·내가 말한 이유('사용자 결정')를 결정 기록에 적어 커밋한 뒤 /new와 첫 단계를 시킬 문장 하나(첫 단계가 화면을 만들거나 고치면 앞에 $screen을 붙여)를 안내해 줘(Plan 모드는 파일을 쓰지 않는다).
```
- 웹이면 계획 중에 README 요구 수준에 맞는 서버·화면 방식(도표가 있으면 도표 도구도) 후보 둘셋과 추천이 나온다. 모르는 말은 되묻고("이 과제에서 B를 고르면 뭐가 달라져?"), 처음 고르는 핵심 계산 방법이나 결과에 영향을 주는 패키지 이름이 나왔는데 내가 설명하지 못하면 그 자리에서 "그 방법이 뭘 하는지 쉬운 말로, 다른 방법과 결과가 어떻게 다른지, 설치·계산 시간과 실패하면 어떻게 되는지, 어떤 조건이면 바꿀지"를 묻고(이미 이해하고 고른 것은 다시 비교하지 않는다), 후보 설명에 빠졌으면 "첫 화면이 어떤 모양이 되고, 좁은 미리보기 폭에서 표·도표는 어떻게 되고, 직접 만들어야 하는 부품은 뭐야?"를 묻는다. 고를 때 내 말로 이유 한 줄("A로. <이 과제 요구에서 나은 점 하나>")을 붙인다. 이 한 줄이 결정 기록에 내 결정으로 남는다
- 계획이 나오면 기본판 단계를 본다: 필수 동작과 그 완료 확인까지 기본판 시각 안에 끝낼 근거가 약해 보이면 "먼저 확인할 핵심 흐름과 뒤로 미룰 항목·영향을 보여 줘. 필수 연결은 유지하는 범위에서 내가 고를게"
- 'Implement this plan?'이 뜨면 1을 누르지 않는다(전부 한 번에 만들기 시작함). Esc → Shift+Tab으로 Default 모드(아래 줄의 Plan mode 표시가 사라짐) → 같은 대화에서 "계획을 계획 문서에 옮기고 커밋해 줘."(Codex가 계획을 '단계' 절에, 비교한 안과 내 선택·이유를 결정 기록에 적어 커밋하고 /new와 첫 단계 문장을 안내한다) → /new 뒤 받은 문장을 그대로 보낸다(번호는 붙이지 않는다. 계획 위쪽이 화면에서 사라져 번호를 잘못 볼 수 있다)

### 단계마다
- /compact 대신 /new를 쓴다. /new는 보고가 안내할 때만(단계의 결정 기록·커밋이 끝난 경계). 단계를 마쳤다는 보고에 /new 안내가 없으면 "결정 기록·커밋 됐어? 그럼 /new 뒤 보낼 문장 줘"라고 묻는다. 그때 /new 뒤에는 받은 문장을 그대로 보낸다(정할 것의 답은 그 문장에 붙인다)
- 단계 보고를 받으면 쉬운 설명 세 줄(EXPLAIN.md에도 남는다)과 결정 기록의 이유를 읽고, 실제 한 건이 어떤 순서로 무엇이 되는지 내 말로 한 줄 말해 본다(코드를 열 필요는 없다)
- 설명과 내가 알던 기준이 다르거나 이해가 안 되면: "<실제 ID>가 어떻게 되는지 쉬운 말로 다시 설명해 줘"
- 서로 독립적인 이해 질문은 모아 한 메시지로 묻는다(메시지마다 Codex가 대화 전체를 여러 번 다시 읽는다). 내가 아는 기준과 다르거나 답에 따라 다음 작업이 바뀌는 질문은 바로 묻는다
- '사용자가 정할 것'의 답은 /new 뒤 첫 문장에 번호가 아니라 내용과 이유로 붙인다. 예: "다음 단계 해 줘. 보류 행은 목록 아래 따로 보이기로, 숨기면 빠뜨린 줄 알 수 없어서. 정렬은 기한순으로, 담당자가 기한부터 본다고 해서." (이유 한 마디가 내 판단으로 기록된다). 정할 것이 없으면 바로 다음 단계를 시킨다. 단계를 시킬 때도 내 말로: "N단계 해 줘. <먼저 할 것>부터, <바꾸지 말 것>은 그대로, 끝나면 <실제 ID>로 확인해 줘". 단계 중에 뜨는 선택 창도 같다: 추천을 고를 때도 버튼만 누르지 말고 Other에 "<고른 것>으로. <이유 한 마디>"로 친다(버튼만 누르면 이유가 기록에 안 남는다)
- 화면을 만들거나 고치는 단계는 Codex가 준 문장에 $screen이 붙어 온다. 그대로 보낸다. 직접 시킬 때는 "$screen N단계 해 줘"로 하되, 같은 대화에서 이미 불렀으면 다시 붙이지 않는다. 첫 주요 화면 단계에서 Codex가 서버를 띄우고 .harness/tools/ui_check.py로 실제 폭에서 찍어 보고 큰 문제부터 고친다(도구가 안 되면 내가 본 것을 말해 준다). 나도 Browser 실제 폭에서 2분 본다: 영문 상태값·해시 같은 내부 값, 페이지 전체 가로 스크롤, 첫 화면에 답·근거·다음 동작, 도표의 축·값 → 보이면 "이 화면에서 <무엇이> <어떻게> 보여. 고쳐 줘"(기본판 보고를 받은 뒤라면 아래 기본판 3번대로 /new 뒤 첫 문장에)
- 기본판(입력→결과가 처음 한 번 도는 단계)이 나오면:
  1. 5~10분(기본판 보고 끝에 Codex가 청한다): Codex가 알려 준 주소로 Browser에서(실제로 쓸 주소와 창 폭으로) 로그인부터 핵심 작업·다시 열기까지 실제 한 건을 처음부터 끝까지 직접 해 보고 본 것을 말한다: 어느 역할로 무엇을 했고 무엇이 보였나, 어느 영역이 어느 폭에서 잘리거나 밀리나, 내부 값(영문 상태값·해시)·자릿수·단위·정렬 순서·되풀이되는 줄·어색한 문장처럼 업무 말로 안 읽히는 곳(Codex의 화면 도구는 배치만 재고 글자 내용은 안 본다. 화면 문제는 늦게 찾을수록 비싸다)
  2. 5분: 설명과 화면을 덮고 실제 입력 한 건(1번에서 직접 해 본 건이면 그것)의 입력→처리→실제 결과와 그 결과를 정한 기준, 그 계산이 어느 동작에서 되고 화면에 언제 반영되는지를 내 말로 codex 탭에 보내되, 아직 확인 못한 점이 있으면 확인할 입력·조작과 기대 결과도 함께 적는다. 기록·실제 결과와 다른 곳만 짚어 달라고 한다(실행한 것과 아직 안 한 확인을 나누며, 코드를 열 필요는 없다).
  3. 고칠 것은 이 대화에서 시키지 않고, 기본판 보고가 안내한 /new 뒤 첫 문장에 함께 붙인다(대화가 길어지면 문맥이 차 자동 압축될 수 있다)
- 업무 기준(포함·제외)은 내가 정하지 않는다. Codex가 '보낼 질문'에 줄을 쓰면 복사해 메신저로
- 요구에 없는 기능과 안 쓰는 코드는 남기지 않는다
- 승인 창이 뜨면 내용을 읽고 y. 같은 명령이 되풀이되면 '다시 묻지 않기'(p)
- 서버: Codex가 백그라운드로 띄우고 주소를 알려 준다 → Browser. 서버 출력은 /tmp/server.log(이상하면 "server.log 끝 보고 원인 말해 줘"). 띄우는 승인 창은 내용을 보고 p(다시 묻지 않기)
- 담당자에게 새 답이 오면 개발 세션에서도 같은 방법으로 주고받은 내용을 통째로 붙여 넣는다(보낸 질문이 함께 들어가 어느 질문의 답인지 맞춰진다)
- 시간이 밀리거나 같은 문제가 길어지면: "남은 단계 중 뺄 것 후보와 영향 알려 줘" → 내가 고르고 이유를 말한다(결정 기록에 남는다)
- Codex가 실행 중이면 기다리지 말고: 담당자에게 보낼 줄 보내기, Browser로 직전 화면 보기, 다음에 시킬 말과 확인할 실제 ID 준비, verify·wrapup이 도는 동안에는 제출 문서 사람 몫 칸(회고)의 초안을 내 말로 써 두기와 tutor 탭에서 "$weakness 연습이야. 점검 질문 10개 줘"로 점검 질문 받아 두기, tutor 탭에서 `$tutor N단계`(지금 단계의 방법·기록된 이유·다른 안·실제 한 건의 길. 아래 'tutor 탭')
### tutor 탭 (읽기 전용 둘째 Codex. 설명만 하고 파일을 쓰지 않는다)
- 켜기(계획이 승인돼 첫 단계를 시킨 뒤, 같은 작업 폴더에서): codex --no-alt-screen -s read-only -a never → "$tutor 1단계". 승인 창이 뜨지 않아야 정상이다(뜨면 켠 명령을 다시 본다)
- 언제: codex 탭이 실행 중일 때 "$tutor N단계"(방법·기록된 이유·다른 안·실제 한 건의 길·깨지는 곳. 끝의 '따라가 볼 한 건'은 답하고 싶을 때만) / 보고가 어려우면 "$tutor <실제 ID>가 왜 그 결과가 돼?" 같은 질문 / codex 탭이 선택지를 물으면 그 질문을 그대로 긁어 "$tutor 선택" 아래에 붙여 선택지마다 실제 한 건이 어떻게 달라지는지와 기록이 어느 쪽인지 듣고, 고른 것과 이유는 내 말로 codex 탭에 답한다 / verify·wrapup이 새 에이전트를 기다리는 동안과 weakness 전에 "$tutor 전체"
- 답의 꼬리표를 본다: [계획]은 기록에 있는 것, [코드]는 지금 코드(커밋·미커밋), [실행]은 실행해 얻은 값, [일반]은 일반 지식. "기록에 이유 없음"이 나오면 tutor가 준 '주 세션에 보낼 문장'(결정 기록에 이유를 적어 달라는 것)을 codex 탭에 보낸다. 점검 질문에는 기록에 있는 이유로 답한다
- 여기에는 담당자 답을 붙이지 않는다(기록은 codex 탭에서). 고치기·결정·질문 보내기도 codex 탭에서. codex 탭이 묻고 있으면 그 답이 먼저다. 대화가 길어지면 아무 때나 /new

- 1:25(5.5시간 2:35)(중간 검증). verify 전인데 Codex가 아직 단계 중이면 끝나기를 기다리지 말고(실행 중이면 Esc로 끊고) "시간 됐어. 여기서 멈추고 한 것·남은 것을 계획 문서에 적고 커밋해 줘"를 보내고, 그 보고를 받은 뒤:

  2. "$verify 해 줘. 특히 볼 것: <결정에 쓰이는 항목>, 이유: <왜 그것이 걱정되나>, 예상: <짐작되면 값>. 내가 본 장면: <어느 역할로 어느 주소·폭에서 무엇을 끝까지 했나>"(숫자는 몰라도 된다. 저장·승인처럼 상태를 바꾸는 기능은 Codex가 사본 서버를 따로 띄워 검사한다) → curl 승인 창은 p(다시 묻지 않기)

  2. Codex가 짚은 곳은 내 문장을 고쳐 다시 보낸다
  3. EXPLAIN.md 맨 아래 '한 화면 요약'과 제출 문서의 '남은 한계'를 직접 읽고, 고칠 말을 Codex에 보낸다
  4. /new → "제출 문서에서 비워 둔 사람 몫 칸을 내가 쓸게. EXPLAIN.md '내 말로 정리'(있으면)와 결정 기록·검증 보고·커밋에서 질문마다 쓸 만한 장면 후보를 근거와 함께 보여 주고, 내 문장이 기록과 다른 곳만 짚어 줘. 다 쓰면 이 칸이 비었다고 적힌 다른 문서 줄도 고치고, 점검 도구를 돌리고 커밋해 줘" → 질문마다 내 말로 쓴다(AI가 쓴 문장을 그대로 넣지 않는다). 끝 안내가 $wrapup·$weakness를 다시 권해도 한 것은 다시 하지 않는다: weakness를 했으면 받은 점검 질문으로 5번, 안 했으면 1번
  5. 점검 질문 10개를 한꺼번에 받아 둔다(tutor 탭에서 미리 받았으면 그것으로). 푸는 것은 제출 시작 뒤. 0:30이 되면 하던 것을 멈추고 아래 제출 시작으로
- 일찍 끝났으면: 동결 전이고 wrapup 전이면 verify 보고가 보인 후보(동결 전에 끝나는 것만) 가운데 하나를 고르거나 마감을 고르고 이유를 내 말로 한 줄 말한다. 마감을 골랐거나 동결 뒤면 기능은 더하지 않고 제출 시간을 남겨 두고 이 순서로: ① 결과를 바꾸는 미확인 기준을 담당자에게 ② 아직 확인하지 못한 실제 사용 장면을 실제 주소·폭·역할로 처음부터 끝까지 따라가 보고, 제출 문서의 '미실행'을 실행 ③ "$weakness 점검 질문 해 줘"로 내 말로 설명. 없는 항목은 건너뛴다. 답이나 수정으로 기준·코드가 바뀌면 관련 검증과 제출 문서를 갱신하고, 바뀐 흐름·숫자·출처만 5분 안에 내 말로 다시 써 "다른 곳만 짚어 줘"로 보낸다
- 0:30(계획 문서의 제출 시작. 5.5시간도 0:30)  코드·입력·설정은 더 고치지 않는다. Codex에 치고 있던 메시지가 있으면 그대로 보내고 "남은 한계 커밋부터" → 사람 몫 칸이 비어 있으면 같은 대화에서 질문마다 내 말로 한두 줄 보내 넣고 커밋 → 저장·마지막 커밋 확인 → 제출 화면 안내대로 버튼 누르기 직전까지 준비(누르는 것은 아래 연습 뒤 0:10). /new나 다른 스킬로 넘어가지 않고, 파일을 모아 검수하지 않는다. AI를 쓸 수 있는 시간이 제출과 함께 끝날 수 있으니 연습은 버튼을 누르기 전에 한다
  - 버튼만 남긴 뒤: 받아 둔 점검 질문을 (0:10까지 남은 분 − 교정 5) ÷ 5개(0개 이상, 받은 수 이하. 서로 다른 종류부터) AI 없이 내 말로 쓴다. 문항마다 5분이 되면 다음 문항. 마지막 5분은 쓴 답을 Codex에 보내 기록과 다른 문장만 교정받는다(코드는 고치지 않는다. AI 없이 답하는 후속 질문은 제출물에서 나온다)

## 내가 말할 자리 (문장은 내 말로. 이유 한 마디가 내 판단으로 기록된다)
- kickoff의 '보낼 질문'을 보면: 그대로 보낼지, 모르는 말·숫자를 빼거나 줄여 보낼지와 그 이유. 고쳐 보냈으면 담당자 답을 붙일 때 그렇다고 알린다
- 담당자 답을 붙일 때: README와 다른 점, 답에서 새로 생긴 경우(그럼 이건?), 질문이 많으면 결과가 바뀌는 것만 남기라는 말
- 범위 합의 전 $relay의 물음에: 성공 기준과 안 만들 것이 맞는지, 부딪치면 무엇을 지킬지를 내 말로
- 스택·화면 방식 후보가 나오면: 모르는 말은 되묻고, 고른 것과 이유 한 줄
- 선택지에 다른 생각이 있을 때(codex 탭에서): 생각대로 물어도 된다. 맞장구만 듣지 않으려면 "내 의견에 맞추지 말고, 추천이 바뀌면 어떤 사실 때문인지 말해 줘"를 붙이고, 고른 것과 이유는 내 말로. 같은 반론을 tutor 탭에 먼저 던져 보면 기록 근거로 따져 준다
- 단계 보고 뒤: 쉬운 설명에서 내가 알던 기준과 다른 곳, 다음에 시킬 단계와 끝나면 확인할 실제 ID. 구현 선택이 나오면 결과가 달라지는지 묻는다
- 서버가 켜진 뒤: 어떤 사용자로 무엇을 물었고 무엇이 나왔는지, 맞는지 이상한지, 어느 폭에서 어디가 잘리는지
- $verify 전후: 전에는 특히 볼 것과 이유(짐작되면 예상), 뒤에는 확인된 것과 아직 주장하지 않을 것
- AI 결과가 나오면: 문서 번호와 줄을 직접 열어 화면 발췌와 같은지
- wrapup 마지막 질문: 번호마다 고칠지 둘지와 이유. 사람 몫 칸(답변·회고)은 wrapup이 비워 두니 '사람 몫·연습 준비'의 4번(제출 시작 전) 새 대화에서 내가 쓴다: 질문마다 내가 겪은 장면을 먼저 말하고, 기록(결정 기록·검증 보고·커밋)과 다른 곳을 짚게 한 뒤 다 쓰면 점검 도구 → 커밋
- 보고가 길고 어려우면 짧게 다시 말해 달라고 한다

## 정해지지 않은 기준을 내가 만들어야 할 때 (기준값·점수·등급·우선순위·'더 나은 것'의 정의 등. 과제 종류와 상관없이)
- 담당자에게 한 줄씩(따로 보낸다): "이 결과로 누가 무엇을 결정하나요?" / "그때 반드시 지켜야 하는 것이 있나요?" / "손해 중 무엇을 먼저 줄여야 하나요?"
- 단계 보고가 다음 단계에 $criteria가 붙었다고 하면 그 단계를 시킬 때 같이 보낸다: "$criteria N단계 해 줘"
- 담당자가 모르면: "내가 고를 수 있게 안마다 얻는 것·잃는 것·추천 이유를 숫자로 보여 줘." 고를 때 내 말로 한 문장: "나는 ___을 지키면서 ___을 먼저 줄이려고 이 안을 고른다"
- 숫자가 상식과 어긋나면: "고치지 말고 어느 조건이 빠져서 그런지 말해 줘."
- 마감 전에: 기준선·버린 안·데이터 흐름·추천이 바뀌는 조건을 기록에서 찾아 AI 없이 한 번 설명해 본다(AI 없이 답하는 후속 질문의 '여러 안·고른 이유·한계'가 된다)

## Browser
PORT에 포트 → URL은 / (끝에 / 를 붙인다) → 원형 화살표. 안 열리면: 터미널 오류 → 실제 포트 → 0.0.0.0 → 경로. 이 창의 폭이 실제 사용 폭이다. 잘리는 곳은 "어느 영역이 어느 폭에서 어떻게"로 말한다

## 막힐 때
- 메시지를 /로 시작하면 명령으로 처리된다("/new 하기 전에…"도 /new가 된다). 문장은 /로 시작하지 않는다
- 고르라는데 선택 창이 안 보이면: "선택지를 여기 글로 다시 보여 줘"
- 스킬이 안 보임: /new. 그래도 없으면 ".agents/skills/kickoff/SKILL.md를 읽고 그대로 해 줘"
- tutor 탭이 승인 창을 띄우거나 파일을 쓰려 함: 읽기 전용으로 켰는지 본다(codex --no-alt-screen -s read-only -a never). 그래도 쓰려 하면 "쓰지 마. 주 세션에 보낼 문장으로 줘". tutor 답과 codex 탭 설명이 다르면 둘 다 맞다고 보지 말고 codex 탭에 "tutor가 <이렇게> 봤어. 기록·데이터로 어느 쪽이 맞는지 확인해 줘"
- $verify 만 치고 Enter를 누르면 스킬이 골라지기만 한다. Enter를 한 번 더 누르거나 "$verify 해 줘"로 친다
- 새 에이전트(spawn_agent)가 안 됨: 스킬이 직접 한다. 그대로 둔다
- 입력창 근처에 '? N questions'(Codex가 쌓아 둔 질문)가 보이면 먼저 열어 답한다. 승인 창이 함께 떠 있으면 승인부터 처리하고 키를 누르기 전에 어느 창인지 본다
- Codex가 멈춘 듯함: 승인 대기인지 본다. 실행 중(esc to interrupt)이면 같은 요청을 다시 보내지 않는다(중복 전송은 같은 일을 두 번 시키고 토큰을 늘린다). 멈출 땐 Esc. 플랫폼 오류(401 등)로 끊겼으면 무엇까지 됐는지 보고 끝나지 않은 일만 "계속해" 한 번 보낸다
- 서버를 띄우다 명령이 안 끝남: Esc → "서버는 출력을 파일로 돌려 백그라운드로 다시 띄워 줘"
- 화면이 안 바뀜: 서버는 켤 때 코드를 읽는다. "옛 서버 끄고 다시 띄워 줘"
- 화면 점검 도구(ui_check)가 설치 안 됨: 3분 넘게 붙잡지 않는다. 내가 Browser에서 실제 폭으로 보고 "어느 영역이 어느 폭에서 어떻게"를 말해 준다
- 저장·승인처럼 상태를 바꾸는 기능은 $verify가 사본 서버(저장 파일·DB까지 사본)를 다른 포트로 띄워 검사한다(작업 폴더 서버에는 보내지 않는다)
- 커밋이 '형식에 맞지 않아' 막힘: Codex가 메시지를 고쳐 다시 한다. 급하면 shell 탭에서 git add <파일> && git commit -m "feat(<범위>): <한 일>"
- 같은 오류 두 번: AGENTS.md대로라면 재현 명령·원인 후보·확인할 것을 먼저 말하고, 가설 하나를 작은 변경으로 확인한 뒤 유지·수정·되돌림을 정한다. 안 하면 "고치기 전에 원인 후보와 확인 방법부터 말해 줘."
- 행 대조가 안 맞음: "빠진 ID부터 찾아 줘."
- 모델 오류 반복, 또는 남은 컨텍스트가 60% 아래: 단계가 끝난 뒤 /new → "계획 문서에서는 개발 시작 메모(합의 뒤 변경 포함)·단계·결정 기록 절, 협업 기록에서는 확인표의 '질문'·'정의 확인'·'답 대기' 행만 읽고 다음 단계 해 줘"(wrapup의 번호 질문에 답한 뒤에는 고른 내용과 수정·재검증 상태가 기록·커밋됐다는 안내를 확인하고, 필요하면 /new → "$wrapup 해 줘. 수정 계속"으로 이어 간다)
- '외부 변경 감지': '외부 변경 불러오기'. 에디터에서 직접 고치지 않는다
- RAM 부족: 안 쓰는 서버와 프로세스를 끈다
- 터미널 Ctrl+C: 글을 선택했을 때만 복사. 선택 없이 누르면 실행 중인 명령이 멈춘다

## 설명할 때
결론(무엇이 언제 어떻게 되나) → 이유(담당자 말·데이터·숫자) → 확인(실제 실행 주체·방법·대상 환경을 기록대로 적고, 안 했으면 '미실행') → 약점은 '지점 → 발생 조건과 파급 → 다음에 검증·개선할 것'. 약점·장애·한계·보완을 물으면 뒤의 세 단계만. 이름은 한 화면 요약(없으면 제출 문서의 데이터 흐름·남은 한계)의 것을 그대로. 전제가 내 구현과 다르면 차이부터 말한다. 확인 못 한 것은 확인 못 했다고 하고, 지금 코드가 어떻게 할지와 확인 방법을 말한다.
