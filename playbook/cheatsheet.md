# 치트시트 (시각은 남은 시간, 3시간 작업 기준 예시)

## 시작 (3:00, 5분 안에)
1. 터미널 + 두 번 → 탭 이름을 codex · log · shell 로(log 탭은 `tail -F /tmp/server.log`로 서버 출력을 본다. 파일이 아직 없어도 기다린다)
2. shell 탭에서 하네스 설치(승인 창이 안 뜬다. 설치기가 끝에서 자체 점검까지 돌린다):
   git clone --depth 1 https://github.com/Chocochip-213/chocochip-codex-harness /tmp/h && bash /tmp/h/setup.sh
   - '완료', '하네스 파일만 따로 커밋했습니다', '자체 점검 … 실패 0'이 보이면 끝. 실패한 도구는 쓰지 않는다(원인은 bash .harness/tools/selftest.sh)
   - 'git 사용자 이름·이메일이 없습니다'가 나오면 안내대로 git config 두 줄 → bash /tmp/h/setup.sh
   - clone이 'already exists'로 멈추면(이미 받아 둠) bash /tmp/h/setup.sh
3. codex 탭: codex → 신뢰 확인 → $kickoff 까지 쳐서 목록에 kickoff가 뜨는지($만 치면 다른 스킬이 많아 안 보일 수 있다)
   - Fast·Approve for me로 켠다(Fast는 같은 모델·추론 강도로 응답만 빨라진다. Approve for me는 샌드박스는 그대로 두고 승인 요청을 검토 AI가 대신 판단한다): codex --no-alt-screen -c service_tier="fast" --approve-for-me → /status 에서 Fast와 권한을 본다. 오류가 나면 그냥 codex 로 켜고 /fast 와 /permissions → Approve for me 를 고른다(안 보이면 기본 승인 그대로 두고 승인 창은 아래대로)
   - 되면 더하는 선택(미확인): -c plan_mode_reasoning_effort="xhigh" 를 붙이면 /plan 때 깊이 생각한다. 오류가 나거나 /model 에 값이 안 보이면 빼고 켠다. 설정 파일은 건드리지 않는다
   - 켜자마자 업데이트하고 'restart Codex'로 끝나면 codex를 한 번 더 친다
   - codex 안에서 설치했으면 /new 를 친 뒤에 보인다(금지 규칙도 /new 뒤부터 적용)
   - /new 뒤 어디서 실행할지 묻는 창이 뜨면 1(Use current Git worktree). 2를 고르면 다른 폴더 복사본에서 작업하게 된다
4. README를 끝까지 읽는다(사람이 직접)

## 질문 세션 (2:50~2:15)
- "$kickoff 남은 시간 2시간 50분. 내가 읽은 목표: <한 줄>" → COLLAB.md의 요구 확인표와 PLAN.md의 시간 기준점을 30초 훑는다 → 보낼 질문을 고른다(빼거나 바꾸면 Codex가 COLLAB.md '보낼 질문' 절을 고쳐 쓴다) → 편집기에서 COLLAB.md '보낼 질문' 절의 줄을 복사해 메신저로(한 줄이 질문 하나. 줄바꿈 Shift+Enter, 보내기 Enter)
- 담당자 답이 오면 DM 창에서 내 질문과 담당자 답을 이름·시각째 통째로 긁어 그대로 붙여 넣는다(Ctrl+Shift+V. 앞에 아무것도 안 붙여도 된다. Codex가 일하는 중에는 붙이지 않는다). 지난번 붙인 뒤 새로 온 부분만 긁는다(섞여도 이미 기록한 쌍은 다시 적지 않는다). Codex가 '보낼 질문' 절에 새로 쓴 줄을 다시 복사해 보낸다
  - 답 끝의 한 줄(남은 질문 수나 바뀐 것)이 안 나오면 같은 내용 앞에 "$relay "를 붙여 다시 보낸다
- '보낼 질문'에 만드는 방법을 정해 달라는 질문(계산 방법·데이터 처리 방식 고르기)이 섞여 있으면 빼고 보낸다. 지금 업무·시스템이 어떻게 돌아가는지 묻는 줄은 남긴다: "만드는 방법은 내가 정할게. 업무 질문만 남겨 줘"
- 담당자가 일부만 답해도 위처럼 붙여 넣는다 → 가장 중요한 질문 하나만 다시 묻는 줄이 나온다. DM에 보냈다고 보이는데 답이 안 온 줄은 '보냄(답 대기)'로 남는다. "너무 많다"고 했을 때만 이후 묶음 개수도 줄어든다
- 붙여넣기가 막히면 담당자 답을 요약해 직접 친다: "담당자 답 요약: …"
- 담당자가 한 번에 하나만 받으면: '보낼 질문'의 줄을 하나씩 보내고, 보낸 질문과 답을 모아 한 번에 위처럼 붙인다(한 질문마다 붙이지 않는다. 다음에 물을 것을 바꾸는 답은 바로 붙인다)
- 담당자 답이 기억나지 않으면 Codex에게 다시 설명시키지 말고 편집기에서 COLLAB.md 확인표를 미리보기로 본다. 물을 때는 짧게: "확인표에서 아직 '질문'·'정의 확인'·'답 대기'인 것만 한 줄씩"
- 2:15쯤(질문 마감, 계획 문서 시간 기준점): 남은 질문은 '가정(기본값)'으로 두고(보낸 줄의 '답 대기' 표시는 남는다) 범위 합의로 간다(답은 개발 중에도 받는다). 모른다고 하거나 알아서 정하라고 한 주제는 다시 묻지 않는다(내가 정하고 가정으로 남긴다. 기준값·점수·우선순위는 기본판 뒤 $criteria에서 비교해 고른다)
- 질문이 다 풀리면 $relay가 먼저 묻는다(안 물으면 "범위 합의로 넘어가자"): 성공 기준·안 만들 것이 맞나, 조건이 부딪치거나 시간이 모자라면 무엇을 지키나 → 내가 답한다 → 범위 합의 메시지와 그 아래 질문 줄을 '보낼 질문' 절에 쓴다 → 복사해 메신저로 → 동의 답을 위처럼 붙여 넣으면 계획 문서 맨 위에 '개발 시작 메모'를 쓴다(동의 답이 10분 안에 안 오면 "동의 대기로 두고 개발 시작 메모 써 줘"라고 보내고 계획으로 간다. 답은 개발 중에 위처럼 붙인다)

## 개발 세션 (2:15~)

### 계획 세우기
- /new → /plan → 아래 블록을 그대로 붙여 넣는다
```text
계획 문서에서는 '개발 시작 메모' 절만 읽고 그대로 계획 세워 줘.
① 메모 항목 번호마다 맡을 단계와 완료 확인을 붙여 줘('못 물음'은 미확인으로 남기고 '없음'만 빼고, 한 단계가 여러 항목을 맡아도 된다).
② 단계마다 만들거나 고칠 것에 근거 항목 번호(메모 번호나 ⑦의 A번호)를 붙여 줘. A번호를 근거로 쓰려면 어느 메모 항목의 구현·검증에 왜 필요한지 적고, 번호를 못 붙이면 그것 없이 어느 항목을 만들거나 검증할 수 없는지 적어 줘. 같은 항목을 채우는 방법이 여럿이면 요구에 없는 기능이 덜 들어가고 고치기·검증하기 쉬운 쪽을 골라 줘(패키지를 쓸지 직접 만들지는 이 기준이 아니라 `.harness/LIBS.md` 원칙대로 정하고, 서버·화면·도표 도구는 그 웹 행대로 후보와 추천을 보여 주면 내가 고른다).
③ 그것도 못 적는 것은 빼서 맨 아래 '넣지 않은 것'에 한 줄로 남겨 줘.
④ 기본판 단계는 맨 앞에 두고 시간 기준점의 기본판 시각을 목표로 하고, 화면이 요구되면 요구된 로그인을 거쳐 실제 입력의 결과를 보는 최소 화면까지 포함해 잡아 줘.
⑤ 판정 기준이 미정이거나 담당자가 만드는 쪽에 맡긴 항목(메모에 '$criteria에서 정함'으로 적힌 것 포함)을 다루는 단계는 이름에 $criteria를 붙이고 기본판 뒤에 두되, 그 단계에는 기준 비교·선택과 고른 기준의 적용만 넣고 그 기준과 무관한 구현은 다른 단계에 둬 줘(그 기준이 결과의 단위나 저장 구조를 바꾸면 그 선택의 추천과 영향을 ⑦ 구조 단락에 적고 계획 승인 때 함께 정해 줘).
⑥ README가 요구한 제출 파일(실행 안내·설정 파일 등)은 그것이 쓰이는 단계에 넣어 동결 전에 준비하고(최종 검증 결과·사용자 확인을 반영하는 마감 갱신은 wrapup에서), 중간 검증 $verify도 단계 한 줄로 넣어 줘. 기본판 보고 때 기본판 시각이 지나 있으면 남은 단계와 뺄 단계 후보·영향을 그 보고에 적어 줘(내가 고르기 전에는 빼지 않는다).
⑦ 단계 절 맨 앞(단계 목록 바로 위)에 구조 한 단락을 줄마다 번호(A1…)와 그렇게 둔 이유 한 마디를 붙여 써 줘: 구성 요소와 주고받는 것, 무거운 계산·변환을 언제 해서 어디에 두는지, 데이터 크기와 쓰는 사람 수에 맞춰 결과를 한 번에 내는 양, 다시 켜도 유지돼야 할 상태, 계산부터 그 결과를 쓰기까지 사이에 입력·상태가 바뀌거나 같은 요청이 겹칠 수 있고 결과에 영향을 주면 어느 시점의 입력으로 계산하고 결과에 그 입력 시점을 남기는지(아니면 '없음'), 실패를 어디에 남기는지. 기존 코드가 있으면 그 구조를 적고, 메모에 없는 것은 가정으로, 해당 없는 항목은 '없음'으로 쓴다('없음'을 채우려고 새 부품을 만들지 않는다)(웹이면 `.harness/LIBS.md` 웹 행대로 서버·화면 방식(도표가 있으면 도표 도구도)을 ②대로 정하고 그 행의 함정을 본다).
⑧ 계획이 승인되면 Default 모드로 돌아간 첫 단계 요청에서 구조 단락·단계·'넣지 않은 것'을 계획 문서 '단계' 절에 그대로 옮기고, 계획 중 내가 고른 것과 내가 말한 이유를 결정 기록에 '사용자 결정'으로 적어 커밋한 뒤 그 단계를 시작해 줘(Plan 모드는 파일을 쓰지 않는다).
```
- 웹이면 계획 중에 README 요구 수준에 맞는 서버·화면 방식(도표가 있으면 도표 도구도) 후보 둘셋과 추천이 나온다. 모르는 말은 되묻고("이 과제에서 B를 고르면 뭐가 달라져?"), 후보 설명에 빠졌으면 "첫 화면이 어떤 모양이 되고, 좁은 미리보기 폭에서 표·도표는 어떻게 되고, 직접 만들어야 하는 부품은 뭐야?"를 묻는다. 고를 때 내 말로 이유 한 줄("A로. <이 과제 요구에서 나은 점 하나>")을 붙인다. 이 한 줄이 결정 기록에 내 결정으로 남는다
- 'Implement this plan?'이 뜨면 1을 누르지 않는다(전부 한 번에 만들기 시작함). Esc → Shift+Tab으로 Default 모드(아래 줄의 Plan mode 표시가 사라짐) → 같은 대화에서 "계획의 첫 단계 해 줘."(번호는 붙이지 않는다. 계획 위쪽이 화면에서 사라져 번호를 잘못 볼 수 있다. Codex가 먼저 계획을 계획 문서 '단계' 절에 옮겨 커밋하고 첫 단계만 한다). /new는 그 단계 보고가 안내할 때

### 단계마다
- /compact 대신 /new를 쓴다. /new는 보고가 안내할 때만(단계의 결정 기록·커밋이 끝난 경계). 단계를 마쳤다는 보고에 /new 안내가 없으면 "결정 기록·커밋 됐어? 그럼 /new 뒤 보낼 문장 줘"라고 묻는다. 그때 /new 뒤에는 받은 문장을 그대로 보낸다(정할 것의 답은 그 문장에 붙인다)
- 단계 보고를 받으면 쉬운 설명 세 줄(EXPLAIN.md에도 남는다)과 결정 기록의 이유를 읽고, 실제 한 건이 어떤 순서로 무엇이 되는지 내 말로 한 줄 말해 본다(코드는 열지 않는다)
- 설명과 내가 알던 기준이 다르거나 이해가 안 되면: "<실제 ID>가 어떻게 되는지 쉬운 말로 다시 설명해 줘"
- 서로 독립적인 이해 질문은 모아 한 메시지로 묻는다(메시지마다 Codex가 대화 전체를 여러 번 다시 읽는다). 내가 아는 기준과 다르거나 답에 따라 다음 작업이 바뀌는 질문은 바로 묻는다
- '사용자가 정할 것'의 답은 /new 뒤 첫 문장에 번호가 아니라 내용과 이유로 붙인다. 예: "다음 단계 해 줘. 보류 행은 목록 아래 따로 보이기로, 숨기면 빠뜨린 줄 알 수 없어서. 정렬은 기한순으로, 담당자가 기한부터 본다고 해서." (이유 한 마디가 내 판단으로 기록된다). 정할 것이 없으면 바로 다음 단계를 시킨다. 단계를 시킬 때도 내 말로: "N단계 해 줘. <먼저 할 것>부터, <바꾸지 말 것>은 그대로, 끝나면 <실제 ID>로 확인해 줘"
- 화면을 만들거나 고치는 단계는 "$screen N단계 해 줘"로 시킨다(같은 대화에서 이미 $screen을 불렀으면 "N단계 해 줘"만). 첫 주요 화면 단계에서 Codex가 서버를 띄우고 .harness/tools/ui_check.py로 실제 폭에서 찍어 보고 큰 문제부터 고친다(도구가 안 되면 내가 본 것을 말해 준다). 나도 Browser 실제 폭에서 2분 본다: 영문 상태값·해시 같은 내부 값, 페이지 전체 가로 스크롤, 첫 화면에 답·근거·다음 동작, 도표의 축·값 → 보이면 "이 화면에서 <무엇이> <어떻게> 보여. 고쳐 줘"(기본판 보고를 받은 뒤라면 아래 기본판 3번대로 /new 뒤 첫 문장에)
- 기본판(입력→결과가 처음 한 번 도는 단계)이 나오면:
  1. Codex가 알려 준 주소로 Browser에서(실제로 쓸 주소와 창 폭으로) 로그인부터 핵심 작업·다시 열기까지 직접 해 보고 본 것을 말한다: 어느 역할로 무엇을 했고 무엇이 보였나, 어느 영역이 어느 폭에서 잘리거나 밀리나(화면 문제는 늦게 찾을수록 비싸다)
  2. 5분: 실제 입력 하나가 어떤 순서로 무엇이 되는지 내 말로 적고, Codex에게 맞는지만 확인받는다(코드는 열지 않는다)
  3. 고칠 것은 이 대화에서 시키지 않고, 기본판 보고가 안내한 /new 뒤 첫 문장에 함께 붙인다(대화가 길어지면 문맥이 차 자동 압축될 수 있다)
- 업무 기준(포함·제외)은 내가 정하지 않는다. Codex가 '보낼 질문'에 줄을 쓰면 복사해 메신저로
- 요구에 없는 기능과 안 쓰는 코드는 남기지 않는다
- 승인 창이 뜨면 내용을 읽고 y. 같은 명령이 되풀이되면 '다시 묻지 않기'(p)
- 서버: Codex가 백그라운드로 띄우고 주소를 알려 준다 → Browser. 서버 출력은 /tmp/server.log(이상하면 "server.log 끝 보고 원인 말해 줘"). 띄우는 승인 창은 내용을 보고 p(다시 묻지 않기)
- 담당자에게 새 답이 오면 개발 세션에서도 같은 방법으로 DM을 이름·시각째 통째로 붙여 넣는다(보낸 질문이 함께 들어가 어느 질문의 답인지 맞춰진다)
- 시간이 밀리거나 같은 문제가 길어지면: "남은 단계 중 뺄 것 후보와 영향 알려 줘" → 내가 고르고 이유를 말한다(결정 기록에 남는다)
- Codex가 실행 중이면 기다리지 말고: 담당자에게 보낼 줄 보내기, Browser로 직전 화면 보기, 다음에 시킬 말과 확인할 실제 ID 준비

  2. "$verify 해 줘. 특히 볼 것: <결정에 쓰이는 항목>, 이유: <왜 그것이 걱정되나>, 예상: <짐작되면 값>. 내가 본 장면: <어느 역할로 어느 주소·폭에서 무엇을 끝까지 했나>"(숫자는 몰라도 된다. 저장·승인처럼 상태를 바꾸는 기능은 Codex가 사본 서버를 따로 띄워 검사한다) → curl 승인 창은 p(다시 묻지 않기)

  4. 끝나면 /new(대화가 길어 이후 요청마다 비싸다. 새 대화는 앞 대화를 못 본다)

- 1:25~0:57 남은 단계와 함께 보강 순서: ① verify 차이 ② 받는 장면 항목 중 아직 파일·화면에 없거나 실제 폭에서 읽히지 않는 것(내가 본 화면 문제 포함) ③ 원본은 그대로 두고, 요구된 입력 범위나 제공 데이터에 있는 이상 유형 하나를 사본에서 바꿔 돌려 예상 결과와 비교(숫자가 예상과 다르게 바뀌면 "원인부터 말해 줘. 고치지는 마.", 그 밖의 가상 유형은 남은 한계로)

## 내가 말할 자리 (문장은 내 말로. 이유 한 마디가 내 판단으로 기록된다)
- kickoff의 '보낼 질문'을 보면: 그대로 보낼지, 모르는 말·숫자를 빼거나 줄여 보낼지와 그 이유. 고쳐 보냈으면 담당자 답을 붙일 때 그렇다고 알린다
- 담당자 답을 붙일 때: README와 다른 점, 답에서 새로 생긴 경우(그럼 이건?), 질문이 많으면 결과가 바뀌는 것만 남기라는 말
- 범위 합의 전 $relay의 물음에: 성공 기준과 안 만들 것이 맞는지, 부딪치면 무엇을 지킬지를 내 말로
- 스택·화면 방식 후보가 나오면: 모르는 말은 되묻고, 고른 것과 이유 한 줄
- 단계 보고 뒤: 쉬운 설명에서 내가 알던 기준과 다른 곳, 다음에 시킬 단계와 끝나면 확인할 실제 ID. 구현 선택이 나오면 결과가 달라지는지 묻는다
- 서버가 켜진 뒤: 어떤 사용자로 무엇을 물었고 무엇이 나왔는지, 맞는지 이상한지, 어느 폭에서 어디가 잘리는지
- $verify 전후: 전에는 특히 볼 것과 이유(짐작되면 예상), 뒤에는 확인된 것과 아직 주장하지 않을 것
- AI 결과가 나오면: 문서 번호와 줄을 직접 열어 화면 발췌와 같은지
- wrapup 마지막 질문: 번호마다 고칠지 둘지와 이유. 사람이 판단한 부분을 써 달라고 하면 내 말로 함께 쓴다
- 보고가 길고 어려우면 짧게 다시 말해 달라고 한다

## Browser
PORT에 포트 → URL은 / (끝에 / 를 붙인다) → 원형 화살표. 안 열리면: 터미널 오류 → 실제 포트 → 0.0.0.0 → 경로. 이 창의 폭이 실제 사용 폭이다. 잘리는 곳은 "어느 영역이 어느 폭에서 어떻게"로 말한다

## 막힐 때
- 메시지를 /로 시작하면 명령으로 처리된다("/new 하기 전에…"도 /new가 된다). 문장은 /로 시작하지 않는다
- 고르라는데 선택 창이 안 보이면: "선택지를 여기 글로 다시 보여 줘"
- 스킬이 안 보임: /new. 그래도 없으면 ".agents/skills/kickoff/SKILL.md를 읽고 그대로 해 줘"
- $verify 만 치고 Enter를 누르면 스킬이 골라지기만 한다. Enter를 한 번 더 누르거나 "$verify 해 줘"로 친다
- 새 에이전트(spawn_agent)가 안 됨: 스킬이 직접 한다. 그대로 둔다
- 입력창 근처에 '? N questions'(Codex가 쌓아 둔 질문)가 보이면 먼저 열어 답한다. 승인 창이 함께 떠 있으면 승인부터 처리하고 키를 누르기 전에 어느 창인지 본다
- Codex가 멈춘 듯함: 승인 대기인지 본다. 실행 중(esc to interrupt)이면 같은 요청을 다시 보내지 않는다(중복 전송은 같은 일을 두 번 시키고 토큰을 늘린다). 멈출 땐 Esc. 플랫폼 오류(401 등)로 끊겼으면 무엇까지 됐는지 보고 끝나지 않은 일만 "계속해" 한 번 보낸다
- 서버를 띄우다 명령이 안 끝남: Esc → "서버는 출력을 파일로 돌려 백그라운드로 다시 띄워 줘"
- 화면이 안 바뀜: 서버는 켤 때 코드를 읽는다. "옛 서버 끄고 다시 띄워 줘"
- 화면 점검 도구(ui_check)가 설치 안 됨: 3분 넘게 붙잡지 않는다. 내가 Browser에서 실제 폭으로 보고 "어느 영역이 어느 폭에서 어떻게"를 말해 준다
- 저장·승인처럼 상태를 바꾸는 기능은 $verify가 사본 서버(저장 파일·DB까지 사본)를 다른 포트로 띄워 검사한다(작업 폴더 서버에는 보내지 않는다)
- 커밋이 '형식에 맞지 않아' 막힘: Codex가 메시지를 고쳐 다시 한다. 급하면 shell 탭에서 git add <파일> && git commit -m "feat(<범위>): <한 일>"
- 같은 오류 두 번: AGENTS.md대로라면 재현 명령·원인 후보·확인할 것을 먼저 말하고, 가설 하나를 작은 변경으로 확인한 뒤 유지·수정·되돌림을 정한다. 안 하면 "고치기 전에 원인 후보와 확인 방법부터 말해 줘."
- 행 대조가 안 맞음: "빠진 ID부터 찾아 줘."
- 모델 오류 반복, 또는 남은 컨텍스트가 60% 아래: 단계가 끝난 뒤 /new → "계획 문서에서는 개발 시작 메모(합의 뒤 변경 포함)·단계·결정 기록 절, 협업 기록에서는 확인표의 '질문'·'정의 확인'·'답 대기' 행만 읽고 다음 단계 해 줘"
- '외부 변경 감지': '외부 변경 불러오기'. 에디터에서 직접 고치지 않는다
- RAM 부족: 안 쓰는 서버와 프로세스를 끈다
- 터미널 Ctrl+C: 글을 선택했을 때만 복사. 선택 없이 누르면 실행 중인 명령이 멈춘다

## 설명할 때
결론(무엇을 어떻게 했나) → 이유(담당자 말·데이터·숫자) → 약점은 '지점 → 발생 조건과 파급 → 다음에 검증·개선할 것'. 약점·장애·한계·보완을 물으면 뒤의 세 단계만. 이름은 한 화면 요약(없으면 제출 문서의 데이터 흐름·남은 한계)의 것을 그대로. 전제가 내 구현과 다르면 차이부터 말한다. 확인 못 한 것은 확인 못 했다고 하고, 지금 코드가 어떻게 할지와 확인 방법을 말한다.
