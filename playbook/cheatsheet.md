# 치트시트 (시각은 남은 시간, 3시간 작업 기준 예시)

## 시작 (3:00, 5분 안에)
1. 터미널 + 두 번 → 탭 이름을 codex · server · shell 로
2. shell 탭에서 하네스 설치(승인 창이 안 뜬다. 설치기가 끝에서 자체 점검까지 돌린다):
   git clone --depth 1 https://github.com/Chocochip-213/chocochip-codex-harness /tmp/h && bash /tmp/h/setup.sh
   - '완료', '하네스 파일만 따로 커밋했습니다', '자체 점검 … 실패 0'이 보이면 끝. 실패한 도구는 쓰지 않는다(원인은 bash .harness/tools/selftest.sh)
   - 'git 사용자 이름·이메일이 없습니다'가 나오면 안내대로 git config 두 줄 → bash /tmp/h/setup.sh
   - clone이 'already exists'로 멈추면(이미 받아 둠) bash /tmp/h/setup.sh
3. codex 탭: codex → 신뢰 확인 → 아래 줄의 강도가 medium인지(아니면 /model) → $kickoff 까지 쳐서 목록에 kickoff가 뜨는지($만 치면 다른 스킬이 많아 안 보일 수 있다)
   - 설치 출력에 추론 강도 설정을 넣었다고 나왔으면 평소 medium, /plan을 켜면 high로 바뀐다(과제 설정이 있어 넣지 않았다고 나오면 /plan 전에 /model에서 high를 고른다)
   - 켜자마자 업데이트하고 'restart Codex'로 끝나면 codex를 한 번 더 친다
   - codex 안에서 설치했으면 /new 를 친 뒤에 보인다(금지 규칙도 /new 뒤부터 적용)
   - /new 뒤 어디서 실행할지 묻는 창이 뜨면 1(Use current Git worktree). 2를 고르면 다른 폴더 복사본에서 작업하게 된다
4. README를 끝까지 읽는다(사람이 직접)

## 질문 세션 (2:50~2:15)
- "$kickoff 남은 시간 2시간 50분. 내가 읽은 목표: <한 줄>" → COLLAB.md의 요구 확인표와 PLAN.md의 시간 기준점을 30초 훑는다 → 초안 아래 후보에서 보낼 질문을 직접 고른다 → 메신저로 (줄바꿈 Shift+Enter, 보내기 Enter)
- 담당자 답이 오면 "$relay " 를 치고 답을 붙여 넣는다(Ctrl+Shift+V) → 다음 메시지를 메신저로
- 초안에 담당자가 답할 수 없는 기술 질문(계산 방법·데이터 처리·시스템 동작)이 섞여 있으면 빼고 보낸다: "기술적인 건 내가 정할게. 업무 질문만 남겨 줘"
- 담당자가 일부만 답하면 그대로 $relay에 붙여 넣는다 → 가장 중요한 질문 하나만 다시 묻는 답장이 나온다. "너무 많다"고 했을 때만 이후 메시지 개수도 줄어든다
- 붙여넣기가 막히면 담당자 답을 요약해 직접 친다: "$relay 담당자 답 요약: …"
- 담당자가 한 번에 하나만 받으면: 초안 질문을 하나씩 보내고, 답을 모아 한 번에 "$relay "로 붙인다(한 질문마다 relay하지 않는다. 다음에 물을 것을 바꾸는 답은 바로 relay)
- 2:15쯤(질문 마감, 계획 문서 시간 기준점): 남은 질문은 가정으로 두고 범위 합의로 간다. '모른다'·'정하실 몫'이라고 한 주제는 다시 묻지 않는다(내가 정하고 가정으로 남긴다)
- 질문이 다 풀리면 $relay가 먼저 묻는다: 성공 기준·안 만들 것이 맞나, 조건이 부딪치면 무엇을 지키나 → 내가 답한다 → 범위 합의 메시지를 준다 → 메신저로 → 동의 답을 "$relay "로 붙여 넣으면 계획 문서 맨 위에 '개발 시작 메모'를 쓴다

## 개발 세션 (2:15~)
- /new → /plan → "계획 문서에서는 '개발 시작 메모' 절만 읽고 그대로 계획 세워 줘. ① 메모 항목 번호마다 맡을 단계와 완료 확인을 붙여 줘('못 물음'은 미확인으로 남기고 '없음'만 빼고, 한 단계가 여러 항목을 맡아도 된다). ② 단계마다 만들거나 고칠 것에 근거 항목 번호를 붙여 줘. 번호를 못 붙이면 그것 없이 어느 항목을 만들거나 검증할 수 없는지 적고, 더 작은 방법이 있으면 그것을 골라 줘. ③ 그것도 못 적는 것은 빼서 맨 아래 '넣지 않은 것'에 한 줄로 남겨 줘. ④ 기본판 단계는 시간 기준점의 기본판 시각 전에 끝나게, 화면이 요구되면 요구된 로그인을 거쳐 실제 입력의 결과를 보는 최소 화면까지 포함해 잡아 줘. ⑤ 판정 기준이 미정이거나 담당자가 맡긴('정하실 몫') 항목을 다루는 단계는 이름에 $criteria를 붙이고 기본판 뒤에 두어 줘."
- /compact 대신 /new를 쓴다. 보고가 /new를 안내하면(단계를 마칠 때마다) /new → "계획 문서에서는 개발 시작 메모·단계·결정 기록 절, 협업 기록에서는 확인표의 '질문' 행만 읽고 다음 단계 해 줘"
- 기본판이 나오면 바로 서버를 켜 로그인부터 핵심 작업·다시 열기까지 직접 해 보고 본 것을 말한다(화면 문제는 늦게 찾을수록 비싸다)
- 'Implement this plan?'이 뜨면 1을 누르지 않는다(전부 한 번에 만들기 시작함). Esc → Shift+Tab으로 Default 모드(아래 줄의 Plan mode 표시가 사라짐) → "<계획의 첫 단계 번호>단계 해 줘."(계획은 앞의 시작 점검·범위 합의를 이어 3단계부터 번호를 붙일 수 있다)
- 이후 "다음 단계." 단계마다 보고의 쉬운 설명 세 줄(EXPLAIN.md에도 남는다)과 결정 기록의 이유를 읽고, 실제 한 건이 거치는 함수와 그 기준 줄을 2~3분 직접 연다. 설명과 내가 알던 기준이 다르거나 이해가 안 되면 "<실제 ID>가 이 함수에서 어떻게 되는지 쉬운 말로 다시 설명해 줘"
- 기본판(입력→결과가 처음 한 번 도는 단계)이 나오면 5분: 핵심 함수 하나를 열어 실제 입력 하나가 거치는 줄을 내 말로 적고, Codex에게 맞는지만 확인받는다
- '사용자가 정할 것'의 답은 /new 뒤 첫 문장에 번호가 아니라 내용으로 붙인다. 예: "다음 단계 해 줘. 빈 값 행은 따로 둔 행으로, 빠뜨리는 쪽이 더 위험해서. 정렬은 추천대로." (이유 한 마디가 내 판단으로 기록된다). 정할 것이 없으면 바로 다음 단계를 시킨다. 단계를 시킬 때도 내 말로: "N단계 해 줘. <먼저 할 것>부터, <바꾸지 말 것>은 그대로, 끝나면 <실제 ID>로 확인해 줘"
- 업무 기준(포함·제외)은 내가 정하지 않는다. Codex가 담당자 질문 초안을 주면 메신저로
- 요구에 없는 기능과 안 쓰는 코드는 남기지 않는다
- 승인 창이 뜨면 내용을 읽고 y. 같은 명령이 되풀이되면 '다시 묻지 않기'(p)
- 서버: "실행 명령만 알려 줘. 서버는 내가 켤게." → server 탭에서 실행 → Browser. 코드를 고치면 server 탭에서 Ctrl+C → 다시 실행
- 담당자에게 새 답이 오면 개발 세션에서도 "$relay " + 붙여넣기(질문을 만든 대화를 /new로 비웠으면 보낸 질문도 함께 붙이면 더 정확: "$relay 보낸 질문: … 답: …")
- 시간이 밀리면: "남은 단계 중 뺄 것 후보와 영향 알려 줘" → 내가 고른다
- 1:30  마지막 단계 보고 뒤 /new(개발 대화가 길어 그 안에서 검증하면 요청마다 비싸다. verify는 계획 문서와 파일에서 시작한다) → /status로 남은 사용량을 본다(여유가 적으면 남은 범위를 줄인다) → "$verify 해 줘"(숫자는 몰라도 된다. 특히 볼 것이 있으면 이름만: "특히 볼 것: <결정에 쓰이는 항목>") → curl 승인 창은 p(다시 묻지 않기). "다시 켜 달라"고 멈추면 server 탭에서 다시 켜고 다시 "$verify 해 줘" → 표가 모두 '같음'인가. 다르면 "원인을 확인해 말해 줘. 합의한 기준과 어긋난 구현 실수면 고치고, 검증 쪽 실수거나 기준이나 가정을 새로 정해야 하는 차이면 고치지 말고 물어 줘." → 고쳤으면 "$verify 해 줘". 끝나면 /new(대화가 길어 이후 요청마다 비싸다. 새 대화는 앞 대화를 못 본다). 그 뒤 담당자 답은 새 대화에서 "$relay <담당자 답>"(보낸 질문을 함께 붙이면 더 정확: "$relay 보낸 질문: … 답: …"), 보강은 "계획 문서에서는 개발 시작 메모·단계·결정 기록 절, 협업 기록에서는 확인표의 '질문' 행만 읽고 <할 일> 해 줘"
- 1:30~0:40 보강 순서: ① verify 차이 ② 받는 장면 항목 중 아직 파일·화면에 없는 것 ③ 원본은 그대로 두고, 요구된 입력 범위나 제공 데이터에 있는 이상 유형 하나를 사본에서 바꿔 돌려 예상 결과와 비교(숫자가 예상과 다르게 바뀌면 "원인부터 말해 줘. 고치지는 마.", 그 밖의 가상 유형은 남은 한계로) ④ 꾸밈
- 0:40  /new → "$wrapup 해 줘"(긴 대화를 비우고 시작) → 맨 끝의 번호 질문에 답한다("1 고침, 2 남김") → 서버를 다시 켜고 wrapup이 준 목록대로 Browser에서 눌러 본다

## 내가 말할 자리 (문장은 내 말로. 이유 한 마디가 내 판단으로 기록된다)
- kickoff 초안을 받으면: 그대로 보낼지, 모르는 말·숫자를 빼거나 줄여 보낼지와 그 이유. 고쳐 보냈으면 relay에 그렇다고 알린다
- 담당자 답을 relay할 때: README와 다른 점, 답에서 새로 생긴 경우(그럼 이건?), 질문이 많으면 결과가 바뀌는 것만 남기라는 말
- 단계 보고 뒤: 쉬운 설명에서 내가 알던 기준과 다른 곳, 다음에 시킬 단계와 끝나면 확인할 실제 ID. 구현 선택이 나오면 결과가 달라지는지 묻는다
- 서버를 켠 뒤: 어떤 사용자로 무엇을 물었고 무엇이 나왔는지, 맞는지 이상한지
- AI 결과가 나오면: 문서 번호와 줄을 직접 열어 화면 발췌와 같은지
- wrapup 번호 질문: 번호마다 고칠지 둘지와 이유
- 보고가 길고 어려우면 짧게 다시 말해 달라고 한다

## 정해지지 않은 기준을 내가 만들어야 할 때 (기준값·점수·등급·우선순위·'더 나은 것'의 정의 등. 과제 종류와 상관없이)
- 담당자에게: "이 결과로 누가 무엇을 결정하며, 무엇은 반드시 지키고 어떤 손해를 먼저 줄여야 하나요?"
- 단계 보고가 다음 단계에 $criteria가 붙었다고 하면 그 단계를 시킬 때 같이 보낸다: "$criteria N단계 해 줘"
- 담당자가 모르면: "내가 고를 수 있게 안마다 얻는 것·잃는 것·추천 이유를 숫자로 보여 줘." 고를 때 내 말로 한 문장: "나는 ___을 지키면서 ___을 먼저 줄이려고 이 안을 고른다"
- 숫자가 상식과 어긋나면: "고치지 말고 어느 조건이 빠져서 그런지 말해 줘."
- 마감 전에: 기준선·버린 안·데이터 흐름·추천이 바뀌는 조건을 기록에서 찾아 AI 없이 한 번 설명해 본다(서술형의 '여러 안·고른 이유·한계'가 된다)

## 막힐 때
- 스킬이 안 보임: /new. 그래도 없으면 ".agents/skills/kickoff/SKILL.md를 읽고 그대로 해 줘"
- $verify 만 치고 Enter를 누르면 스킬이 골라지기만 한다. Enter를 한 번 더 누르거나 "$verify 해 줘"로 친다
- 새 에이전트(spawn_agent)가 안 됨: 스킬이 직접 하도록 되어 있다. 그대로 진행
- Codex가 멈춘 듯함: 승인 대기인지 본다. 실행 중(esc to interrupt)이면 같은 요청을 다시 보내지 않는다(중복 전송은 같은 일을 두 번 시키고 토큰을 늘린다). 멈출 땐 Esc. 플랫폼 오류(401 등)로 끊겼으면 무엇까지 됐는지 보고 끝나지 않은 일만 "계속해" 한 번 보낸다
- 서버를 켜 놓고 안 끝남: Esc → server 탭에서 직접 켠다
- 화면이 안 바뀜: 서버는 켤 때 코드를 읽는다. 껐다 켠다
- 저장·승인처럼 상태를 바꾸는 기능을 마음 놓고 검사하려면: 작업 폴더를 /tmp에 복사해 다른 포트로 서버를 켜고, 저장 파일·DB도 그 사본을 가리키는지 확인한 뒤 그 주소를 $verify에 알려 준다(작업 폴더 서버에는 보내지 않는다)
- 커밋이 '형식에 맞지 않아' 막힘: Codex가 메시지를 고쳐 다시 한다. 급하면 shell 탭에서 git add <파일> && git commit -m "feat(<범위>): <한 일>"
- 같은 오류 두 번: AGENTS.md대로 재현 명령·원인 후보부터 말하게 되어 있다. 안 하면 "고치기 전에 원인 후보와 확인 방법부터 말해 줘."
- 행 대조가 안 맞음: "빠진 ID부터 찾아 줘."
- 같은 문제로 15분: 기능 하나를 빼고 결정 기록에 이유를 쓴다
- 모델 오류 반복, 또는 남은 컨텍스트가 60% 아래: 단계가 끝난 뒤 /new → "계획 문서에서는 개발 시작 메모·단계·결정 기록 절, 협업 기록에서는 확인표의 '질문' 행만 읽고 다음 단계 해 줘"
- '외부 변경 감지': '외부 변경 불러오기'. 에디터에서 직접 고치지 않는다
- RAM 부족: 안 쓰는 서버와 프로세스를 끈다
- 터미널 Ctrl+C: 글을 선택했을 때만 복사. 선택 없이 누르면 실행 중인 명령이 멈춘다

## 설명할 때
결론(파일·함수) → 이유(담당자 말·데이터) → 약점과 파급 → 확인한 것과 다음 검증. 전제가 내 구현과 다르면 차이부터 말한다. 확인 못 한 것은 확인 못 했다고 하고, 지금 코드가 어떻게 할지와 확인 방법을 말한다.
